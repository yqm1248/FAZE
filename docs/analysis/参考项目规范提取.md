# 参考项目规范提取

本仓库的工程规范不是自创，是从三个既有项目提取后适配到 Expo 前端场景。
本文记录**每份参考贡献了什么**，以及**哪些没有照搬、为什么**。

## 1. `D:\gitzxz\zxz-bi-server`（Spring Boot / Java，325 个 java 文件）

### 结构

```text
com.tfgc/
  annotation/ bo/ common/ config/ controller/ converter/ dto/ entity/ enums/
  factory/ filter/ interceptor/ mapper/ mapping/ properties/ service/ strategy/ utils/
```

采用「技术分层 + 业务子包」双维度组织。例如薪资包（xzb）同时出现在：

| 层 | 位置 | 职责 |
| --- | --- | --- |
| 契约 | `dto/xzb/`、`dto/xzb/qrhs/` | 请求/响应对象、任务上下文 |
| 流程 | `service/impl/` | 编排 |
| 数据访问 | `mapper/dm/`、`mapper/mysql/` | 按数据源分 |
| 状态 | `enums/` | `SalaryAuditStatusEnum` 等 |
| 规则 | `common/rule/calculation/bigdecimal/{fixed,incentive,insurance}/` | 计算规则拆成独立类 |

### 注释写法（本仓库直接采用）

类头：

```java
/**
 * @Description: 薪资包预算执行情况DTO
 * @Author: yang
 * @Date 2025-12-30
 */
```

方法：

```java
/**
 * 获取部门列表
 * @param request 部门列表请求参数
 * @return 部门列表
 */
```

### 值得学的工程模式

`TFGCFixedCalCmpRule` 把"固定薪资的构成项"抽象成函数引用列表：

```java
private final List<Function<EmployeeSalaryCalculationDTO, BigDecimal>> fixedFunctions = List.of(
    EmployeeSalaryCalculationDTO::getMonthlyPositionSalary,
    EmployeeSalaryCalculationDTO::getCommunicationSubsidy,
    EmployeeSalaryCalculationDTO::getTransportationSubsidy,
    EmployeeSalaryCalculationDTO::getMealSubsidy
);
```

新增一个薪资项只加一行，不改计算逻辑。**本仓库对应做法**：
`assets/legacy/index.ts` 把素材路径收成常量表；`shared/navigation` 把路由收成常量表。

### 没有照搬的

| 内容 | 原因 |
| --- | --- |
| `@Schema` / `@Operation` 注解体系 | 前端用 TS 类型 + JSDoc 表达同样的信息 |
| Service / Mapper / Entity 分层 | 本项目无数据库、无后端 |
| 262 KB 的 `IndexServiceImpl` | 规模本身不是优点；规范文档自己也写明"不接受其超长类作为规模标准" |

## 2. `C:\Users\14541\Desktop\2026.7.13实习\wgcloud`（Spring Boot / Java）

### 贡献

1. **根目录边界划分**：`config/ log/ src/ target/ 技术资料/`，配置、日志、源码、资料互不混放。
   → 本仓库对应：`design/ docs/ apps/ scripts/`，设计资产与代码分离。
2. **项目说明文件**：根目录 `CLAUDE.md` 用一页讲清项目是什么、怎么构建、跑什么命令、包结构各层职责。
   → 本仓库对应：[../../AGENTS.md](../../AGENTS.md) 与 [../architecture/法泽FAZE_技术路线_v2.3.md](../architecture/法泽FAZE_技术路线_v2.3.md)。
3. **按职责分包**：`controller / agentController / service / mapper / entity / dto / config / task / util / common / filter`
   中，`agentController` 与 `controller` 按"面向谁"而非"技术类型"区分。
   → 本仓库对应：`features/` 按业务域切分，而不是按 `pages/components/utils` 三层切。

### 没有照搬的

- `application-{profile}.yml` 多环境配置：本项目暂无环境差异，接入后端时再加 `app.config.ts` 的 env 分支。

## 3. `E:\项目文件\jxyd200`（pnpm monorepo：Expo APP + Vue PC + Java + Node）

### 结构（本仓库直接沿用）

```text
apps/mobile-app/
  app/          Expo Router 薄路由，每个文件一行 re-export
  features/     业务域，每域 {pages, components, api.ts, types.ts, presentation.ts, README.md}
  shared/       {api, auth, components, hooks, utils}
  assets/
```

关键做法：

1. **路由壳与页面分离**。`app/product-detail.tsx` 全文只有一行：

   ```ts
   export { default } from '@/features/product/pages/ProductDetailPage';
   ```

2. **`features/_template/` 模板目录**。给出 `.template` 后缀的骨架文件，新业务照着建，避免每次自由发挥。
3. **每个 feature 一份 README**。写清该域承载什么、页面与路由对照表、依赖边界、回退方式。
4. **共享目录准入标准**："只有被至少两个独立业务域使用、且没有业务词汇的组件才能进入共享目录"。
5. **注释风格**（TS）：

   ```ts
   /**
    * APP 唯一的后端地址来源。
    *
    * 页面、Feature 和上传工具均通过此常量拼接既有 API；不得在业务页面重新写入
    * 环境地址，以保持 Web、真机和 E2E 的环境切换口径一致。
    */
   ```

   先一句话职责，空行，再写约束与原因。

### 没有照搬的

| 内容 | 原因 |
| --- | --- |
| Tailwind v4 / Uniwind 类方案 | 类名字符串无法静态校验"是否用了令牌"，与"禁止令牌外字面量"的规则冲突。本项目改用 `StyleSheet` + `tokens.*` |
| `presentation.ts` 展示转换层 | 当前无后端状态码需要转换，接入后端时再加 |
| `_template/` 目录 | 页面数量少（12 个），先按规范文档约束；超过 20 个页面再引入模板目录 |
| pnpm workspace 多包 | 只有一个应用，不引入 workspace 复杂度 |

## 4. 三者的共同点（本仓库的底线）

三个项目虽然技术栈不同，但共享同一组工程底线：

1. **目录即文档**：看目录就知道代码在哪，不靠全文搜索。
2. **注释写"为什么"**：不写"做什么"。类头/文件头必须说明职责而非类名复述。
3. **命名表达职责**：禁止 `Data`、`Info`、`Util2`、`Manager` 这类泛名。
4. **状态与常量集中**：状态码、键名、路径不得散落在业务代码里。
5. **文档与代码同仓**：设计依据、实施记录、验收标准都在仓库内，不靠口头传递。
