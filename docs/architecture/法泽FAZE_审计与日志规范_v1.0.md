# 法泽 FAZE · 审计与日志规范（V1.0）

> **用途**：区分「审计」与「日志」两件事，定义各自的范围、字段、留存期、不可篡改要求与可查询性设计。
> **定稿日期**：2026-10-30
> **不重复的内容**：审计四要素的**定义**在《[数据表规范](法泽FAZE_数据表规范_v1.0.md)》§1.3；`operation_log` / `login_log` 的**DDL** 在技术路线 §5.11.5；AOP 采集的**代码写法**在《[后端代码规范](法泽FAZE_后端代码规范_v1.0.md)》§10.4；敏感字段的 **L1~L5 分级**在《数据表规范》§9。

---

# 一、先看问题：现在有「日志」，没有「审计」

## 1.1 实测结论

| 项 | 现状 | 证据 |
|---|---|---|
| 「审计四要素」的定义 | **有**（2026-10-30 补的） | 《数据表规范》§1.3 |
| `operation_log` / `login_log` 表结构 | **有** | 技术路线 §5.11.5 |
| 哪些动作**必须**审计 | **没有清单** | 只有零散几处（手工充值、调账、封禁、清退「必须写 operation_log」），散在技术路线 §4.8.4.2 与总纲 §5.2 |
| **留存期** | **0 处** | 全仓无「留存」「保存年限」「清理周期」的规定（技术路线 §4.7 只说「IM 离线消息清理」，那是业务数据不是日志） |
| **不可篡改** | **0 处** | 没有任何地方说审计日志能不能改/删 |
| **可查询性** | 部分 | PC A-26 有「操作日志」「登录日志」两个页面，但查询维度与索引没定 |
| **审计 vs 日志的分界** | **0 处** | 两份东西混着讲：`operation_log` 既是业务留痕又被当日志中心的数据源 |
| 应用日志的留存 | 技术路线 §4.7 无规定；logback 建议 30 天 | — |

## 1.2 五个必须定死的问题

| # | 问题 | 不定死的后果 |
|---|---|---|
| 1 | **审计和日志是不是一回事？** | 分不清就会用日志文件当审计证据——日志能删、能轮转、能被 `log.level=OFF` 关掉，**不能当审计** |
| 2 | **哪些动作必须审计？** | 「敏感操作必须留痕」是模糊要求，开发时必然漏：审核、退款、改价、封禁都可能忘 |
| 3 | **留多久？** | 网安法要求网络日志 ≥ 6 个月；钱的事更长。不定就默认「永远不删」，半年后表撑爆 |
| 4 | **能不能改/删？** | 能改的审计日志在纠纷、监管检查里没有证明力 |
| 5 | **怎么查？** | 有数据但查不出来，等于没有。PC A-26 要按什么条件筛、走哪个索引 |

# 二、分界：审计 ≠ 日志

## 2.1 定义

| | **审计（Audit）** | **日志（Log）** |
|---|---|---|
| 回答什么 | **谁**在**什么时候**对**什么东西**做了**什么**，结果如何 | **系统运行时发生了什么**（请求、异常、耗时、外部调用） |
| 服务谁 | 事后追责、合规检查、纠纷取证、内部稽查 | 开发者排障、运维监控、容量分析 |
| 消费者 | 业务方、法务、监管、客服 | 工程师 |
| 载体 | **数据库表**（`operation_log` / `login_log` / `balance_flow` 等） | **文件**（logback）+ 可选日志平台 |
| 生命周期 | **长期**（年） | **短期**（天） |
| 可修改性 | **只追加，不可改不可删** | 可轮转、可清理、可调级别 |
| 完整性要求 | 必须完整，漏记是缺陷 | 允许采样、允许丢（`discardingThreshold` 除外） |
| 失败处理 | **写不进去必须降级落盘并报警** | 写不进去就算了 |

## 2.2 为什么必须分开

**反例就在参考项目里**：

- **ZXZ** 的操作日志是**前端埋点写库**（`BIController:179-207`），且 `try/catch` 吞异常——**客户端可以不发，等于审计可伪造、可跳过**。
- **wgcloud** 的异常日志靠 55 个 Controller 里复制粘贴，实测 `AgentGoController:155-157`（**最高频的 agent 上报路径**）就没有——**靠手写必然漏**。
- wgcloud 还把日志写库和文件双写混在一起（`LogInfoService:59-71`），但那张 `LOG_INFO` 表**既能查又能当审计**，语义不清。

**一句话**：**日志的失败模式是「丢一行没人发现」，审计的失败模式是「漏一条查无对证」。**

## 2.3 一句话裁决

> **审计进数据库、日志进文件。**
> 一条记录如果要能拿出去当证据，它必须在 `operation_log` 里，而不是在某天的 `.log` 文件里。

# 三、审计

## 3.1 四要素（引用《数据表规范》§1.3，此处只列清单）

| 要素 | 字段 | 说明 |
|---|---|---|
| **谁** | `operator_id` + `operator_type` | `operator_type` ∈ `ADMIN` / `USER` / `LAWYER` / `SYSTEM`（系统任务的操作者记为 SYSTEM） |
| **何时** | `created_at` | UTC 存储，接口输出 +08:00 |
| **从哪** | `ip` | 客户端 IP；**内部任务写 `127.0.0.1`** |
| **做了什么** | `module` + `action` + `target_type` + `target_id` + `detail` | `detail` 是 JSON，存变更前后的值（见 §3.3） |

## 3.2 必须审计的动作清单（按段列，逐条核对）

**这是原文档最缺的部分**。判据三条，满足任一条就必须审计：

1. **动钱**（改余额、流水、退款、结算、抽成）；
2. **改不可逆状态**（审核通过/驳回、封禁、清退、注销、下架）；
3. **改别人能看到的内容**（文章发布/下架、法条修订、敏感词增删、公告推送）。

| 段 | 动作 | action 命名 | 是否审计 |
|---|---|---|---|
| **1** | 手工充值 | `WALLET_MANUAL_RECHARGE` | ✅ **必须**（锚点 `1-A4`） |
| 1 | 调账 | `WALLET_ADJUST` | ✅ 必须 |
| 1 | 用户封禁 / 解封 | `USER_BAN` / `USER_UNBAN` | ✅ 必须 |
| 1 | 实名审核通过/驳回 | `VERIFY_APPROVE` / `VERIFY_REJECT` | ✅ 必须（`1-A2`） |
| 1 | 律师入驻审核 | `LAWYER_APPROVE` / `LAWYER_REJECT` | ✅ 必须（`1-A3`） |
| 1 | 用户注销 | `ACCOUNT_CANCEL` | ✅ 必须（涉个保法） |
| 2 | 订单改价 / 手动退款 | `ORDER_PRICE_EDIT` / `ORDER_REFUND` | ✅ 必须 |
| 2 | 律师违规处理 | `LAWYER_VIOLATION` | ✅ 必须 |
| 5 | 提现审核（出款） | `WITHDRAW_APPROVE` / `WITHDRAW_REJECT` | ✅ **必须**（钱出去） |
| 5 | 结算单确认 | `SETTLEMENT_CONFIRM` | ✅ 必须 |
| 7 | 文章上架 / 下架 | `ARTICLE_PUBLISH` / `ARTICLE_OFFLINE` | ✅ 必须 |
| 7 | 法条修订 | `LAW_ITEM_EDIT` | ✅ 必须（AI 引用它） |
| 7 | 敏感词增删改 | `SENSITIVE_WORD_*` | ✅ 必须 |
| 7 | 公告推送 | `ANNOUNCEMENT_PUSH` | ✅ 必须（触达全量用户） |
| 7 | 内容审核处置 | `CONTENT_REVIEW_*` | ✅ 必须 |
| 7 | 工单分配/关闭 | `TICKET_*` | ⚠️ 建议 |
| 8 | 系统参数修改 | `SYS_CONFIG_EDIT` | ✅ 必须（抽成比例在这里） |
| **全部** | **登录 / 登出 / 登录失败** | — | ✅ 必须（走 `login_log`，不是 `operation_log`） |

**判定规则的落地**：每个管理端写接口（`POST`/`PUT`/`DELETE` 且 `/admin/` 前缀）**默认必须**标 `@OperationLog`；只有**纯查询**不标。CI 用 ArchUnit 断言：`modules.admin.controller` 下所有非 GET 方法必须有 `@OperationLog` 注解。

## 3.3 `operation_log` 的 `detail` 存什么

```json
{
  "before": { "balanceCents": 5000 },
  "after":  { "balanceCents": 15000 },
  "reason": "线下转账，凭证号 TX20261030001"
}
```

| 规则 | 说明 |
|---|---|
| **必须存 before/after** | 只存 after 无法回溯「改前是多少」 |
| **敏感字段脱敏后存** | 手机号存 `138****8888`；**身份证号不存**（只存 `realnameMasked`） |
| **禁止存密码、支付密码、token** | 即使是哈希也不行 |
| **大文本截断到 2000 字符** | 文章正文这类改的是引用 id + 摘要，不是全文 |
| `detail` 用 JSON 列 | MySQL 8 原生 `JSON` 类型，不存成 `TEXT` 再解析 |

## 3.4 不可篡改（工程保证，不是口号）

| 层 | 措施 |
|---|---|
| **应用层** | `operation_log` 的 Mapper **只提供 `insert` 与 `select`**。禁止 `update` / `delete` 方法（ArchUnit 断言：`OperationLogMapper` 不能有 update/delete） |
| **数据库层** | 该表**不给应用账号 `UPDATE` / `DELETE` 权限**（MySQL 用单独账号或 `GRANT INSERT, SELECT`） |
| **备份** | 每日备份，保留期与 §5 一致 |
| **可选增强** | 加 `prev_hash` 字段形成哈希链（每行含上一行的哈希）——**V1 不做**，成本高于收益；等有监管明确要求再加 |

> **注意**：`operation_log` 的清理**不由应用做**。超期的删除必须走**人工审批的运维脚本**，且删除前导出归档（§5.3）。

## 3.5 采集方式

**必须服务端 AOP**，禁止前端埋点（ZXZ 的反例见 §2.2）。

```java
@OperationLog(module = "trade", action = "WALLET_MANUAL_RECHARGE", targetType = "USER_BALANCE")
public void manualRecharge(...) { ... }
```

AOP 切面负责填：`operator_id`/`operator_type`（从 SecurityContext）、`ip`（从请求）、`created_at`、`target_id`（从方法参数或返回值）、`detail`（`before`/`after`）。

**写库必须异步 + 失败降级**（《后端代码规范》§10.4.1）——审计不能因为数据库抖动而丢。

# 四、日志

## 4.1 五个级别，各写什么

| 级别 | 语义 | 写什么 | 谁看 |
|---|---|---|---|
| `ERROR` | **需要人介入** | 未捕获异常、第三方服务挂了、资金链路失败、审计落库失败 | 运维告警 |
| `WARN` | 可自愈但异常 | 业务异常（余额不足、状态非法）、限流触发、重试、降级 | 运维巡检 |
| `INFO` | 关键业务节点 | 接口入口/出口摘要、任务开始/结束、审核结果、状态迁移 | 排障时看 |
| `DEBUG` | 排障细节 | SQL 参数、完整请求体（脱敏后）、外部调用耗时 | 只有本地/测试开 |
| `TRACE` | 不用 | — | — |

## 4.2 三条禁令

| 禁令 | 原因 |
|---|---|
| **禁止在循环里打 `INFO`** | 一个 3000 行的导入打 3000 条日志 |
| **禁止字符串拼接**：`log.info("order=" + order)` | 应 `log.info("order={}", order)`；前者无论级别都拼字符串 |
| **禁止 `System.out` / `printStackTrace()`** | ZXZ 的 `RedisUtil` 里有 17 处 `printStackTrace`（`RedisUtil:41,59,76…`），栈全进标准输出，不进日志文件 |

## 4.3 禁止写进日志的内容（与《数据表规范》§9 的 L1~L5 对齐）

| 级别 | 能否进日志 | 例外 |
|---|---|---|
| L1 可明文（昵称、头像 URL） | ✅ | — |
| L2 手机号 | **只能脱敏**（`138****8888`） | 无 |
| L3 身份证号 | **只能脱敏**（`110***********1234`） | 无 |
| L4 私有资源（身份证影像、执业证、聊天附件） | ❌ **禁止**（连 ossKey 都不打完整） | 无 |
| L5 仅审计可查（密码哈希、支付密码、聊天原文） | ❌ **绝对禁止** | 无 |

**另外三条**：
- **禁止打印完整请求体**：聊天内容、身份证影像的 base64 可能在里面。
- **禁止打印 token / `Authorization` 头**（ZXZ `LBpmProcessInstanceController:48` 打印了 `mkCode`——换 token 的凭证）。
- **禁止打印 SQL 语句全文含参数值**：`MyBatis` 的 `DEBUG` 级别会打印带参数的完整 SQL，**生产环境必须关到 `INFO`**。

## 4.4 结构化日志

日志行统一格式，便于 grep 和后续接日志平台：

```text
%Y-%m-%dT%H:%M:%S.SSS%z | LEVEL | traceId | logger | msg
```

logback pattern：

```xml
<pattern>%d{yyyy-MM-dd'T'HH:mm:ss.SSSXXX} | %-5level | %X{traceId:-no-trace} | %logger{40} | %msg%n</pattern>
```

**为什么不用 JSON**：法泽当前没有日志平台，纯文本 + 固定分隔符足够 grep；接平台时再换 encoder，不改业务代码。

## 4.5 `traceId`（贯穿）

| 环节 | 做法 |
|---|---|
| 入口 | `TraceIdFilter`：取请求头 `X-Request-Id`，没有则生成 UUID |
| 传播 | `MDC.put("traceId", id)`；响应头回填 `X-Trace-Id` |
| 跨服务调用 | 出站时把 `traceId` 放进 `X-Request-Id` |
| 异步任务 | 任务表里存 `trace_id`，执行时从表里取出来放 MDC |
| 响应体 | `R.traceId`（《接口规范》§5.1） |
| 清理 | `finally { MDC.remove("traceId") }`（线程池复用线程，不清会串） |

**为什么异步任务也要带**：一个「发短信」任务失败时，日志里只有任务 id，无法知道它来自哪次用户请求。

# 五、留存期（原文档完全没有）

## 5.1 法律依据（合规决策权在负责人，此处给依据与建议值）

| 依据 | 条文 | 对法泽的含义 |
|---|---|---|
| 《网络安全法》第二十一条 | 「采取监测、记录网络运行状态、网络安全事件的技术措施，并按照规定**留存相关的网络日志不少于六个月**」 | **登录日志 / 操作审计 ≥ 6 个月** |
| 《个人信息保护法》第五十六条 | 「个人信息保护影响评估报告和**处理情况记录**应当至少保存**三年**」 | **个人信息处理相关审计 ≥ 3 年** |
| 《电子商务法》第三十一条 | 「商品和服务信息、**交易信息**保存时间自交易完成之日起**不少于三年**」 | **订单、支付、退款记录 ≥ 3 年** |
| 《会计档案管理办法》 | 会计凭证、账簿等保管期限分 10 年 / 30 年 | 若余额流水被认定为会计资料，按 30 年；**平台侧建议 ≥ 5 年** |

> **这不是法律意见**。`AGENTS.md` §1.1 明确「合规事项由项目负责人负责」。本节给的是**技术必须实现的能力**（可配、可归档、可导出），**具体年限由负责人拍板后填进 `sys_config`**。

## 5.2 分级留存（可配置，不写死）

| 数据 | 载体 | 建议留存 | 配置项 |
|---|---|---|---|
| 应用日志 | 文件 | **30 天** | `log.retention-days` |
| 错误日志 | 文件（单独 appender） | **90 天** | 同上 |
| `login_log` | 数据库 | **≥ 180 天**（网安法 6 个月） | `audit.login-log-days` |
| `operation_log` | 数据库 | **≥ 3 年**（个保法 / 电商法） | `audit.operation-log-days` |
| `balance_flow` / `payment_record` | 数据库 | **≥ 5 年**（资金） | `audit.finance-log-days` |
| `reconciliation_diff` | 数据库 | ≥ 5 年 | — |

## 5.3 归档与删除（不是直接 DELETE）

```text
达到留存期
   ↓
① 导出归档（CSV / Parquet）到冷存储（OSS 归档型）
   ↓
② 校验归档完整性（行数 + 校验和）
   ↓
③ 人工审批（运维 + 负责人）
   ↓
④ 分批删除（每批 ≤ 1000 行，避免长事务锁表）
```

**禁止**：
- 应用代码里写 `DELETE FROM operation_log WHERE created_at < ...` 并挂在 `@Scheduled` 上自动跑——**审计日志的删除必须有人签字**。
- 直接 `TRUNCATE`。

# 六、可查询性（PC A-26）

## 6.1 三个页面的查询维度

| 页面 | 查询条件 | 排序 |
|---|---|---|
| **操作日志**（A-26 之一） | 时间范围 / 操作人 / 模块 / 动作 / 目标 id / IP | 时间倒序 |
| **登录日志**（A-26 之二） | 时间范围 / 账号 / IP / 结果（成功/失败） | 时间倒序 |
| **资金流水**（A-07~A-10 关联） | 用户 / 类型 / 时间 / 业务单号 | 时间倒序 |

## 6.2 索引必须覆盖查询

| 表 | 索引 | 覆盖的查询 |
|---|---|---|
| `operation_log` | `idx_operation_log_created_at` | 时间范围 |
| | `idx_operation_log_operator_id_created_at` | 按操作人 + 时间 |
| | `idx_operation_log_target_type_target_id` | 查「这条订单/用户被谁改过」 |
| `login_log` | `idx_login_log_phone_created_at` | 按账号查登录历史 |
| | `idx_login_log_ip_created_at` | 查同 IP 的多账号（撞库特征） |

**「查这条订单被谁改过」**是最常用的取证查询（`target_type='ORDER' AND target_id=?`），必须有索引。

## 6.3 导出

| 项 | 规则 |
|---|---|
| 导出行数上限 | 同步导出 ≤ 5000 行；超过走任务表（《后端代码规范》§3.9） |
| 导出格式 | CSV（Excel 兼容，`UTF-8 with BOM` 防中文乱码） |
| **导出本身也要审计** | `action='LOG_EXPORT'`——**查日志这个动作也要留痕**，否则谁导了全量用户数据没人知道 |

# 七、告警（日志的一个用途，但不是审计）

## 7.1 什么该告警

| 条件 | 级别 | 说明 |
|---|---|---|
| `ERROR` 日志出现 | 立即 | 但频率限制见 §7.2 |
| **审计落库失败**（降级到文件） | **立即 + 高优先级** | 这是审计链断了 |
| 资金恒等式不成立（`余额 ≠ SUM(流水)`） | 立即 | 锚点 `1-A7` |
| 第三方服务连续失败 ≥ 5 次 | 1 分钟内 | 豆包、短信、支付 |
| 登录失败率突增（同 IP 5 分钟内 > 20 次） | 1 分钟内 | 撞库特征 |

## 7.2 告警抑制（否则会被淹没）

| 机制 | 做法 |
|---|---|
| 相同异常去重 | 同一个 `异常类 + 方法` 在 5 分钟内只告警一次，其余计数汇总 |
| 静默窗口 | 已知问题（如某第三方维护中）手工静默 2 小时 |
| 告警分级 | 资金/审计类走即时通知；普通 `ERROR` 走每日汇总 |

> 参考 wgcloud 的做法：它用 `WarnPools` + `ExpiringMap` 做「同一告警 2 小时内不重复发」（`WarnPools:90-119`）。**这个思路对，但状态放 Redis**（多实例共享）。

# 八、logback 配置（引用《后端代码规范》§10.5）

三条必须：
1. **三个 appender**：`console` + `file`（全量 INFO）+ **`error`（单独，只收 ERROR）**。
2. **`AsyncAppender` + `discardingThreshold=0`**（不丢 WARN/ERROR）。
3. 滚动：按天 + 单文件 100MB + 留存按 §5.2 配置。

# 九、合并前检查清单（10 问）

1. 这个管理端写接口标了 `@OperationLog` 吗？（§3.2 默认必须）
2. `action` 在 §3.2 的清单里吗？新加的动作登记了吗？
3. `detail` 存了 `before`/`after` 吗？敏感字段脱敏了吗？
4. 日志里有没有手机号 / 身份证 / 密码 / token / 聊天原文？（§4.3）
5. `log.info` 用的是占位符还是字符串拼接？
6. 异常日志打了完整堆栈吗？（`log.error("msg", e)` 而不是 `log.error(e.getMessage())`）
7. 异步任务里放了 `traceId` 吗？
8. `traceId` 在 `finally` 里清了吗？
9. 新增的查询有没有对应索引？（§6.2）
10. 这次导出操作写审计了吗？（§6.3）
