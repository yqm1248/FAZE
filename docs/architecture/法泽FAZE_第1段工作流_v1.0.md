## 一、本段目标与出口

**目标**：建立「人」和「钱」的地基。做完这一段，平台可以**真实经营**——用户能注册、能实名、律师能入驻、管理员能手工充值、余额以流水为真相、支付密码能设能锁。**但还没有正式交易流程**（下单、咨询、退款都在段 2）。

**出口（进段 2 的条件）**：

1. `1-A1` ~ `1-A10` 十条锚点**全部二值通过**（每条都有证据文件，不接受「看起来能用」）
2. 12 张表已由 Flyway 建出，且 `git status` 里**没有任何手工改库的痕迹**（迁移脚本可重放）
3. 40 个接口在《接口规范》§7.2 的清单上**一个不少**，C 端 20 个与 PC 端 20 个都有实测记录
4. 余额恒等式 `SUM(balance_flow.delta_cents) == user_balance.balance_cents` 在**差异为 0** 的状态下交付
5. `docs/analysis/ruoyi-patches.md` 已创建并登记本段对 RuoYi 框架层的**全部**改动（预期为 0 条，非 0 必须逐条说明）

**反向定义（什么不算出口）**：

- 锚点靠 mock / 固定返回通过 → 不算
- 12 张表靠手工 SQL 建、Flyway 脚本事后补 → 不算
- 对账脚本「跑通了但没对过账」→ 不算（必须跑出差异 = 0 的实际输出）
- 支付密码「能设能验」但没测过连错 5 次锁定 → 不算（`1-A5` 就是干这个的）
- 页面「能打开」但四态不全 / 断网白屏 → 不算（`1-A9`）

### D 组：账务内核（5 个任务）

#### D3 · 扣费引擎（幂等 + 乐观锁）

**目标**：一个统一的扣费入口，具备 `1-A8` 要求的幂等性：同一业务单号调 3 次只产生 1 条流水。

**前置**：D1、D2、A1（`uk_flow_biz`）。

**步骤**：

1. 接口（内部服务方法，本段不对外暴露 HTTP）：
   ```java
   DeductResult deduct(ownerType, ownerId, bizType, bizId, amountCents, remark)
   ```
2. 事务内顺序（**顺序不能变**）：
   1. 校验余额足够（`SELECT ... FOR UPDATE` 或乐观锁）
   2. 插 `balance_flow`（`uk_flow_biz` 唯一键兜底幂等）
   3. `UPDATE user_balance SET balance_cents = balance_cents - ?, version = version + 1 WHERE user_id=? AND version=?`
   4. 第 3 步影响行数 = 0 → 重试（最多 3 次）或抛乐观锁冲突
   5. 唯一键冲突（第 2 步）→ **视为重复请求，返回首次结果，不报错**
3. 金额一律 `BIGINT` 分，**禁止浮点**
4. 余额不足 → 明确错误码，**不产生流水**

**验收（二值，`1-A8`）**：

- [ ] 同 `(owner_type, owner_id, biz_type, biz_id)` 调 3 次 → `balance_flow` **只有 1 条**，余额只减一次
- [ ] 并发 10 次调用 → 仍只有 1 条
- [ ] 余额不足时流水与余额都不变
- [ ] 乐观锁冲突时有重试，不出现「扣了钱没流水」或「有流水没扣钱」

**风险**：

| 风险 | 出口 |
|---|---|
| 「先查余额再扣」的 TOCTOU | 必须 `FOR UPDATE` 或乐观锁，**不许先 `SELECT` 再 `UPDATE` 中间无锁** |
| 唯一键冲突被当成业务异常抛出 | 捕获 `DuplicateKeyException` → 返回幂等成功 |

#### D5 · 对账脚本与恒等式巡检（PC A-09 的服务端）

**目标**：一条 SQL 能跑出「缓存余额 vs 流水汇总」的差异，差异必须为 0。对应锚点 `1-A7`。

**前置**：D1~D4。

**步骤**：

1. 写 `deploy/verify-balance.ps1`（或 Java 定时任务，本段先脚本）：
   ```sql
   SELECT ub.user_id,
          ub.balance_cents AS cached,
          COALESCE(SUM(bf.delta_cents),0) AS computed
   FROM user_balance ub
   LEFT JOIN balance_flow bf
     ON bf.owner_type='user' AND bf.owner_id=ub.user_id
   GROUP BY ub.user_id, ub.balance_cents
   HAVING cached <> computed;
   ```

3. 输出：差异行数 + 明细；**差异 = 0 才算通过**

5. 脚本要能重复跑（只读，不改数据）

- [ ] 正常状态下差异 = 0
- [ ] **故意造一次差异**（手工改缓存）→ 脚本能查出来
- [ ] 输出格式固定（便于 CI 判定）

#### E2 · 校验与错误锁定

**目标**：连错 5 次锁 30 分钟，到期自动解锁。对应锚点 `1-A5`。

**前置**：E1、A2（Redis）。

3. 锁定期内校验 → 直接拒绝并返回**剩余秒数**

5. 锁定**不可手工解除**（除运维清 Redis），到期自动失效

- [ ] 等 30 分钟（或手工改 Redis TTL 模拟）→ 自动解锁
- [ ] 重置密码后计数清零

**风险**：锁定状态存 Redis，**Redis 重启会丢锁定**（可接受：重启本身是低频事件，且丢锁定只会「放宽」不会「误锁」）。

### `1-A6` 余额不由字段决定（**本段最关键的一条**）

| 项 | 内容 |
|---|---|
| **验前准备** | 一个有流水的测试用户（余额已知，如 100 元） |
| **步骤** | ① 记录当前接口返回的余额 ② 直接连 MySQL 执行 `UPDATE user_balance SET balance_cents = 99999900 WHERE user_id = <ID>;` ③ 不重启、不改任何代码，再调 `GET /app/wallet/balance` ④ 看返回值 ⑤ 恢复 `UPDATE ... SET balance_cents = 10000` |
| **二值判定** | ④ 返回的仍是 **100.00 元**（流水汇总），**不是 999999.00 元** |
| **证据** | 两次接口响应体 + 那次 `UPDATE` 的 SQL 与影响行数 + `SELECT SUM(delta_cents) FROM balance_flow WHERE owner_type='user' AND owner_id=<ID>` 的结果（应等于 10000） |
| ****可能假通过** | ① 接口返回的其实是缓存值，但**恰好等于**流水汇总（数据早就是平的）→ **必须先制造「缓存 ≠ 流水」的状态再测**；② 改完缓存后接口报错 500（不是「返回流水汇总」）→ 不算通过；③ 读了缓存但加了「对账校验」失败时降级读流水 → 这是**实现方式不同但结论正确**，可接受但要写明 |
| **失败最常见原因** | 实现者图省事直接 `SELECT balance_cents` —— 这条锚点就是专门防这个的 |

> **这条的深层目的**：它验证的是「账务模型的正确性」，不是「某个接口的返回值」。如果这条不通过，说明后面所有涉及钱的功能都建立在会漂移的缓存上，`1-A7` 的对账永远对不平。

| **二值判定** | 每页 4 态都有**可读的**视觉反馈；错误态有重试按钮且点了真能恢复 |
| **证据** | 18 × 4 张截图（存 `docs/acceptance/seg1/G5-states/`）+ 断网恢复录屏 1 段 |
| ****可能假通过** | ① 空态就是白屏（没画空态组件）② 错误态是 `alert()` 或红屏 → 不算（AGENTS §5 禁止 `alert()`）③ 重试按钮点了没反应 |
| **失败最常见原因** | 页面只做了「正常态」，四态留到最后补 → 漏页 |
