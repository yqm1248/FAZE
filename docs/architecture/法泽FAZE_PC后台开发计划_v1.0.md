# 法泽 FAZE · PC 管理后台开发计划（V1.0）

> **这份文档是什么**：PC 管理后台的**开发顺序**。回答「先做哪几页、后做哪几页、每一阶段做完能验收什么」。
>
> **不回答**：页面长什么样（看设计稿 `design/admin/`）、做什么功能（看技术路线 §十五 管理后台）、段与段之间的顺序（看《分期交付计划_v1.0》）。
>
> **与《分期交付计划_v1.0》的关系**：那一份定的是第 0~8 段的顺序与移动端页面归属；**PC 后台的页面归属一直标着「待重排」**（分期计划 §2.3 裁决四下的警告）。本文件就是那次重排的产物，落地后那处警告可以撤掉。
>
> **与《APP UI 设计顺序》的关系**：那一份是 APP 68 屏的施工记录；本文件是 PC 后台 27 页的施工记录，**两者平级、互不引用页面编号**。
>
> **定稿**：2026-10-29

## 一、范围与边界

### 1.1 覆盖什么

| 项 | 定论 |
|---|---|
| 交付物 | PC 管理后台的页面（HTML 设计稿）+ 本计划书 |
| 页面数 | **27 页**（含登录页，不含 RuoYi 框架自带页） |
| 角色 | **只做 1 个角色：管理员**。不做超管 / 运营 / 审核 / 财务的权限细分，所有菜单对管理员可见 |
| 技术底座 | RuoYi-Vue3 3.8.7（`E:\itheima\vue\ry_vue3\RuoYi-Vue3`），业务页在 `src/views/biz/<domain>/`，API 在 `src/api/biz/<domain>/` |
| 部署 | 独立域 `admin.faze.com`，仅 admin 角色可登录（技术路线 §15.2） |
| 画幅 | 1440×900 固定 |
| 语言 | 简体中文（与 APP 设计稿同口径：多语言与 RTL 放代码层） |

### 1.2 明确不做什么

1. **不做 RuoYi 框架自带页的设计**：用户管理、角色管理、菜单管理、部门管理、字典管理、操作日志、登录日志、代码生成器 —— 全部沿用若依原样，只改主题色。这 8 个页面的开发工作量**不计入本计划**（它们随框架就有）。
2. **不做权限细分与多角色**。菜单权限仍走 RuoYi 的 `sys_menu`，但只有「管理员」一套可见范围。
3. **不改 RuoYi 框架层**（侧边栏 200px、顶栏 50px、标签页 34px、`.app-container` padding 20px 都是框架层写死的；确需 patch 记到 `docs/analysis/ruoyi-patches.md`）。
4. **不做 PC 端的移动适配**。后台是桌面工具，1440 起，不做响应式。
5. **不含小程序、不含律师工作台**（工作台在 APP 端）。

### 3.1 阶段依赖关系

```text
P1 底座 ──► P2 人投资质 ──► P3 账务 ──► P4 交易
   │                              │
   └──────────────────────────────┴──► P5 内容 ──► P6 案件与审核 ──► P7 治理
```

**硬依赖**：
- P1 → 全部（没有登录与列表范式，后面每页都要重造轮子）
- P2 → P3（没有实名与律师审核通过，账务无处挂业务单号）
- P3 → P4（没有余额，订单扣不了款）

**可调整**：
- P5 内容与 P4 交易无硬依赖，**可对调**（如果运营侧急着录文章，先做 P5）
- P7 治理可与 P6 并行

## 四、接口缺口（这是本计划最大的施工风险）

技术路线 §4.8.2 的 `/api/v1/admin/**` **只有 2 组、共 3 个接口**：

| 已定义 | 用途 |
|---|---|
| `GET /admin/lawyer-applications` | 律师入驻审核列表 |
| `POST /admin/lawyer-applications/{id}/audit` | 律师入驻审核动作 |
| `GET /admin/orders` | 订单列表 |
| `POST /admin/refunds/{id}/audit` | 退款审批 |

**27 页里 25 页没有对应的 admin 接口定义**（除 A-01 走 RuoYi 自带登录、A-05 与 A-11/A-12 部分命中）。全部细节见《未完成需备注》。

**这意味着**：本计划能做的是「设计 + 前端页面」，**后端接口必须在 P2 开工前补齐**，否则页面只能接假数据。这是提交给后端/项目负责人的硬前置，不是本计划能解决的。

## 五、与《分期交付计划》的对应关系

| PC 阶段 | 对应分期交付计划 | 说明 |
|---|---|---|
| P1 底座 | 第 0 段 | 「后台能登录、能看到 biz 菜单」 |
| P2 人与资质 | 第 1 段 | 「后台审律师」是该段验收原文 |
| P3 账务 | 第 1 段 + 第 6 段 | 手工充值属第 1 段；提现审核属第 6 段 |
| P4 交易 | 第 2 段 + 第 5 段 | 订单属第 2 段；律师结算属第 5 段 |
| P5 内容 | 第 2 段 + 第 4 段 | 文章属第 2 段；文书模板属第 4 段 |
| P6 案件与审核 | 第 5 段 + 第 7 段 | 案件属第 5 段；内容审核属第 7 段 |
| P7 治理 | 第 7 段 | 治理全量 |

**注意一处顺序冲突**：分期交付计划要求 9 段**严格串行**（做完第 1 段才做第 2 段）。而 PC 的 P3 同时服务第 1 段和第 6 段、P4 同时服务第 2 段和第 5 段 —— 这**不违反**串行要求，因为 PC 页面不阻塞对应段的核心验收，只是「那一段需要后台看一眼时，这一页得在」。若某段先做完了而 PC 对应页还没做，先用「最小可用页」顶着（能查该段核心记录 + 能执行验收动作），不追求完整。

**设计稿的画法约定**（与 APP 一致，但尺寸不同）：

1. 一屏一个 HTML，文件名用本文档「设计稿」列的名字。
2. 画幅 1440×900，`<meta name="dsh-design" content="web">`。
3. 靠 RuoYi 骨架：侧边栏 200px + 顶栏 50px + 标签页 34px + 内容区 padding 20px。
4. 视觉数值只从 `design/admin/tokens.css` 取，不写裸值。

## 七、明确不做

1. **不做 RuoYi 自带系统管理页的设计与开发**（8 个页面沿用框架）。
2. **不做多角色权限**（只管理员）。
3. **不做 PC 端的深色模式**（RuoYi 支持 theme-dark 菜单，但页面主体只做浅色）。
4. **不做移动端适配**。
5. **不做「工作台」「数据大屏」「BI 报表」** —— 技术路线 §15.1 没列，本计划不自行扩范围。
6. **不代项目负责人定业务规则**（抽成比例、提现门槛、审核时效等一律标占位，不写死）。
