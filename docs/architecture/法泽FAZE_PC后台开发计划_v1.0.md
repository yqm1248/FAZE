# 法泽 FAZE · PC 管理后台开发计划（V1.0）

> **这份文档是什么**：PC 管理后台的**开发顺序**。回答「先做哪几页、后做哪几页、每一阶段做完能验收什么」。
>
> **不回答**：页面长什么样（看设计稿 `design/admin/`）、做什么功能（看技术路线 §十五 管理后台）、段与段之间的顺序（看《开发计划总纲》）。
>
> **与《开发计划总纲》的关系**：总纲定第 0~8 段的顺序、每段边界与**页面归属**；本文件定**28 页分别是什么、职责、数据表，以及 P1~P7 的开发批次建议**。
>
> **关键口径（2026-10-30 修订）**：**P1~P7 不是交付单位，段才是**。PC 页跟着它服务的那一段交付，具体归属以总纲 §4.2 为唯一权威。本文件 §五 只保留「批次 ↔ 段」的对照，不再声明谁先谁后。
>
> **与《APP UI 设计顺序》的关系**：那一份是 APP 68 屏的施工记录；本文件是 PC 后台 28 页的施工记录，**两者平级、互不引用页面编号**。
>
> **定稿**：2026-10-29

## 一、范围与边界

### 1.1 覆盖什么

| 项 | 定论 |
|---|---|
| 交付物 | PC 管理后台的页面（HTML 设计稿）+ 本计划书 |
| 页面数 | **28 页**（含登录页，不含 RuoYi 框架自带页） |
| 角色 | **只做 1 个角色：管理员**。不做超管 / 运营 / 审核 / 财务的权限细分，所有菜单对管理员可见 |
| 技术底座 | **RuoYi-Vue 3.9.2 官方发行版**（`E:\itheima\SSM\3、SSM框架（…）\文件\RuoYi-Vue`，分支 `release-3.9.2` = tag `v3.9.2`，**Spring Boot 4.0.3**）；前端 RuoYi-Vue3 3.9.2。业务页在 `src/views/biz/<domain>/`，API 在 `src/api/biz/<domain>/` |
| 部署 | 独立域 `admin.faze.com`，仅 admin 角色可登录（技术路线 §15.2） |
| 画幅 | 1440×900 固定 |
| 语言 | 简体中文（与 APP 设计稿同口径：多语言与 RTL 放代码层） |

### 1.2 明确不做什么

1. **不做 RuoYi 框架自带页的设计**：用户管理、角色管理、菜单管理、部门管理、字典管理、操作日志、登录日志、代码生成器 —— 全部沿用若依原样，只改主题色。这 8 个页面的开发工作量**不计入本计划**（它们随框架就有）。
2. **不做权限细分与多角色**。菜单权限仍走 RuoYi 的 `sys_menu`，但只有「管理员」一套可见范围。
3. **不改 RuoYi 框架层**（侧边栏 200px、顶栏 50px、标签页 34px、`.app-container` padding 20px 都是框架层写死的；确需 patch 记到 `docs/analysis/ruoyi-patches.md`）。
4. **不做 PC 端的移动适配**。后台是桌面工具，1440 起，不做响应式。
5. **不含小程序、不含律师工作台**（工作台在 APP 端）。

> **划分依据**：① 依赖顺序（没有登录与框架，后面都跑不起来）；② 《开发计划总纲》各段的验收动作；③ 风险前置（先把最容易错的审核流、资金流做出来）。
>
> **这是「批次建议」，不是交付顺序**：同一批次里跨段的页面（例如 P1 的 A-01 属段 0、A-03 属段 1、A-02 属段 7）**要拆开按段交付**，不能为了「凑一批」提前做后面段的页。实际施工时以总纲 §4.2 为准。

> **每阶段都自带验收**：阶段做完必须能自己一个人验，不依赖下一阶段。


## 四、接口契约（原「接口缺口」，2026-10-30 已补）

**历史**：技术路线 §4.8.2 的 `/api/v1/admin/**` 原本只有 2 组 4 个接口（律师入驻审核 2 个、订单列表 1 个、退款审批 1 个），28 页里 25 页没有契约，页面只能接假数据。

**现在**：技术路线新增 **§4.8.4 管理端接口补全**，按页面列全 **87 个**接口（新补 83 个 + 原有 4 个），覆盖 28 页里的 **26 页**（A-01 走 RuoYi 自带登录；A-05 沿用原有 2 个）。

**变了什么、没变什么**：

| 项 | 状态 |
|---|---|
| 前端页面能不能开工 | **能**——每页的列表 / 详情 / 动作都有路径与用途约定 |
| 后端是否已实现 | **没有**。契约只是文档；faze-api 要按 §4.8.4 实现。**P2 开工前至少要跑通 5 组**：登录、用户列表、实名审核、律师入驻审核、手工充值 |
| 字段级定义 | 以运行时 Swagger 为准，本文档不重复定义字段 |
| 看板指标口径 | **仍未定**（DAU / 留存 / 收入怎么算）。A-02 的接口形状有了，口径要继续拍板 |

**仍然是风险的地方**：接口有了不等于能验收。P2 之前后端若不实现，页面还是只能接假数据；区别是现在「缺什么」是清单化的，不再靠猜。

## 五、与《开发计划总纲》的对应关系

> **这一节不再定义「谁先谁后」。** 交付单位是**段**，PC 页跟着它服务的那一段交付。下表只说明「某个 P 批次里的页面分别落到哪些段」，方便按段施工时把一批拆开。**唯一权威归属表在总纲 §4.2。**

| PC 阶段 | 页面 | 落在哪些段 | 拆开时的注意点 |
|---|---|---|---|
| P1 底座 | A-01 / A-02 / A-03 | 段 0 / 段 7 / 段 1 | A-01 必须先做（没有后台登录，后面所有验收都做不了）；A-02 看板要等有真实数据，放段 7；A-03 用户列表等段 1 有 C 端用户再查 |
| P2 人与资质 | A-04 / A-05 / A-06 | 段 1 | 三页同段，可以成批做；A-05 的接口是原有的 2 个，最先能跑通 |
| P3 账务 | A-07 / A-08 / A-09 / A-10 | 段 1（前三页）/ 段 5（A-10） | A-07 手工充值是段 1 的硬依赖；A-10 提现审核不能提前做——段 5 之前没有提现申请单 |
| P4 交易 | A-11 / A-12 / A-13 | 段 2（前两页）/ 段 5（A-13） | A-12 的退款审批跟着段 2 的退款申请页一起做；A-13 结算口径依赖段 5 的收入汇总 |
| P5 内容 | A-14 / A-15 / A-16 / A-17 / A-18 / A-27 | 段 2 / 段 5 / 段 8 / 段 4 / 段 3 | **这一批跨 5 个段，必须拆**：A-14/A-15 段 2、A-16 段 5、A-18 段 4、A-27 段 3、A-17 段 8 |
| P6 案件与审核 | A-19 / A-20 | 段 5 / 段 7 | A-19 跟着在线立案走；A-20 内容审核队列要等段 7 的敏感词与审核策略 |
| P7 治理 | A-02 / A-21 / A-22 / A-23 / A-24 / A-25 / A-26 / A-28 | 段 7（除 A-28）/ 段 3（A-28） | A-28 AI 对话检索必须跟段 3 同期上线——它是段 3「后台可追溯」这条验收的落地页，晚到段 7 就等于段 3 验收不了 |

**两条容易搞错的约束**（写在这里防止复发）：

1. **段内可以「一批一起做」，但不能「提前做后面段的页」。** 例：P5 的 6 页里 A-27 属段 3、A-18 属段 4，做段 3 时只做 A-27，不许顺手把 A-18 也做了——段 4 的模板字段定义那时还没定。
2. **PC 页不阻塞对应段的核心验收吗？以前是，现在不是。** 旧口径允许「先用最小可用页顶着」，因为当时 PC 页没排进段内。现在**每段的必要条件里就包含它的 PC 页**（例如段 1 的 `1-A4` 手工充值必须在 A-07 上操作），所以 PC 页是该段交付物的一部分，不再是「有空再做」。

## 六、UI 设计稿与本文档的关系

| 交付物 | 位置 | 说明 |
|---|---|---|
| UI 设计稿（28 屏 HTML） | `design/admin/` | 与本文件**同步产出**，不是先设计后开发的两段式 |
| 设计系统 | `design/admin/tokens.css`、`components.css` | 颜色继承 APP 令牌，尺寸另立 PC 刻度 |
| 本文档 | `docs/architecture/法泽FAZE_PC后台开发计划_v1.0.md` | — |

**设计稿的画法约定**（与 APP 一致，但尺寸不同）：

1. 一屏一个 HTML，文件名用本文档「设计稿」列的名字。
2. 画幅 1440×900，head 里写 `<meta name="dsh-design" content="web 1440x900">`。**尺寸必须写进去**：设计工作台的 web 类型默认按 1280×800 建画布，只写 `content="web"` 时骨架的 `overflow:hidden` 会把右侧 160px、下方 100px 直接裁掉，且不出现滚动条。2026-10-30 实际踩过一次，当时 26 屏的 meta 全部重写。
3. 靠 RuoYi 骨架：侧边栏 200px + 顶栏 50px + 标签页 34px + 内容区 padding 20px。
4. 视觉数值只从 `design/admin/tokens.css` 取，不写裸值。
5. 每屏顶部必须有块注释：这屏的职责 + 依据（本文档哪一条 / 技术路线哪一节）+ 依赖的接口。
6. **四态**：设计稿只出了「正常」态，空态与加载态没画 —— 这是取舍不是遗漏，理由与补法见《未完成需备注》§七第 1 条。开发时列表页的空态、加载态直接接 `components.css` 的 `.empty` 与 `.skeleton`，不另出设计稿。

## 七、明确不做

1. **不做 RuoYi 自带系统管理页的设计与开发**（8 个页面沿用框架）。
2. **不做多角色权限**（只管理员）。
3. **不做 PC 端的深色模式**（RuoYi 支持 theme-dark 菜单，但页面主体只做浅色）。
4. **不做移动端适配**。
5. **不做「工作台」「数据大屏」「BI 报表」** —— 技术路线 §15.1 没列，本计划不自行扩范围。
6. **不代项目负责人定业务规则**（抽成比例、提现门槛、审核时效等一律标占位，不写死）。
