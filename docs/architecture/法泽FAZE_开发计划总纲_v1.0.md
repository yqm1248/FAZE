## 1.3 为什么推倒重写（旧两份的问题）

旧《分期交付计划》（内容 v1.2）和《第 0 段执行计划 v3.0》是 2026-10-28 ~ 29 写的，当时 PC 后台还没启动、页面归属还没定。到 10-30 已经出现**五类实质冲突**，不是措辞问题：

| # | 冲突 | 具体表现 | 后果 |
|---|---|---|---|
| 1 | **第 0 段的规模失控** | v3.0 有 24 个任务、6 组、13 条验收，其中大量任务（鉴权态、RTL 坐标系、四态、lint 规则）是「地基」，但没有一个能在段末被独立判定为「成了」 | 负责人已经判定：不要了，重新设计 |
| 2 | **支付被切错位置** | 旧版把「支付页 / 支付结果页 / 退款页」放在第 6 段（真实渠道段），而第 2 段的验收原文是「下单 → **输支付密码扣款** → 接单」。余额扣款不需要真实渠道 | 照旧版施工，第 2 段的验收无法执行——要验的页面在四段之后 |
| 3 | **PC 页面归属两份文档各说一套** | 旧版说「PC 归属移交 PC 计划」，PC 计划 §五 给的是 P1~P7 ↔ 段的粗对应；P1 一次含 A-01（段 0）、A-02（段 7）、A-03（段 1） | 施工时不知道某一段到底要不要做 PC 页，做几页 |
| 4 | **验收项数量自相矛盾** | 旧版第 0 段：正文列 13 条，别处写 15 条；ADR 写「14 条」又引 21 条 | 勾选时无法确定「勾完没有」 |
| 5 | **MQ 决策已落地，旧版还开着三选一** | 旧版 §3.5 列了 A/B/C 三个选项等拍板；负责人已选 **B：不用 MQ，改「数据库任务表 + 定时重试」** | 旧版这一节整节失效 |

另外一处不是冲突但会误导：旧版把**页数口径**写成 68 页，而 PC 后台 28 页是另算的——读的人容易把两边加一起当「96 页要开发」。

## 1.4 与 PC 计划的关系（这轮必须理清）

《PC 后台开发计划》里的 **P1 ~ P7 是「开发批次建议」，不是交付单位**。交付单位是**段**。原因：

- P1 一次打包 A-01 / A-02 / A-03 三页，但按验收依赖，A-01 属第 0 段、A-03 属第 1 段、A-02 属第 7 段。若按 P1 施工，第 0 段就要做数据看板——那时库里一条业务数据都没有，看板只能是假数。
- P3 同时服务第 1 段（手工充值）和第 6 段（提现审核），但新版把提现审核移到第 5 段（律师收入与提现在第 5 段产生）。按 P3 施工，第 1 段要等商户号。

**结论**：PC 页**跟着它服务的那一段交付**。P1~P7 只作为「同一批页面放在一起做省力」的建议，实际排期服从段序。§4.2 是唯一权威的 PC 页面归属表。

# 二、什么算「一段」：成立标准

## 2.1 四条硬条件（沿用，不再改）

一段成立，必须同时满足：

1. **单方可验收**：项目负责人一个人，一台真机 + 一个后台账号 + 一条命令，就能客观判定「成了 / 没成」，不需要等下一段配合。
2. **自带端到端**：一段 = 前端页面 + 后端接口 + 数据库迁移 + 该段需要的 PC 页，四样同时交付。不允许「服务端写完了前端看不见」。
3. **段末可对真实用户开放**：这一段做完，对应功能就能真开给用户用，而不是「等全部做完一起开」。
4. **外部依赖有替代出口**：段内任何外部依赖（商户号、推送通道、第三方 API）缺失时，必须有不依赖它的验收路径，否则这段被永久阻塞。

## 2.2 三条附加条件（本轮新增）

5. **段内可回滚**：每段结束时数据库迁移与代码能独立回退到段首状态，且回退步骤写在段工作流里。理由：9 段串行，若第 5 段发现第 2 段的表设计错了，没有回滚手段就只能硬改已执行的迁移。
6. **段末文档闭合**：本段新增/变更的表、接口、页面、错误码，必须已经写进技术路线或该段工作流；口头约定的东西不算交付。
7. **段末不留假数据**：全段搜索 mock / 写死的示例数据，逐条登记「替换时机」；能在本段替换的不许留到下一段。

## 2.3 什么样的「段」不成立（反例，写下来防复发）

| 反例 | 为什么不行 |
|---|---|
| 「IM 服务端」单独成段 | 产出是一堆接口，但没有页面能打开、没有钱、没有律师，负责人无法判定成了没有（旧 S0~S16 分期就是这么死的） |
| 「设置与其他 18 页」 | 18 个互不相关的页面捆成一段，没有一页能独立验收，也没有一页能独立产生价值 |
| 「多语言」单独成段 | RTL 是布局坐标系，晚一步就是 68 页逐页返工；它必须从第 0 段就进代码，不能当填充物后补（旧版已按此拆成两条线，见 §7.1） |
| 「数据看板 + 登录 + 用户列表」一段 | 看板依赖前面积累的真实数据，第 0 段做完时它只能是假数，验收无法成立 |


**硬依赖**（前一段不收口，后一段不能开工）：

- **段 6 可滑动**：默认排在段 5 之后、段 7 之前，但允许滑到**段 2 之后的任意位置**（含最后）。它只依赖段 1 的账务内核与段 2 的余额扣款链路。商户号没下来时，段 7 / 段 8 可以先做。
- **段 3 与段 4 之间**：段 4 对段 3 的依赖只到「条文号存在性校验服务」这一小块，若段 3 因法条数据未到位被卡，段 4 可以先用「校验服务打桩 + 只验排版」推进，但**不得跳过段 3 直接段 5**。

## 3.3 「严格串行」到底约束什么

AGENTS.md 写的是「9 个段严格串行，不许两段并行」。这句要精确理解，否则会出现两种相反的错误：一是把它当摆设、边做段 2 边做段 4；二是把它当逐任务闸门、每写一个类就停下来等确认（旧 v3.0 的 24 任务 24 门禁就是这么来的，已被判定作废）。

**约束的是「同一时刻只有一个段处于施工中」**：

| 允许 | 不允许 |
|---|---|
| 段 n 施工期间，把段 n 需要的 PC 页一起做（PC 页按 §4.2 归属） | 段 n 未收口就开始段 n+1 的业务代码 |
| 段 n 施工期间，并行推进文档、环境准备、外部资质办理 | 为了「顺手」提前实现后面段的功能（探针类除外，见段 0） |
| 段内按「组」连续推进，组间设检查点，组内不设闸门 | 把段内任务拆成逐任务闸门、每个任务都停下来汇报 |
| 段 6 在允许窗口内滑动 | 段 1/2/3/4/5/7/8 之间调整顺序 |

## 4.4 归属规则（以后再要挪页，按这三条判）

1. **验收依赖优先于模块归属**。页面属于「它的验收动作所在的那一段」，不属于「它所在的业务模块」。律师入驻页在模块 2（律师服务），但验收动作在段 1，所以归段 1。
2. **数据产生方优先于数据消费方**。案例库归段 5，因为案例数据在段 5 产生；不归段 4，即便段 4 的文书也会引用案例。
3. **空壳页面不提前做**。依赖未就绪的页面（无数据、无渠道、无上游链路）提前做，产出的是假界面，反而制造「已经做完了」的错觉。

## 5.4 段 3：AI 法律顾问

**定位**：把段 0 验证过的探针变成可用功能，并把合规要求（显式 / 隐式标识、留存、防护）同期落地。**这一段是合规风险最高的一段**：AI 输出必须只引用库里存在的条文。

**交付物**

| 项 | 内容 |

| 服务端 | `law_item` 全量入库（2000 ~ 3000 条，Flyway 基础数据）；MySQL ngram 全文索引检索（**不用向量库**）；豆包 API + SSE 流式；三层输出防护（输入侧意图识别 → Prompt → 输出侧条文号存在性校验）；显式标识 + 隐式标识；对话留存 `ai_message`（含 `refs` 法条引用快照） |

**必须做**

- 不做多语言 AI 回答（段 8 评估，取决于模型对 bo / ug / kk 的支持）。

- 不做生成式 AI 备案（负责人已定「上线后重新评估」；技术侧只保证有开关可降级）。

## 7.2 账务恒等式（从段 1 起，每段都要守）

- `balance_flow` 是**唯一真相**；`account.balance` 是缓存，可被重算覆盖。
- 任何改变余额的动作（充值、消费、退款、调账、提现冻结 / 解冻、分佣）**必须**写 `balance_flow`，且带业务单号与幂等键。
- 每段收口时跑一次恒等式巡检：`余额 == SUM(balance_flow.amount)`，差异必须为 0。
- 金额一律整数分（`BIGINT`），禁止浮点。

## 7.3 合规红线（贯穿全部段）
