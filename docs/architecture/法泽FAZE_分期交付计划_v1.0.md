# 一、这份文件为什么存在

## 1.1 旧分期（技术路线 §23.1 的 S0–S16）的硬伤

旧分期是 S0 基础设施 → S1 设计系统+i18n → S2 认证流 →……→ S16 上架，共 17 段。它按**技术层与页面模块横向切分**，有三个致命问题：

| 硬伤 | 具体表现 |
|---|---|
| **每段单独不可验收** | 「S5 IM 通信」的产出是「1 页 + 服务端」。服务端写完了，但没有钱、没有律师、没有订单，这一页打不开也走不通。项目负责人无法判断这段「成了还是没成」 |
| **前 15 段做完之前没有任何一刻能真正上线** | 唯一能让真实用户用起来的时点被推到 S15 之后。这意味着长达整个开发周期里，所有决策（表结构、支付方案、AI 形态、字体）都在**没有真实反馈**的情况下做出 |
| **聚合页被当作交付单位** | 「S11 设置与其他 18 页」是把 21 个互不相关的页面捆成一段。里面没有一页能独立验收，也没有一页能独立产生价值 |

## 1.2 本分期的判定标准

**一段成立的四个条件**（缺一条就不成立）：

1. **单方可验收**：项目负责人自己一个人，用一台真机 + 一个后台账号 + 一条命令，就能客观判定「成了 / 没成」，不需要等下一段配合。
2. **自带端到端**：一段 = 前端页面 + 后端接口 + 数据库迁移 + 该段需要的后台页面，四样同时交付。不允许「服务端写完了前端看不见」。
3. **段末可对真实用户开放**：这一段做完，对应的功能就能真开给用户用，而不是「等全部做完一起开」。
4. **外部依赖有替代出口**：段内任何外部依赖（商户号、推送通道、第三方 API）缺失时，必须有不依赖它的验收路径，否则这段被永久阻塞。

## 1.3 适用范围与边界

- 本计划只覆盖 **Android + 服务端 + PC 后台**。
  - **⚠️ v1.1：PC 后台当前暂缓**（项目负责人 2026-10-29：「暂时先不开启 PC 端」）。本计划中所有涉及 PC 后台的内容**保留但挂起**，不随段推进自动触发；后台页面归属见 §2.3 裁决四下的说明，待 PC 设计重做后统一重排。
- **iOS 不作为这九段的一部分**。Android 跑顺之后单独排一期，复用第 0–8 段的全部后端与后台，只重做客户端构建与上架。
- 本计划**不排日历时间**。项目负责人已明确「时间不是约束，质量优先」，因此只排**依赖顺序**，不排周数、不排人天。任何「第 X 周完成」的表述都不在本文件范围内。
- 本计划**不重新定义功能**。页面四态、字段、接口、状态机、错误码全部以技术路线 v2.3 为准。

## 2.3 六处关键裁决

这六处是专家团意见分歧最大的地方，记录裁决与理由，避免后续反复。

### 裁决一：第 0 段必须存在，且不是「基础设施段」

**依据**：三位专家独立提出同一点——APK 构建路径不通，则后面每一段「装上手机点一遍」的验收方式**全部作废**，整个分期体系失去判定手段。

**裁决**：第 0 段排第一，且必须包含三项探针（APK、藏文字体、豆包往返）。它交付的不是「空壳」，而是「验收能力」。

**反对意见及不采纳理由**：有专家建议把第 0 段压成纯 spike、不进正式序列。不采纳——它同时交付 Tab 骨架、RTL 坐标系、LocalizedText、网络层、鉴权态，这些是后续 67 页的地基，压缩掉等于把这些推到第 1 段，第 1 段就会变成一个畸形的大段。

### 裁决二：支付拆成两段（第 1 段账务内核 + 第 6 段真实渠道）

**依据**：支付专家的核心洞察——**商户号只挡「真充值」这一环，不挡账务内核**。余额账本、流水、扣费引擎、对账恒等式全部可以在没有商户号的情况下建成并验证。

**裁决**：第 1 段建账务内核（balance_flow 为唯一真相、扣费引擎、人工充值、对账脚本）；第 6 段只替换渠道适配器、加提现与掉单补单。

**因此第 6 段是「可滑动段」**：商户号什么时候下来，就什么时候把它插进来，第 1–5 段完全不阻塞。

**风险**：如果商户号永远不下来，第 6 段永远做不了。但这不阻塞业务——第 1 段的人工充值 + 线下转账可以让平台真实经营，第 6 段是体验升级而非功能前提。

### 裁决三：AI 放第 3 段，但探针必须进第 0 段

**依据**：AI 段需要三样前置——账号归属（否则没有配额与留存主体）、余额体系（否则无法计费）、内容安全前置条件。所以不能早于第 1 段。但它也不宜晚于第 4 段，因为文书中心要复用条文号存在性校验服务。

**裁决**：AI **技术风险**在第 0 段用最小探针消除（一个后台按钮 → 服务端调豆包 → 流式返回 → 从 law_item 命中一条条文）；AI **业务功能**放第 3 段。

这样既不让最高技术风险压到最后，也不让 AI 在没有账号体系时裸奔。

### 裁决四：管理后台不独立成段

**依据**：六位专家一致反对「后台留到最后」。若后台整段后置，则每一段的验收都缺一环，且后台开发期间前面的业务假设全部无法验证。

**裁决**：哪一段的验收需要「打开后台看一眼」，那个后台页面就跟那段一起交付。具体分布：第 1 段（用户/实名/律师审核/手工充值/流水）、第 2 段（文章录入/订单查询）、第 5 段（案件/律师结算）、第 7 段（治理全量）。

> **⚠️ v1.1 追加：PC 后台的页面归属待重排。** 项目负责人 2026-10-29 明确「暂时先不开启 PC 端」，PC 设计尚未重做，上表这四段各自的后台页面清单是**按旧设计推导的，不是定稿**。
>
> 处理方式：**PC 设计重定之后一次性重排这一段分布，现在不改**（改了也是白改）。已开工的段若需要后台配合，先按最小可用页面做（能登录 + 能查该段的核心记录 + 能执行该段的验收动作），不追求后台完整性。
>
> 追这条原因：把「后台页面分布」和「移动端页面数」混在一张表里看，会误以为 PC 页数已经排好了。**实际那 68 页全部是移动端页面，PC 页数从来没进过任何统计。**

### 裁决五：律师工作台从倒数第二挪到第 5 段

**依据**：双角色 App 的验收必须两端同时在场。旧分期把工作台放 S10，等于让律师在整个咨询域期间「不能工作」——那样第 2 段的咨询闭环根本走不通。

**裁决**：第 2 段就交付律师端**接单 + 会话**（否则咨询闭环不成立）；第 5 段交付工作台全量 7 页（含收入提现、订单管理、文书管理、服务设置、律师资料）。

### 裁决六：多语言拆成两条时间尺度完全不同的线

**依据**：多语言专家的核心判断——RTL 不是「校对」，它是**布局的坐标系**（`marginStart/End`、图标镜像、手势方向、`textAlign` 都要跟着变）。晚一步就是 68 页逐页返工。但四语言**译文与术语校对**是填充物，可以最后补。

**裁决**：

| 线 | 内容 | 落在 |
|---|---|---|
| **线 A：机制** | RTL 坐标系、`forceRTL` + 软重启、`LocalizedText`（Unicode range 切 run）、禁用物理方向属性的 lint 规则、语言切换页 | **第 0 段** |
| **线 B：填充** | 藏/维/哈译文、法律术语表冻结、母语者校对 | **第 8 段** |

中间各段只需保证「新页面在 ug-Arab-CN 下不出布局错」，不要求译文齐全（`key` 直接上屏也算通过）。

## 2.4 依赖关系

```
第0段 ──┬→ 第1段 ──→ 第2段 ──→ 第3段 ──→ 第4段 ──→ 第5段
        │        │                            │
        │        └────────────────────────────┴→ 第6段（需商户号，可滑动）
        │
        └→（第7段依赖段1/2/5 的业务数据；第8段依赖全部）
```

**硬依赖**（前一段不做完，后一段无法开始）：
- 第 0 段 → 全部。无第 0 段则没有任何可安装包，一切验收失效。
- 第 1 段 → 第 2 段。没有账号与余额，无法下单扣款。
- 第 2 段 → 第 3 段。AI 需要账号归属与余额。
- 第 1 段 → 第 6 段。没有账务内核，渠道无处落地。

**软依赖**（可并行或调整顺序）：
- 第 4 段（文书）与第 5 段（案件）之间无硬依赖，可调换。
- 第 7 段（治理）可与第 5、6 段并行。
- 第 8 段必须最后，因为要覆盖全部页面。

## 3.5 ⚠️ 待决：RabbitMQ 什么时候起、怎么起（v1.1 新增）

**这一条不是文档表述问题，是技术决策空着一个洞。** 记录下来，避免再被当成"两份文档打架"放过去。

### 事实

| 出处 | 原文 |
|---|---|
| 技术路线 v2.3 L205 | 消息队列：**RabbitMQ 3.13（管理界面）**，在技术栈表里 |
| 技术路线 v2.3 L644 | RabbitMQ 承担：**异步发短信、推送、生成文书、内容审核**，主流程不阻塞，失败重试 + 死信队列 |
| 技术路线 v2.3 §18.2 | Docker Compose 里有 `image: rabbitmq:3.13-management`（**这是生产部署章节**，不是本地开发） |
| 第 0 段执行计划 v3.0 L57 / L740 | 容器：**没有 docker，也不用**。禁用清单第一条：**任何形式的 docker**（项目负责人明确不要） |

所以：**生产部署用 docker 没问题，本地开发不用 docker 也没问题 —— 真正的问题是「本地怎么跑 RabbitMQ」，一份文档都没写。**

### 为什么现在必须记下来

RabbitMQ 承载的四件事分别落在具体段里：**第 1 段（短信验证码）、第 2 段（离线推送）、第 4 段（文书生成）、第 7 段（内容审核）**。第 0 段用不到它，所以执行计划里没有它是**正确的**。但**到第 2 段之前，必须给出方案**，否则第 2 段的推送方案要么临时改架构，要么卡在那里。

### 三个选项（**需要项目负责人拍板，本文件不代决定**）

| 选项 | 做法 | 代价 | 风险 |
|---|---|---|---|
| **A. 本机装 Windows 版 RabbitMQ** | 装 Erlang + RabbitMQ 服务，`start-services.ps1` 里加第三项拉起 | 环境多两个安装步骤；和「不用 docker」不冲突 | 版本与 Spring Boot 3.5 的兼容性没人实测过；Erlang 版本强绑定 |
| **B. 不用 MQ，改「同步 + 重试表 + 定时补发」** | 短信/推送/文书生成/审核都改成数据库任务表 + 定时轮询，失败重试落表 | 少一个中间件；行为可查（表里能看） | **要改技术路线**：L644 整段失效；第 2 段推送和第 4 段文书生成的实现方式要重写；并发量大时轮询有延迟 |
| **C. 第 2 段之前再决定** | 现在不选，第 1 段先不用 MQ（短信验证码开发期本来就用固定码或后台打印） | 零成本 | **第 1 段结束时必须定**，否则第 2 段开工就卡 |

**建议**：选 **C**，但把「第 1 段检查点必须回答这个问题」写进第 1 段的验收。理由：现在选 A 会引入一个没验证过兼容性的中间件，选 B 会让技术路线 L644 立刻失效；而第 1 段确实不需要 MQ，有时间验证。

**不管选哪个，技术路线 §18.2 的 docker 部分要注明「生产部署」**，否则下一个人还会拿它去对第 0 段的本地环境。

| LibreOffice 在 Windows headless 下字体回退不可控 | 用 `--headless --convert-to pdf` 并显式指定字体目录；若中文/少数民族文字混排仍错，备选 Chromium 打印 |
| PDF 体积过大 | 图片压缩 + 字体子集化 |

# 八、第 5 段：案件中心 + 律师工作台

## 8.1 目标

双角色彻底闭合。律师侧从「只能接单」变成「能管理全部工作」。

## 8.2 范围

**移动端（14 页）**
- 模块 4 全部 5 页：案例列表、案例详情、在线立案、立案成功、案件送达
- 模块 11 全部 7 页：工作台首页、客户咨询、订单管理、文书管理、收入提现、服务设置、律师资料
- 模块 10 的 2 页：我的案件、案件进度

**服务端**
- `caseflow` 域：立案申请、案件状态机、进度时间轴、送达记录
- `content` 域的案例库：`case_library` + `case_library_translation`
- 律师端聚合：订单管理、文书管理、收入统计、服务设置
- 律师结算：从 `balance_flow` 推导律师收入
- AI 转律师派单（技术路线 §22.3）

**数据库**
- `legal_case`、`case_progress`、`case_service_record`
- `case_library`、`case_library_translation`
- `lawyer_service_config`、`lawyer_income_settlement`

**后台**
- 案件管理、立案审核、律师结算

## 8.3 验收标准

- [ ] 在线立案提交 → 生成案件记录 → 立案成功页显示案件号
- [ ] 律师端推进度 → **用户端时间轴同步新增节点**，时间正确
- [ ] 案件送达：用户收到送达记录并可查看
- [ ] **律师收入页金额 == 该律师 `balance_flow`（收入类）汇总** —— 对账一致
- [ ] 律师订单管理能看到全部订单，可筛选、可操作
- [ ] 律师可编辑服务设置（价格、时段、可接单状态），改价后用户端立即反映
- [ ] AI 对话中用户表达要律师 → 可跳转到律师列表并带上上下文
- [ ] 案例库：后台录入案例（4 语言）→ App 案例列表可见 → 详情法条引用正常
- [ ] 我的案件、案件进度页数据与律师端一致

## 8.4 明确不做

- 不做真实提现出款（第 6 段做人工出款流程）
- 不做法院系统对接（无公开接口，见技术路线 §18 说明）

# 九、第 6 段：真实充值渠道 + 提现 + 掉单补单

> **本段是可滑动段。** 商户号什么时候下来就什么时候做，第 1–5 段完全不依赖它。

## 9.1 目标

把第 1 段的账务内核接上真实资金通道。**不改内核，只换适配器。**

## 9.2 范围

**移动端（4 页）**
- 模块 7：支付、支付结果、退款、**充值（v1.1 补）**
  - 充值页跟着渠道走：第 1 段「明确不做」里写着「不做微信/支付宝充值（第 6 段）」，充值页没有真实渠道就是空壳，所以归这一段

**服务端**
- 支付网关抽象：微信支付、支付宝适配器
- 充值下单、异步回调验签、掉单补单
- 退款流程 + 退款审核
- 提现：申请 → 审核 → 人工出款 → 凭证上传
- 渠道对账：下载对账单、比对、`reconciliation_diff` 落库
- 定时恒等式巡检：`余额 == SUM(balance_flow.amount)`

**数据库**
- `payment_channel`、`recharge_order`、`withdraw_order`、`reconciliation_diff`、`invoice`

**后台**
- 充值管理、退款审核、提现审核、对账差异处理

## 9.3 验收标准

- [ ] **真实支付 1 元** → 余额增加 1.00 → 后台能看到渠道流水号
- [ ] 同一回调**重放 3 次**，只入账 1 次（幂等唯一键：业务单号 + 类型）
- [ ] 人为断网制造掉单 → 补单脚本跑通 → 余额正确
- [ ] 提现申请 → 后台审核 → 人工出款 → 上传凭证 → 用户端看到状态流转
- [ ] 退款：全额退、部分退、累计退款不超原单
- [ ] 渠道对账单下载并比对，差异报表能输出
- [ ] 恒等式巡检定时任务跑通，差异立即告警
- [ ] 手机、后台、渠道三方金额对得上

## 9.4 明确不做

- 不做微信分账（见技术路线 §9.7）
- 不做自动打款到卡（企业付款资质另行评估）

## 9.5 风险与出口

| 风险 | 出口 |
|---|---|
| 商户号迟迟不下来 | 人工充值 + 线下转账已能支撑真实经营，本段延后不影响上线 |
| 提现出款资质不足 | 先做人工线下打款 + 凭证上传 + 记账 |

# 十、第 7 段：运营与治理收口

## 10.1 目标

让运营方**真的能自己干活**，而不是每件事都找技术。

## 10.2 范围

**移动端（10 页）**
- 模块 10 剩余：设置、企业、收藏、关注、客服、FAQ、投诉、反馈、关于、功能总览

**服务端**
- `ops` 域全量：内容审核、敏感词、投诉工单、黑名单、违规记录、公告
- 风控：频率限制、异常行为检测、账号风控
- 客服：`service_ticket` 工单系统
- 监控：Prometheus 指标、Grafana 面板、告警规则
- 日志：结构化日志、链路追踪
- 备份与灾备演练

**后台**
- 内容审核队列、敏感词管理、投诉工单、黑名单、客服工作台、系统配置、操作日志、登录日志、监控面板

## 10.3 验收标准

- [ ] 管理员按**运营动作清单**完整走通：审核律师 → 审核文章 → 处理投诉 → 拉黑用户 → 回复客服工单
- [ ] 内容审核：发一条含敏感词的消息 → **原文落库不被篡改** → 命中标注 → 展示层拦截
- [ ] 敏感词库可增删改，生效即时
- [ ] 投诉工单：用户提交 → 客服受理 → 回复 → 用户看到回复
- [ ] 黑名单用户无法登录，且登录时有明确提示
- [ ] 操作日志记录「谁/何时/从哪/改了什么」
- [ ] Prometheus 抓到接口 QPS、延迟、错误率；Grafana 面板可见
- [ ] 故意让某接口 500 → **告警真的会响**
- [ ] **备份恢复演练**：从备份恢复到新库，数据一致，业务可用
- [ ] 收藏、关注页可用；客服入口能进；FAQ 从后台配置
- [ ] 剩余 10 页四态齐全

## 10.4 明确不做

- 不做等保测评（资质侧，见并行轨道）
- 不做渗透测试（第 8 段收口时做）

# 十二、并行轨道（不进段，但必须与第 0 段同时启动）

这些是**审批周期**，不受「时间不是约束」这条保护——它们是外部方的时间，不是我们的。

| 轨道 | 卡在哪一段 | 谁负责 | 说明 |
|---|---|---|---|
| **Android 开发者账号** | 第 0 段 | 项目负责人 | 没它连内测包都发不出去 |
| **藏文字体来源与商用授权** | 第 0 段 P-2 | 项目负责人 | 旧项目那套 234 字形无 GSUB，不可用。开源许可是否允许嵌入 APP、商业字体报价与授权范围都要先定 |
| **豆包 API key / 配额 / 是否需企业资质** | 第 0 段 P-3 | 项目负责人 | 第 0 段探针的前置 |
| **个推应用 + 各厂商通道配置** | 第 2 段 | 项目负责人 | 华为/小米/OPPO/vivo 的推送通道需逐个申请 |
| **法条数据来源与人工校对责任人** | 第 3 段 | 项目负责人 | 2000–3000 条要逐条核，是长尾人工活。必须在第 0 段就启动，否则会把第 3 段拖成瓶颈 |
| **支付商户号** | 第 6 段 | 项目负责人 | 唯一能让第 6 段滑动的依赖 |
| **主体注册 / ICP 备案 / App 备案 / 公安联网备案 / 软著 / 等保** | 第 8 段 | 项目负责人 | 周期长，必须早期启动 |
| **应用商店账号**（各厂商） | 第 8 段 | 项目负责人 | 通常需要软著或备案号作为前置 |
