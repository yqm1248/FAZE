- 结论：**5 条不可见断言全部通过**（连真实 API）；**20 条巡检全部在允许范围内**（18 项为 0、2 项按台账豁免）。巡检已接进 CI。

---

## 一、为什么要有「不可见断言」

这次验收 68 条里，界面上能看出来的错占 80% 条数，而真正危险的**一条都跑不出来**：

| 类型 | 例子 | 界面能不能看出来 |
|---|---|---|
| 鉴权破例 | 无 token 该 401 还是 200 | 看不出来，只有客户端拦截器知道 |
| 动态响应头 | 支付密码剩余次数、`Retry-After` | 看不出来，跨域下前端**读不到** |
| 链路 id | `X-Trace-Id` | 看不出来，但排障时没它只能靠时间戳猜 |
| 跨域可读性 | `Access-Control-Expose-Headers` | 看不出来，头发了但不在列表里等于没发 |
| 数据的行合不合法 | 状态与流水不匹配、孤儿行 | 看不出来，要等用户在某个角落撞见 |

**这五类全都不产生「页面上的错误」，所以靠验收永远发现不了。**

## 二、5 条不可见断言（`scripts/monitor/check-invisible.mjs`）

连 `http://127.0.0.1:8081` 跑，只读操作（GET / 登录 / OPTIONS），不产生业务数据。

| ID | 断言 | 实测 |
|---|---|---|
| I1 | 无 token 调 `/app/account/profile` → **HTTP 401** 且业务码 `402002/402003` | ✅ PASS |
| I2 | 该 401 响应带 `X-Trace-Id` | ✅ PASS |
| I3 | 登录成功：`code=200` + 拿到 `accessToken` + **`user.id` 是字符串** | ✅ PASS |
| I4 | 带 token 调受保护接口 → 200 且带 `X-Trace-Id` | ✅ PASS |
| I5 | OPTIONS 预检的 `Access-Control-Expose-Headers` 含 `X-Trace-Id` / `X-First-Byte-Ms` / `X-Pay-Pwd-Remaining` / `Retry-After` | ✅ PASS |

### 其中 I5 有一个值得记的过程

第一次跑 `I5` **失败**：`缺失=X-Pay-Pwd-Remaining,Retry-After`。

但这两个头在 G6 已经加进 `CorsConfig` 了。原因很朴素：**8081 上跑的还是改动之前的进程**。

重启 API 后重跑，5 条全过。

> **这件事本身就是「不可见断言」存在的理由**：如果只看代码 diff，会以为已经修好；
> 只有真的发一次预检请求，才知道运行时生效没有。**代码改了对，服务没重启，等于没改。**

### 为什么没有测「支付密码错误 → 实际返回 `X-Pay-Pwd-Remaining`」

那需要把某个账号的支付密码试错，会触发锁定计数——**副作用大于收益**。改用两条合起来守：
- 服务端是否真的发这个头 → `CorsExposedHeadersTest`（G6）+ code review；
- 浏览器能不能读到 → I5 的暴露列表。

### 已知非零项台账（`scripts/monitor/known-issues.json`）

| 项 | 允许 | 为什么现在不清 | 关闭条件 |
|---|---|---|---|
| A12 | ≤1 | user 3 的 `realname_auth=rejected` 而 `realname_status=approved`。负责人定**方案 C：不改数据**（根因是 DRIFT-015 两套真相，改数据只是让两边一致） | DRIFT-015 修完后重跑，自动归 0 时删豁免 |
| A20 | ≤1 | `law_refs` 写「第七百三十三条」，但库缺真正的 733 正文（V710 明确不补录）。改快照只会把错误藏起来 | 补录真 733 正文并回写快照（段八） |

**台账机制的两个设计要点**：

1. **用 `≤` 而不是 `=`。** CI 的库是 Flyway 从空库建的、没有这两条历史脏数据，实测 0 条也必须通过。
2. **每条豁免必须写 `closeWhen`。** 没有关闭条件的豁免等于永久放弃这条检查——那就不该叫「已知问题」，该叫「已删除检查」。

## 四、CI 接了什么、没接什么

| 脚本 | 接进 CI | 位置 | 为什么 |
|---|---|---|---|
| `check-integrity.mjs` | ✅ 接了 | `backend` job（那里有 MySQL service） | 只读 SQL，无外部依赖 |
| `check-invisible.mjs` | ❌ **没接** | —— | 见下 |

**`check-invisible` 没接 CI 的理由**：它需要一个**运行中的 API 进程**。CI 的 backend job 现在只跑 `mvn test`，要接就得再起一次 Spring Boot（等健康检查、等 Flyway、还要保证与测试用同一个库），这会让 CI 多出一个「启动失败」的失败源。

而「起了服务却跑不通」和「代码错了」在 CI 日志里长得一样，都属于**红了但不知道修哪里**。所以它定位为**本地验收工具**（每轮验收前跑一次，证据附在验收文档里），等 G9 把 CI 装配稳定后再评估。

> **这条是判断，不是事实。** 如果以后有人真的忘了跑它而导致问题，就应该重新评估接入成本。

## 五、怎么跑

```powershell
# 巡检（需要库）
npm run check:integrity

# 不可见断言（需要 API 在 8081，且库里有测试账号 13800000001/123456）
npm run check:invisible

# 连别的环境
node scripts/monitor/check-invisible.mjs --base-url=http://127.0.0.1:8081
```

**退出码约定**（两个脚本一致）：

| 码 | 含义 | 处置 |
|---|---|---|
| 0 | 全部通过 | —— |
| 1 | 断言/检查失败 | 代码或数据有问题 |
| 2 | 环境不可用（连不上库/API） | 先起服务，不是代码问题 |

**把「环境问题」和「代码问题」分开是刻意的**：混在一起会让人在「服务没起」时报「代码回归」。

2. **`A05 自下单` 现在 n=0**——注意这是「库里没有发生」，不是「代码拦住了」。代码确实没有校验（DEF-014），只是运气好还没人这么干。
