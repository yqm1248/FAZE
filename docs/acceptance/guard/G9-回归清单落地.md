## 一、计划说怎么落，实际怎么落

计划 §4.3 末尾写：**R-01/02/07/10/14/15 进 verify 与 CI（自动）；R-03/08/09/12/13/16/20 进 PR 检查清单（模板）；R-04/05/06/17/19 进 check-invisible + 巡检 SQL（每日/每轮）**。另有 R-11（关键词黑名单）、R-18（schema diff）未分类。

实际执行时改了 3 处分类，每处都有理由：

| 计划 | 实际 | 为什么改 |
|---|---|---|
| R-15 进 verify | 进 CI（新增独立脚本） | 它要扫 Java 源码与迁移 SQL，跑在 `apps/mobile-app` 的 verify 里语义不对 |
| R-11 关键词黑名单 | **单独新脚本** `check-copy-tone.mjs` | `check-raw-text.ps1` 查的是「裸 `<Text>`」，与文案措辞是两件事，混进去会让那个脚本同时背两个职责 |
| R-06 进巡检 | **登记为缺口**（DEF-017） | 计划假设「单号撞唯一键会重试」，实测**没有重试逻辑**——要求的是一条不存在的代码 |

## 三、本次新增的 4 个机制

### 1. A21 造数残留巡检（R-19）

`data-integrity.sql` 加 A21：查**对外展示字段**里的造数痕迹（`app_user.nickname` / `lawyer.real_name` / `case_library.title`）。

实测命中 **8 条**：`app_user` 6 条（seed 的验收账号，昵称合法地含「测试」二字）+ `lawyer` 2 条（「验收律师甲」「端到端测试」）。按台账允许 ≤8，`closeWhen` = 上线前清库 + 生产库复跑应为 0。

**为什么允许值不是 0**：CI 的库是 Flyway 空库 + seed，seed 里的账号昵称本来就含「测试」。硬写 0 会让 CI 永久红，而永久红的门禁比没有更糟。

### 2. 文案内部口吻检查（R-11）

`scripts/check-copy-tone.mjs` 扫四语言 i18n 的 value，关键词 12 个。

**实测抓到 2 处真缺陷，都已修**：

| key | 原文 | 问题 | 改后 |
|---|---|---|---|
| `trade.payPassword.verifyDesc` | 「**用来演示**锁定与剩余次数…」 | 用户看不懂什么叫「演示」 | 「显示锁定状态与剩余次数…」 |
| `profile.settings.fontSizeNote` | 「**目标用户**里有不少中老年人…」 | 「目标用户」是产品内部词 | 「不少中老年人会使用…」 |

**已知盲区**：关键词表只有中文。bo / ug-Arab-CN / kk-Arab-CN 的内部口吻直译（如维吾尔文把「目标用户」直译）**检不出来**，那部分靠段八的人工核对。

### 3. 字段写入路径检查（R-15）

`scripts/facts/check-write-paths.mjs`：对 476 个业务字段逐一找「写入证据」（六种：Java setter / lambda 方法引用 / 字符串字面量 / XML `#{}` / XML 裸列名 / 种子与迁移 INSERT）。

**实测只有 2 个字段没有任何写入证据，且都是真缺口**（已登记 DEF-016）：

| 字段 | 现状 | 后果 |
|---|---|---|
| `content_review.reviewer_id` | 搜 `setReviewerId` 0 处，实库 5 行全 NULL | 管理端答不上「这条是谁处置的」 |
| `user_device.push_cid` | 搜 `setPushCid` 0 处，实库 153 行全 NULL | 推送找不到投递目标（比 DEF-007「通道未接」更深一层） |

**这条检查自己会过期**：字段补上写入路径后，`write-paths-baseline.json` 里那条会报「过期」，逼人删掉——防止台账变成新的历史包袱。

### 4. 每日巡检编排器 + PR 模板

`scripts/monitor/daily-check.mjs`：一条命令跑 8 项（事实/受控区块/基线/页面/承诺/文案/写入路径/数据完整性），结果追加到 `logs/daily-check-YYYY-MM-DD.log`（本地日期命名）。

**为什么不直接用 CI**：CI 只在 push/PR 时跑，而**数据类问题是在两次提交之间长出来的**（造数没清、手工改库、重复回调、脏数据跨天累积）——这类问题不会让任何一次构建变红。

`.github/PULL_REQUEST_TEMPLATE.md`：把 7 条人工项写成勾选项，每条带「什么情况下必须查」+ 反例（R-03 直接引用 DRIFT-014 的现场）。并且把 12 道自动门禁列成表放在前面，**让人知道哪些不用手勾**。

## 四、计划前提被推翻的 3 处

1. **R-04/R-05/R-06 的测试类有 3 个根本不存在**（`LawRefConsistencyTest` / `BizNoCollisionRetryTest` / `CaseIdempotencyTest`）。其中 R-06 的原因最实在：**计划要求的「撞唯一键重试」只做了一半**——订单号与充值单号有重试，其余 7 类业务单号没有（DEF-017）。这不是缺测试，是缺实现。
2. **R-08 要的 `ErrorBanner` 组件没建**：G5 查明仓里已有 `ErrorState`（整页错误）与 `useErrorMessage`（取文案）两个入口，再建第三个就是「同一件事三种呈现」。
3. **R-03 想靠 grep 自动查，实际查不了**：全仓 `LIMIT 1` 只有 8 处，人工核完都合法（都带 `ORDER BY` 或当前用户条件）。但**规则本身没法自动判**——「这个 WHERE 里该不该带 userId」需要知道业务语义，静态扫描答不了。所以它是 PR 人工项，不是脚本项。

**「有 8 处所以不用脚本」不等于「以后不用查」**：PR 模板里给了具体查法（`grep -rn "LIMIT 1" ...` 逐条看），下次新增一处时人会看到这条规则。

## 五、已知盲区（这一节比上面几节都重要）

1. **R-11 只认中文关键词**：三种少数民族文字的内部口吻查不出来。
2. **R-15 是静态扫描**：扫不到反射、动态拼接列名、DB 触发器写入的字段；反过来，注释里提到列名也会被算成「有写入」——**它是「查新增缺口」的工具，不是「证明所有字段都有写入」的证明**。
3. **PR 模板靠人勾**：它能让「没勾」变可见，不能让「假勾」消失。7 条人工项的真实性依赖评审者，不依赖 CI。
4. **`check-invisible` 仍不进 CI**（G7 的决定没变）：它需要运行中的 API 进程，接入会多一个「启动失败」的失败源。每日巡检里用 `--with-api` 时，**服务没起判「跳过」而不是「失败」**——因为「没起服务」和「服务坏了」在日志里长得一样。
5. **`npm run check:drift` 是个悬空命令**（指向不存在的 `scripts/facts/check-drift.mjs`），本次已删。DRIFT.md 是人工台账，没有可自动校验的形态。
