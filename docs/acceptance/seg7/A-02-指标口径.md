# A-02 数据看板 · 指标口径

> **用途**：`7-A10`「看板的每个数字都能说出口径与来源」的正面证据。
> **对应实现**：`services/faze-api/src/main/java/com/faze/modules/ops/admin/service/AdminDashboardService.java`
> + `modules/ops/mapper/DashboardMapper.java`（每个方法上都引用了本文节号）。
> **生成日期**：2026-11-08（第 7 段 A5）；**2026-11-09 修订**（第 7 段 T1：§8 接 V707 的 `app_user.region`、补 §10 的 `pendingReason`、加 §11 代码↔文档双向索引）。
> **口径总原则**：
> 1. 时间窗一律按 **Asia/Shanghai 自然日**切，换算成 UTC 边界后传给 SQL（库内存 UTC）。
> 2. 金额一律**整数分**，前端负责转元。
> 3. **昨日为 0 时环比返回 `null`**（页面显示 `—`），不返回 Infinity / NaN。
> 4. 拿不到数据的指标**返回空态 + 说明**，不造数；确实「口径待定」的指标返回
>    `value: null` + `pendingReason`（见 §10）。

## 1. 时间窗定义

| 参数 | 窗口 | 对比期 |
|---|---|---|
| `today` | 今日 00:00:00 – 24:00:00（Asia/Shanghai） | 昨日同一时段 |
| `7d` | 今日往前 7 个自然日（含今日） | 再往前 7 天 |
| `30d` | 今日往前 30 个自然日（含今日） | 再往前 30 天 |

SQL 边界由 Java 计算：`date.atStartOfDay(Asia/Shanghai).withZoneSameInstant(UTC)`。
**不在 SQL 里用 `CURDATE()` / `NOW()`**——那两个跟着 MySQL 服务器时区走，会与库内 UTC 口径打架。

## 2. 今日活跃用户（DAU）

- **定义**：时间窗内有登录成功的去重用户数。
- **算法**：
  ```sql
  SELECT COUNT(DISTINCT user_id) FROM login_log
  WHERE result = 'success' AND created_at >= :begin AND created_at < :end
  ```
- **数据来源**：`login_log`（B 类追加表）。
- **边界**：**这是降级口径**。设计口径是「当日登录 **或** 任意 `/app/**` 业务请求」的去重用户，但本段没有访问日志表（段 1 未建），拿不到「任意业务请求」。
- **已知局限**：只登录不操作的用户计入，只看页面不登录的用户**不计入**（本来就无法计入）。降级本身已在 `sys_config.dashboard.dau_definition` 里登记为 `login_or_request`，切换真口径时改这一处。
- **代码位置**：`DashboardMapper#countActiveUsers`；`AdminDashboardService#summary`。

## 3. 今日新增注册

- **算法**：
  ```sql
  SELECT COUNT(*) FROM app_user
  WHERE deleted_at IS NULL AND created_at >= :begin AND created_at < :end
  ```
- **数据来源**：`app_user`。
- **边界**：**不含软删账号**（`deleted_at IS NOT NULL` 不计入新增）。
- **已知局限**：软删后又恢复的用户会在恢复时保留原 `created_at`，不会重复计入。
- **代码位置**：`DashboardMapper#countNewUsers`；`AdminDashboardService#summary`。

## 4. 今日订单

- **算法**：
  ```sql
  SELECT COUNT(*) FROM orders WHERE created_at >= :begin AND created_at < :end
  ```
- **数据来源**：`orders`（**不是** `legal_order`——工作流 A5 写的表名不存在，实际表是 `orders`）。
- **边界**：**全状态计入**（待支付、已取消都算），因为看板看的是「下单量」不是「成交量」。
- **已知局限**：退款不减少计数（退款是独立状态，不是删除）。
- **代码位置**：`DashboardMapper#countOrders`；`AdminDashboardService#summary`。

## 5. 平台今日收入

- **算法**：
  ```sql
  SELECT COALESCE(SUM(platform_fee_cents), 0) FROM orders
  WHERE paid_at IS NOT NULL AND paid_at >= :begin AND paid_at < :end
  ```
- **数据来源**：`orders.platform_fee_cents`。
- **边界**：
  - **按 `paid_at` 落窗**，不是 `created_at`——收入在支付时确认。
  - **不含充值**（充值属预付款，不是收入；这是裁决 1 第④条的明确要求）。
  - **退款不扣减**（服务费在支付时已确认，退款走退款流水，另账）。
- **已知局限**：`platform_fee_cents` 为空的订单按 0 计（历史数据可能没回填）。
- **代码位置**：`DashboardMapper#sumPlatformFee`；`AdminDashboardService#summary`。

## 6. 订单量趋势（近 14 天）

- **算法**：
  ```sql
  SELECT DATE(created_at) AS d, COUNT(*) AS c FROM orders
  WHERE created_at >= :begin GROUP BY DATE(created_at) ORDER BY d
  ```
- **数据来源**：`orders`。
- **边界**：**缺日补 0**（Service 层按 14 天逐日填充）。不补 0 会让折线把没数据的那天直接连起来，看起来像连续增长。
- **分桶口径（2026-11-09 修正）**：**按 Asia/Shanghai 自然日切桶**，SQL 用
  `DATE(created_at + INTERVAL 8 HOUR)`。旧实现是 `DATE(created_at)`（UTC 日界 = 上海 08:00），
  实测过「上海 11-09 01:21 的订单被折线记到 11-08，而 summary 的今日窗口算进 11-09」的矛盾，
  已修。中国无夏令时，+8 恒定，不需要 `CONVERT_TZ` 的时区表。
- **已知局限**：`DATE(created_at + INTERVAL 8 HOUR)` 对 1900 年以前/未来极远日期无意义，本项目不涉及；
  跨月/跨年边界同样按上海日历切，无需特殊处理。
- **代码位置**：`DashboardMapper#selectOrderTrend`；`AdminDashboardService#trends`。

## 7. 收入趋势（近 14 天）

- **算法**：
  ```sql
  SELECT DATE(paid_at) AS d, COALESCE(SUM(platform_fee_cents), 0) AS c FROM orders
  WHERE paid_at IS NOT NULL AND paid_at >= :begin GROUP BY DATE(paid_at) ORDER BY d
  ```
- **数据来源**：`orders.platform_fee_cents`。
- **边界**：与 §5 同一口径，按支付日落窗；缺日补 0。
- **分桶口径（2026-11-09 修正）**：与 §6 相同，按 **Asia/Shanghai 自然日**切桶
  （`DATE(paid_at + INTERVAL 8 HOUR)`），不再用 UTC 日界定日。
- **已知局限**：同 §5（`platform_fee_cents` 为空按 0）。
- **代码位置**：`DashboardMapper#selectRevenueTrend`；`AdminDashboardService#trends`。

## 8. 用户地区分布（2026-11-09 重写：V707 已接通）

> **修订背景**：本节旧版写的是「**无法实现**，`app_user` 没有 `region` 列」。那是 A5 时的真实状态；
> V707 迁移已补 `app_user.region` + `idx_app_user_region`，`DashboardMapper#selectRegions` 已接通。
> 旧结论已不成立，故整节重写。

- **定义**：按**注册地区**（`app_user.region`）统计用户数，取前 5 名，其余合并为「其他」。
- **算法（真实 SQL）**：
  ```sql
  SELECT COALESCE(NULLIF(region, ''), '其他') AS name, COUNT(*) AS c
  FROM app_user
  WHERE deleted_at IS NULL
  GROUP BY COALESCE(NULLIF(region, ''), '其他')
  ORDER BY c DESC
  ```
  Service 层取前 5 名，第 6 名起的人数和并入「其他」（若「其他」已在前 5 名，则并入该项，
  不再 append 第二项——避免出现两个「其他」）。
- **数据来源**：`app_user.region`（V707 新建列 + `idx_app_user_region`）。
- **边界**：
  - NULL 与空串都归「其他」：用 `COALESCE(NULLIF(region, ''), '其他')` 归一化。
    放在 SQL 里而不是 Java 里，是因为排序要在合并之前完成。
  - **只过滤 `deleted_at IS NULL`**，不按 `status` 过滤（见下方「已知局限」的口径差）。
- **已知局限（必须写清，不许含糊）**：
  1. **列有了、数据还没有**：注册流程仍未采集地区（段 1 的注册页不收集），
     所以**当前 `region` 恒为 NULL**，接口真实返回只有一项「其他」。这不是 bug，
     是「数据结构已就位、采集入口未做」的如实体现。段 8 补采集入口后自然出现真实地区。
  2. **口径差 1 人（§十一 第 19 条）**：本指标只过滤 `deleted_at IS NULL`，
     而公告「全量」可发人群过滤 `status = 'active'`。2026-11-09 实测库内
     `app_user` 共 **9 行**（active 8 行 + cancelled 1 行，且 9 行的 `deleted_at` 全为 NULL），
     所以**看板计 9 人、公告人群计 8 人，两者差 1 人**。
     **当前处理：不补偿**。看板回答「有多少注册用户（未注销）」，
     公告回答「有多少可触达用户」，语义不同；强行对齐会让其中一个说错话。
     **段 8 决定**是否统一为 `status='active' AND deleted_at IS NULL`，
     或给看板加「不可触达」副文案。这一条不是遗漏，是**已知口径差 + 待决策项**。
- **代码位置**：`DashboardMapper#selectRegions`；`AdminDashboardService#regions`。

## 10. 实时在线（`onlineCount`）—— 口径待定 `pendingReason`

- **本段不实现**：WebSocket 会话在 `conversation` 域的 `OnlineRegistry`（单实例内存），
  本段跨域读需要新增查询接口，超出「看板收口」的范围。
- **接口行为（F3 第 4 条落地）**：`onlineCount` 返回 `null`，并且响应里带两个字段：
  ```json
  {
    "onlineCount": null,
    "pendingReason": "口径待定：实时在线数需要 WebSocket 会话查询，本段不跨域读，段 8 接入",
    "pendingReasons": { "onlineCount": "口径待定：实时在线数需要 WebSocket 会话查询，本段不跨域读，段 8 接入" }
  }
  ```
  - `pendingReason`：单字符串，兼容只认一个原因的旧前端；
  - `pendingReasons`：字段级 map，前端可按 `pendingReasons.onlineCount` 精确挂到卡片上。
  - **4 个核心指标也允许 `null`**（VO 用包装类 `Long`）：若将来某个指标口径被推翻，
    Service 置 `null` + 在同名字段写 `pendingReasons` 即可，页面显示「口径待定」
    而不是 0 或空白。**不许用 0 冒充「没有数据」**。
- **恢复条件**：段 8 在 `conversation` 域加 `OnlineQueryService.count()`，看板注入即可。**已记挂账。**
- **代码位置**：`AdminDashboardService#summary`；`DashboardSummaryVO#onlineCount/pendingReason/pendingReasons`。

## 附 1：指标计数与 `7-A10` 的「10 个指标」

`7-A10` 原文要求「10 个指标每一个都能在口径文档里找到算法与来源」。按本段**实际交付**：

- **可计算指标 9 个**：§2 活跃、§3 新增、§4 订单、§5 收入、§6 订单趋势、§7 收入趋势、
  §8 地区分布、§9 待我处理（5 类合计 1 项）、§10 实时在线（口径待定）。
- **口径项 1 个**：§1 时间窗定义（不是数值指标，但它决定上面 9 个的边界，且页面
  「数据统计截至 …」的文案由它决定）。

**结论**：**不为凑 10 硬拆**。若验收方按「数值指标」数，是 9 个，缺的那 1 个是
`onlineCount`（已按 §10 明确标注「口径待定 + 段 8 接入」）；若把 §1 时间窗口径算作第 10 项，
则 10/10 齐全。两种数法都不影响「每个数字都能说出口径与来源」这一判据。
