# ── 对 legal_order / balance_flow 全表 COUNT 慢查询的判断（F3-4 要求）────────────────
# 1) 工作流 A5 写的表名 `legal_order` **不存在**（本段实测）：真实表是 `orders`。
#    对不存在的表做全表 COUNT 无从谈起；对 `orders` 的 COUNT，当前 16 行、EXPLAIN 显示
#    type=ALL 且 rows=16 —— 数据量小时全表扫描是最优解，加索引反而增加写放大。
# 2) `balance_flow` 当前不在看板任何指标里（余额流水用于钱包/对账，不是 A-02 的 4 组接口）。
#    若将来把「平台流水」加进看板，它才是随数据量线性变慢的候选：
#    balance_flow 是只增不改的资金流水表，10 万行以上时 `SUM(delta_cents)` 全表扫描
#    在 100ms 级；50 万行后进入 500ms 级，需要预聚合（这也是代码注释里写死的升级路径）。
# 3) 结论：本段 4 个接口在当前数据量（app_user 9 / orders 16 / login_log 477 / service_ticket 少量）
#    下全部是毫秒级；**慢查询的触发条件是数据量，不是 SQL 写法**。
#    升级路径（代码注释同步）：数据量 > 50 万行时改为预聚合表 dashboard_daily_stat；
