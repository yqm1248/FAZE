## 一、可复现的动作序列

### 1.1 前置：登录拿 token

请求体（UTF-8 无 BOM 文件，**不用 PowerShell 内联字符串**——实测会把中文编成 `?`）：

```json
{"phone":"13800000001","password":"123456","deviceId":"seg3-lead-verify"}
```

```powershell
curl.exe -s -S -o tmp/seg3/login.out -w "%{http_code}" -X POST "http://127.0.0.1:8081/api/v1/pub/auth/login/password" `
  -H "Content-Type: application/json; charset=utf-8" -H "X-Device-Id: seg3-lead-verify" `
  --data-binary "@tmp/seg3/login.json"
```

实测：HTTP 200，`userId=1`，`accessToken` 长度 239。

> **踩坑记录**：登录的 `deviceId` 是**请求体字段**（`LoginBO.deviceId`，`@NotBlank`），不是只放请求头就行；只传 `X-Device-Id` 头会返回 `401001 deviceId: 设备标识不能为空`。头与体必须一致（AuthService 会比对，不一致记风控）。

## 三、库内核对：原文完整

```sql
SELECT id, role, CHAR_LENGTH(content) AS len, LEFT(content,20) AS head, HEX(LEFT(content,3)) AS first3_hex
FROM ai_message ORDER BY id DESC LIMIT 8;
```


判读：

| 核对项 | 结果 |
|---|---|
| 3 条 user 原文是否完整 | **是**。长度 11 / 9 / 32 与请求一致；`E5BFBDE795A5E4BBA5` 是「忽略以上」的 UTF-8 字节、`E8BE93E587BA` 是「输出」、`6967...` 是 `ign`，说明落库的是原文，**不是 `????` 或空串** |
| 是否写了 assistant 行 | 是，3 条 `role='assistant'` 内容固定为「无法处理该请求」（7 字），即拦截也留痕，便于 A-28 追溯 |
| user 行的 `content_id` / `refs` | 均为 NULL（D4 约定：user 消息不存 refs、无 content_id），与 E2 的核对一致 |
| 有没有把注入内容打进日志 | 未检查日志文件（本条的判据不含日志）；`ai_message.content` 属 L4，代码侧禁止打日志，见 §十一 第 21 条 |
