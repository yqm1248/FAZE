## 一、三项交付物

### ① 稳定的断言钩子

`shared/components/AiGeneratedLabel.tsx` 实测四套钩子（文件头注释第 3 条 + 源码）：

| 钩子 | 值 | 用途 |
|---|---|---|
| `testID` | `ai-generated-label` | E2E 按 testID 查元素（RN 里同时映射 accessibility identifier） |
| `nativeID` | `ai-generated-label` | Android 原生 `resource-id`（E2E 第三套兜底） |
| `accessibilityLabel` | `t('common.aiGeneratedLabel')` | 无障碍朗读 + 只认该属性的 E2E 工具 |
| `accessibilityRole` | `text` | 保证被识别为可读文本 |

**CDP 实测（真实 Chrome）**：连发 3 个问题后
```text
labelCount = 3          ← 3 条 AI 回答各一个
refCount   = 3          ← 3 个 refs 卡片
msgBubbleCount = 6      ← 3 user + 3 assistant
bubbleInfo = [ {ai-msg-0, hasLabel:true}, {ai-msg-1, hasLabel:false},
               {ai-msg-2, hasLabel:true}, {ai-msg-3, hasLabel:false},
               {ai-msg-4, hasLabel:true}, {ai-msg-5, hasLabel:false} ]
```
→ **完全交替（有/无/有/无/有/无）**：标识只挂在 assistant 气泡上，用户消息一个都没有。
这正好对应用例要求「每条回答都带标识、用户消息不带」。

> 注：`msgBubbleCount` 的顺序是列表倒序渲染的结果，不影响判定——判定看的是**交替模式**与**数量相等**（3 个标识 : 3 条 assistant）。

### ② 文案走 `t()`

```powershell
Select-String -Path apps/mobile-app/features/*/*,apps/mobile-app/shared/*/*,apps/mobile-app/app/* -Include *.tsx -Pattern '本内容由 AI 生成'
```
实测 **命中 0**。

文案只在 i18n 资源里：
```text
apps/mobile-app/shared/i18n/resources/zh-Hans/common.json:
  "aiGeneratedLabel": "本内容由 AI 生成，仅供参考",
```
其余三语言（`bo` / `ug-Arab-CN` / `kk-Arab-CN`）按登记式缺译写入 `.i18n-pending.json`，不硬翻
（i18n 规范 §5.1；E1 已说明「四语言 key 同构」在当前 `check-i18n` 口径下做不到，见 `E1-label.md`）。

## 三、没做到的 / 风险（如实记录）

1. **不是真机**：RN Web 与原生在 `accessibilityLabel` 的暴露方式、`nativeID` 的 `resource-id` 映射上有差异。
   **`nativeID` 这一条在 web 上无法验证**（它是 Android 原生属性）——这是本节最实质的缺口。
   建议：段 4 开始前用真机或 121 平台跑一次「按 `resource-id=ai-generated-label` 查元素」。
2. **E2E 脚本本身未交付**：工作流把 E2E 执行归负责人（121），本段只交钩子与自证。
3. `labelCount` 是「当前页面上」的计数（一条对话 3 轮），不是「历史所有回答」。跨会话的标识覆盖未验。
