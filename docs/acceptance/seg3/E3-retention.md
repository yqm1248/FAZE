## 三、文档里没有「自动清理」的实现承诺，代码里也没有

工作流 E3 第 2 条：**超期处理本段不做自动清理**，只留「人工审批的运维脚本 + 先归档后删除」。

文档侧（`AI对话留存策略.md` §二）明写「**本段没有任何 `@Scheduled` 清理器**——这一点在验收时要能断言」。

代码侧实测（`modules/ai` 全包，含子目录）：

```
# 与留存清理相关的标识符（应为 0）
retention | RetentionClean | DELETE FROM ai_message        →  0 命中
# 真实 @Scheduled 注解（应为 0；只在 AiStreamSchedulerConfig 的注释里出现过这个词）
@Scheduled                                                  →  唯一命中在 AiStreamSchedulerConfig.java 的注释文字中
```

✅ **没有任何定时清理器**、没有任何 `DELETE FROM ai_message`。
✅ 说明 `ai_message_retention_days` 只供运维脚本读取，不驱动任何后台任务——与文档口径一致。

> 唯一命中 `@Scheduled` 的地方是 `AiStreamSchedulerConfig` 的类注释（「也不改用 Spring 的 TaskScheduler 自动配置——那会受 `spring.task.scheduling.pool-size` 影响，且与 `@Scheduled` 任务抢同一批线程」），是**在解释为什么不用**它，不是使用它。

## 七、遗留与说明

1. **超期清理脚本不存在，也不该现在有**：清理必须走「人工审批 + 先归档后删除」，工作流明确本段不做。将来要做时，脚本要读 `ai_message_retention_days`，并且**必须先归档再删**——这条写进了文档 §二，不要用定时任务代替审批。
2. **`ai_message_retention_days` 的 `category` 用 `audit` 而不是 `ai`**：它不是 AI 功能参数，是合规留存期。放 `audit` 组能让 A-08 页面按「审计与留存」聚合展示，避免运营在「AI 参数」里随手改留存期（改小等于提前销毁证据）。
3. **三处一致性（文档 / G2 / H2）的最终复核归 I 组**：G2 的删除接口一旦写成物理删除，H2 就查不到、`3-A6` 的可追溯性也断了。这属于 I 组收口时的交叉检查项。
