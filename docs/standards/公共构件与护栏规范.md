## 一、这份文档解决什么

第三方验收 68 条里，**有 5 类模式各出现了 ≥2 次**（不是 5 个 bug，是 5 种复发机制）：

| # | 模式 | 本次已发生的实例 | 拦它的东西 |
|---|---|---|---|
| A | 同一行为两套实现 | 幂等键 5 处各写各的；法条回查用关键词搜索 | 本文件的构件（§二） |
| B | 静默兜底 | `find(...) ?? list[0]` 把「没找到」伪装成「找到了」 | ESLint `no-array-fallback` |
| C | 状态双真相 | 实名两列不同步（`realname_auth` vs `app_user.realname_status`） | DRIFT-015 + 巡检 SQL |
| D | 有读无写 / 有写无校验 | `court_name` 全仓 0 处写入；`view_count` 不自增 | 字段生命周期登记（G9） |
| E | 契约承诺与实现不符 | 注释承诺幂等、文案承诺「影响全 App」 | 本文件 §三 + `check:contracts`（G8） |

**写这一份而不是六份的理由**：这六条护栏各自都只有几十行，但它们**必须一起读**——
因为它们共用同一套判断标准：**同一件事只允许一个入口，入口之外的写法必须被机器拦住**。

## 二、六个构件

### 2.1 `useIdempotencyKey(prefix)` —— 幂等键的唯一生成点

**位置**：`shared/hooks/useIdempotencyKey.ts`

**语义只有一种，写反就失去意义**：

| 时机 | 动作 | 为什么 |
|---|---|---|
| 页面挂载 | 生成一次 | 同一次操作的多次点击、多次重试，必须用同一个键 |
| **成功后** | `reset()` 换新键 | 下一次是**新操作**；复用旧键会让服务端回放上次结果，用户看到「提交成功」但其实是上一单 |
| **失败后** | **不 reset** | 重试必须复用同一个键，服务端才认得出这是重试而不是新提交 |

**改造前后的实测差异**：

| 位置 | 改造前 | 问题 |
|---|---|---|
| `features/case/api/client.ts` | 在 api 层 `newIdempotencyKey()` | 每次调用新键 = 每次都当新提交，网络抖动后重试会建出**第二个案件** |
| `features/lawyer/pages/LawyerDetailPage.tsx` | 每次点击现生成 | 同上，会建出**第二单** |
| `features/trade/pages/RechargePage.tsx` | 页面内自写一份生成函数 | 行为对，但是**第二套实现** |
| `features/workbench/components/WithdrawPanel.tsx` | 第三套实现 | 同上 |

四处现在都走同一个 hook。**拦它的两道机器**：
- ESLint `no-idem-key-in-api`（禁 `newIdempotencyKey` 标识符）；
- ESLint api 层专属块（`features/*/api/**` 禁 `Math.random` / `Date.now`）。

### 2.2 `useLawItemByRef(lawItemId)` —— 法条按主键回查

**位置**：`shared/hooks/useLawItemByRef.ts`

**为什么必须按 id**：客户端手里是 `law_refs` 快照里的 `lawItemId`。旧实现是
「拿 `lawName + articleNo` 去关键词搜索，再 `find(...) ?? list[0]` 兜底」——
**检索结果一变就显示出另一条法条**。那不是显示错误，是**内容错误**（用户据此判断法律依据）。

**这条护栏的前提一开始不成立**：App 端当时**只有** `GET /pub/law-items` 列表接口，
没有任何「按 id 查单条」的接口，所以旧实现是没得选。2026-11-11 补了
`GET /api/v1/pub/law-items/{id}`（`LawItemPublicDetail`，**含全文、不过滤已废止行**），
按 id 回查才真正可行。

> **这条是本文件唯一一条「先补接口、再立护栏」的**。其余五条都只动前端。

### 2.3 `useOptimisticToggle` —— 收藏 / 关注的统一交互

**位置**：`shared/hooks/useOptimisticToggle.ts`

> **计划里叫 `useFavorite(targetType, targetId)`，实现时改了名与签名。** 原因见 §五 偏差一。

统一三件事：**乐观翻转 → 请求 → 失败回滚**，外加防重入。

改造前 `CaseDetailPage` 与 `LawyerDetailPage` 各写一遍，两处行为不同：
- 案例收藏：失败**不**回滚（界面显示已收藏，服务端没变）；
- 律师关注：任何错误都 `toast` 成「登录已过期」（**复用了一个特定错误码的文案**，用户看到的信息是错的）。

### 2.4 `formatAmount` / `MoneyText` —— 金额展示唯一入口

**位置**：`shared/i18n/datetime.ts` 的 `formatAmount(cents, withSymbol)`、`shared/components/MoneyText.tsx`

金额是**整数分**（AGENTS §4.5），展示必须走它：它用整数运算取整数位与两位小数，
带千分位与 `-` 号，`withSymbol=false` 给需要「不带 ¥ 的元串」的场景。

**本次清掉的存量**：

| 文件 | 处数 | 原写法 |
|---|---|---|
| `features/workbench/pages/IncomePage.tsx` | 5 | `` `¥ ${yuan(x)}` `` + 一个自写的 `yuan()`（内含 `value / 100` **浮点运算**） |
| `features/workbench/components/WithdrawPanel.tsx` | 1 | `` `¥ ${formatCents(x)}` `` + 自写的 `formatCents()` |

两个本地函数都是「分 → 带千分位元串」的**第二份实现**，现在都改为委托 `formatAmount`。
**顺带修掉一处浮点运算**（`yuan()` 原来用 `/100` 再 `toFixed(2)`）。

**两处合法例外**（带 `eslint-disable` 与理由）：`FilingPage` 与 `FilingDonePage` 里
回显的是**用户在表单里输入的原始文本**，不是「分 → 元」的格式化。用 `formatAmount`
会补两位小数、加千分位，等于在确认页改变用户刚看到的值——那是行为变更，需要验收拍板，
不是护栏该顺手做的事。

### 2.5 错误文案：**没有**新建 `ErrorBanner`

**计划要求建 `ErrorBanner` 统一「错误文案按错误码分流」。实际没有建，因为它已经有了两份：**

| 已有构件 | 负责什么 |
|---|---|
| `shared/components/ErrorState.tsx` | 整页错误态（四态之一） |
| `shared/hooks/useErrorMessage.ts` | 内联错误的一行文案，按 `AppError.msgKey` 翻译 |

再建第三个「错误横幅」组件，结果是**同一件事三种呈现**——正好是这份文档要消灭的形态。

所以改为：**修掉硬编码**。全仓 `t('error.xxx') as MessageKey` 盘点后只有 1 处真违规
（`LawyerDetailPage` 把任意失败显示成「登录已过期」），已改为 `useErrorMessage`。

> **判定标准**：什么时候该新建构件？**当且仅当现有构件无法表达这个职责时。**
> 「我想统一某件事」不等于「我要新建一个组件」——先数清楚已经有几个入口。

### 2.6 归属校验模板（后端）

**规则**：删除 / 更新类操作，SQL 条件里必须带 `user_id = 当前用户`；
**禁止**「先查任意用户的一行（`LIMIT 1` 且不带 user 条件），再比较 userId 抛 403」。

**为什么**：后一种写法在**多用户共享的目标**上必然出错。实例（DRIFT-015）：

`SocialQueryService.unfavorite` 先 `LIMIT 1` 取**任意用户**的收藏行（无 `WHERE user_id`、无 `ORDER BY`），
再把这一行的 `userId` 与调用方比较。后果是**行为取决于数据库返回哪一行**——
同一个请求，换个用户重试就换个结果。实测：同一 token 下 `targetId=3`（有人收藏）返回
`401008 无权限`，`targetId=99`（无人收藏）返回 `200`——**完全反了**。

**机器可查的证据**：后端全仓 `LIMIT 1` 共 **7 处**（1 处是注释），逐处判定：

| 位置 | 判定 |
|---|---|
| `FileRecordMapper` ×2 | 合理：按 id / owner 取最新文件 |
| `ConversationSeqGenerator` | 合理：取最大 seq |
| `DocTemplateResolver` | 合理：取模板 |
| `SignatureService` | 合理：取当前用户签名（条件里带 user） |
| `LawyerApplicationService` | 合理：取该用户最新申请（条件里带 user） |
| **`SocialQueryService:140`** | **违规**：不带 user 条件取任意行再判 403 → DRIFT-015，待业务修复 |

> **这条规则目前只有 code review 在拦，没有自动门禁。** 写在这里而不是假装它有机器拦截——
> 按《说辞一致与真相源规范》§七，**答不上「谁在拦」的规则不该写成已生效**。

## 三、三条 ESLint 规则

规则写在 `apps/mobile-app/eslint.config.mjs` 的 `no-restricted-syntax`（无需自定义插件）。

| 规则 | 拦什么 | 对应回归项 |
|---|---|---|
| `no-array-fallback` | `x ?? arr[0]` 这类静默兜底 | R-02 |
| `no-raw-money` | 模板字符串里出现 `¥`（金额手拼） | R-08 同源 |
| `no-idem-key-in-api` | 自造 `newIdempotencyKey`；api 层 `Math.random` / `Date.now` | R-01 |

**三条规则的上线过程都记录了误报与修正**：

1. `no-raw-money` 第一版选择器写的是 `TemplateElement[value.raw=/¥\$\{/]`——**永远匹配不到**。
   `${` 是模板字面量的**语法**，不在 `raw` 里；`` `¥${n}` `` 的 AST 是
   `TemplateElement(raw="¥") + Expression + TemplateElement(raw="")`。改为匹配 `raw` 含 `¥`。
   **教训：选择器写完要拿一个已知违规的文件验证它真的会报。**
2. `no-idem-key-in-api` 如果只拦 api 层，页面里内联 `Math.random()` 就漏了（`LawyerDetailPage`
   原来正是这样）。所以拆成两条：全局禁标识符 + api 层禁随机源。
3. `Math.random` 在页面层**是合法的**（聊天页用它造 `clientMsgId`、倒计时用 `Date.now()`），
   所以 api 层规则用独立的 files 块限定范围，不能写进全局。

## 四、豁免台账（每一条都必须可审）

| 文件 | 关掉什么 | 理由 |
|---|---|---|
| `shared/components/LocalizedText.tsx`、`LtrText.tsx` | `no-restricted-imports` + `no-restricted-syntax` | 全仓唯一允许 import RN `Text` 的地方 |
| `shared/components/icons/**`、`DirectionalIcon.tsx` | `no-restricted-syntax` | 图标镜像的唯一合法落点 |
| `shared/theme/fonts.ts` | `no-require-imports` | Metro 只认 `require('*.ttf')` |
| `shared/theme/**`、`app.config.ts` | `no-restricted-syntax` | 设计令牌与 app 清单必须写颜色字面量 |
| `app/dev/**`、`features/dev/**` | `no-restricted-syntax` | 探针页不进 release 包 |
| **`shared/hooks/useIdempotencyKey.ts`** | `no-restricted-syntax` | **幂等键生成的唯一合法落点**（本文件新增） |
| `FilingPage.tsx`、`FilingDonePage.tsx` 各 1 行 | 单行 `eslint-disable-next-line` | 金额输入原文回显，非格式化（§2.4） |

> 豁免数从 4 组变 6 组 + 2 行。**每加一组都要写明理由**，否则下一个人会照着加第七组。

## 五、与计划的三处偏差（如实记录）

| # | 计划写的 | 实际做的 | 为什么 |
|---|---|---|---|
| 一 | `useFavorite(targetType, targetId)` | `useOptimisticToggle({ value, onChange, apply })` | 计划签名会让 `shared/` 反向 import `features/`（收藏在 content、关注在 lawyer），违反 AGENTS §3.1 分层。注入执行函数既保住分层，又不减少统一性。**另外改成受控模式**：真值来自异步详情接口，hook 内部持有会出现「接口回来把用户刚点的结果覆盖掉」 |
| 二 | 新建 `ErrorBanner` 组件 | 不新建，修掉硬编码 | 已有 `ErrorState` + `useErrorMessage` 覆盖同一职责，再建就是第三套（§2.5） |
| 三 | `useLawItemByRef` 直接落地 | **先补后端接口** `GET /pub/law-items/{id}` | 计划假设了「按 id 回查」的接口存在，实测 App 端只有列表接口。不补接口这条护栏无处落地 |

> 三处偏差都不是「简化」，是**计划的前提与仓库实际不符**。记下来，否则下一个人会照计划再试一遍。

## 五·补、G9 新增的四个检查（2026-11-13）

《护栏计划》§4.3 的回归清单 R-01~R-20 落地（G9）时补了四个机制，每个都对应一条「之前没人拦」的规则：

| 机制 | 命令 | 覆盖 | 实测抓到什么 |
|---|---|---|---|
| 造数残留巡检 **A21** | `npm run check:integrity` | R-19 | 8 条造数痕迹（seed 验收账号 + 2 名验收律师），按实测值进台账 |
| 文案内部口吻 | `npm run check:copy-tone` | R-11 | **2 处真缺陷，已修**：支付密码页「用来演示锁定」、字号说明「目标用户里有不少中老年人」 |
| 字段写入路径 | `npm run check:write-paths` | R-15 | **2 个真缺口**：`content_review.reviewer_id` 与 `user_device.push_cid` 全 NULL（DEF-016） |
| 每日巡检编排 | `npm run check:daily` | R-04/05/17/19 等 | 8 项一次跑完，日志按**本地日期**落 `logs/daily-check-YYYY-MM-DD.log` |

外加 `.github/PULL_REQUEST_TEMPLATE.md`：7 条人工规则（R-03/08/09/12/13/16/20）的落地载体。**模板里每条都带「什么情况下必须查」+ 一个反例**，不写成光秃秃的勾选项——否则人会全勾。

四条共同的纪律（与 §四 豁免台账同源）：

1. **每个台账必须写 `closeWhen`**，而且**检查自己会过期**：字段补上写入路径后，`write-paths-baseline.json` 里那条会报「过期」并让 CI 红，逼人删掉它。台账不能变成新的历史包袱。
2. **允许值用 `≤` 不用 `=`**：CI 的库是 Flyway 空库 + seed，本地库有历史数据，两边实测值不同，写等号必有一边永久红。
3. **「服务没起」判「跳过」不判「失败」**：每日巡检跑不可见断言时，API 不在线是常态；把它判失败只会训练人忽略红灯。
4. **新豁免必须同时在验收文档记一笔**，不允许只改 JSON。

## 六、这套护栏的已知盲区

1. **`no-raw-money` 只拦模板字符串**。`'¥' + x`、`String(x).padStart` 都拦不住。
2. **`no-array-fallback` 只拦 `?? arr[0]`**。`arr[0] ?? fallback`、`arr.at(0)`、`arr.shift()` 都不拦。
3. **归属校验（§2.6）没有自动门禁**，只有 code review。
4. **`implemented` 类的视觉一致性不归这套护栏管**（见 `design/PAGE-MAP.json` 的 `legend`）。
5. 三条规则都只覆盖 `apps/mobile-app`。**PC 后台（`pc/admin-web`）目前 0 条自定义 lint**——
   那边同类问题一条都拦不住。
6. **文案口吻检查只认中文关键词**：bo / ug-Arab-CN / kk-Arab-CN 三种语言的「内部口吻」直译
   （例如维吾尔文把「目标用户」直译成 نىشان ئىشلەتكۈچىلەر）用中文关键词**检不出来**，
   这部分靠段八的「四语言译文人工核对」兜。
7. **写入路径检查是静态扫描**：扫不到反射、动态拼接列名、DB 触发器写入的字段；反过来，
   注释里提到列名也会被算成「有写入」。**它是「查新增缺口」的工具，不是「证明所有字段都有写入」的证明。**
8. **PR 模板靠人勾**：能让「没勾」变可见，不能让「假勾」消失。7 条人工项的真实性依赖评审者，不依赖 CI。
