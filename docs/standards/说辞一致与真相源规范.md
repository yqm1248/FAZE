# 说辞一致与真相源规范

> **【文档基线 v1.67】**
>
> 适用范围：本仓库全部代码、文档、设计稿。
> 强制性：**强制项，不是建议**。违反后果见 §七「承接手段」。
> 与既有文档的关系：本规范不取代任何现有规范，只补「同一个事实在三个地方说法不同时，听谁的」这一层。

---

## 零、这份规范解决什么问题

**一句话：同一个事实，在代码、文档、设计稿三处只允许有一种说法。**

### 0.1 立规的直接动因

第三方对本项目做了一轮 68 条验收。逐条复核后的结论是：

| 判定 | 条数 | 含义 |
|---|---|---|
| 真 | 42 | 代码确有缺陷 |
| 部分真 | 16 | 现象存在，但归因或边界说错了 |
| 假 | 7 | **代码是对的，验收方按文档/设计稿的期望判定为错** |
| 剔除 | 3 | 已由负责人明确延期或不重要 |

**那 7 条误报的原因不是验收方看错了，是三处说法不同：**
验收方按文档期望、代码按自己实现，两边都没错，错的是没人负责对齐。

### 0.2 一个开篇实证：仓库里有四个「71」

截至本规范确立时，仓库里同时存在这些说法，且**全部正确、全部自洽、互相不矛盾**：

| 说法 | 出处 | 实际构成 |
|---|---|---|
| APP 有 **68** 个页面 | 《开发计划总纲》《UI 设计顺序》 | 有设计稿的主屏数 |
| APP 有 **69** 个页面 | `docs/README.md`、`AGENTS.md`、导航树 | 产品页面数 = 68 + 「我的投诉」（无设计稿） |
| `design/ui/` 有 **71** 个 HTML | `docs/README.md` §二 | 68 主屏 + 3 个弹层补充屏 + 0 |
| `PAGE_ROUTES` 有 **71** 条 | `routes.ts` | 69 产品路由 + 2 个开发探测页 |
| 页面实现有 **71** 个 | `features/**/*Page.tsx` | 69 产品页 + 2 个探测页 |

**四个数字全对，读者却无法判断哪个是哪个。** 这就是本规范要消灭的东西——不是错误，是**口径缺失**。

跑 `node scripts/facts/page-inventory.mjs` 可以得到上表每一个数字及其构成，不用人工数。

> **这条实证的结论：数字必须机器算，不能人写。** 人写的数字会在下一次改动时静默过期。

## 一、真相源分级

处理任何「说法不一致」，先按这张表定权威：

| 级别 | 是什么 | 权威度 | 谁可以改它 |
|---|---|---|---|
| **P0** | 运行中的代码 + 运行中的数据库 | **唯一事实** | 改代码必须过 `npm run verify` / `mvn compile` + 相应验收 |
| **P1** | Flyway 迁移脚本（`V7xx__*.sql`） | **表结构与种子数据的唯一事实** | 只许新增迁移，不许改已应用的 |
| **P2** | `docs/` 下的文档 | 解释性事实（"为什么"、"边界"） | 追 P0 |
| **P3** | `design/` 下的设计稿 | 视觉意图 | 追 P0 |

### 1.1 为什么代码是 P0，而不是文档

三条理由，都可验证：

1. **代码是唯一被真实执行过的。** 文档可以写一个不存在的能力（本仓库实测有：字号「影响全 App」、幂等「重复提交返回原结果」、案号「FAZE- 开头」），代码不会。**假承诺只能出现在文档和注释里，不能出现在运行时。**
2. **代码有强制门禁，文档没有。** `tsc --noEmit`、`eslint`、`check:rawtext`、`check:i18n`、`mvn compile`、79 个 JUnit 文件都会拦人。文档只有「人工审阅」这一道，实际等于没有。
3. **文档数量是代码的 1.5 倍且无测试。** 实测：文档 164 份 Markdown / `PAGE_ROUTES` 69 条产品路由 / Controller 78 个。文档规模已经大于它描述的对象，**靠人工保持同步在数学上不成立**。

### 1.2 P1 为什么单独一级

表结构的事实**既不在代码里也不在文档里**。代码里只有 entity 映射（会漏字段），文档里写的是设计意图（会过期）。唯一准确的是**已经执行过的迁移脚本**。

所以：**「表有几个字段」「枚举有几种值」这类问题，查 Flyway + `SHOW CREATE TABLE`，不查文档。**

## 二、三类不一致，三种处置（本规范的核心）

「不一致」不是一个东西，是三个。混在一张表里会互相稀释优先级——**这是上一版计划犯过的错**，必须分开。

### 2.1 DRIFT（漂移）—— 同一事物，说法不同

**判据**：该事物在代码里**存在**，且至少两方对它的描述矛盾。

**处置**：登记 `docs/facts/DRIFT.md`，逐条裁决。

**例子**：`profile.json` 的字号说明写「调整后会影响整个 App 的字号」，实际 `scaleTextStyle` 只被 `SettingsPage.tsx` 消费。事物存在（字号设置）、两方描述矛盾（承诺 vs 实现）。

### 2.2 GAP（缺口）—— 计划有，代码无

**判据**：文档或设计稿承诺了某个能力，**在代码里搜不到实现**。

**处置**：登记 `docs/facts/DEFERRED.md`（段八挂账汇总表）。**本轮不推进，不改代码。**

**例子**：真实钉钉群 webhook（`alert.dingtalk_webhook` 值为空串）、支付商户号、App 备案号、四语言人工译文。

> **GAP 为什么必须和 DRIFT 分开**：GAP 的处置是"先不管"，DRIFT 的处置是"现在就定谁改"。混在一起，GAP 会被误当成待修缺陷排进优先级，而 DRIFT 会被"反正是段八的事"拖延。
>
> 负责人 2026-11-10 明确：「这些只是我列举出来的，里面应该还有其他我没想到的……后面才弄」「碰到这些没做、但计划书上却有的内容，都是先不管的」。**所以 DEFERRED 表是"不管区"的容器，一次装完，而不是每次遇到就提一遍。**

### 2.3 DIRT（脏数据）—— 代码对，库里脏

**判据**：代码逻辑正确，但库里的行**违反代码自己的约束**。

**处置**：巡检 SQL（`scripts/monitor/`）+ 清理脚本。**不进 DRIFT。**

**例子**：`orders id=14` 状态 `completed`，但 `order_status_log` 0 行、`balance_flow` 0 行；而对照订单 5/16/27 分别有 4/1/4 行日志和 1 条收入流水。代码的 `LawyerOrderService.complete()` 是 `@Transactional` 且结算在同一事务内——**代码没漏，是有人手插了测试数据**。

> **DIRT 为什么不能进 DRIFT**：它不是"说法不一致"，是"数据不合规"。改成文档去描述脏数据，等于把缺陷写进法律。

### 2.4 三类对照表

| | DRIFT | GAP | DIRT |
|---|---|---|---|
| 现象 | 说法不一 | 说得有、实际没有 | 库里有不合法数据 |
| 判据 | 代码里**有**该事物 | 代码里**搜不到** | 代码**正确**，数据违规 |
| 登记处 | `docs/facts/DRIFT.md` | `docs/facts/DEFERRED.md` | `scripts/monitor/` 巡检 SQL |
| 本轮处置 | 立即裁决谁改 | **不动** | 巡检 + 清理 |
| 典型 | 字号承诺 | 真实钉钉群 | 订单 14 |

## 三、裁决规则

DRIFT 的每一条都要落一个处置。**规则按顺序判，第一条命中即停止。**

### 规则 1（默认）：改文档 / 改设计稿，去追代码

**代码是 P0。** 除非命中规则 2，一律改文档或设计稿。

### 规则 2（例外，改代码）：只有两种情况

**2a. 代码违反硬约束。** 硬约束指：
- 资金正确性（金额、流水、余额恒等式）
- 权限归属（越权能改别人的数据）
- 数据完整性（有读无写导致永远为空的字段、两处状态不一致）
- 本仓库已生效的明文规范（`AGENTS.md`、`docs/standards/`、ESLint 规则）
- 法律/合规要求

**2b. 代码有明确实现错误**，即：**注释或文档承诺的行为，与实现的代码相反**。
典型：注释写「重复提交返回原结果」，实现每次生成新幂等键。

> **2b 的判据要严格**：只是"实现得不好"不算，必须能被指认为「承诺 A、实现是 not A」。
> 理由是：代码是 P0，改代码就有回归风险；只有**代码自己都说了它要做 A** 的时候，改代码才是纠正而不是变更需求。

### 规则 3：GAP 一律不改代码

即使某 GAP 看起来"应该实现"，只要它属于 DEFERRED 表，本轮不改。理由见 §2.2。

### 规则 4：处置只允许 5 个值，禁止「待定」

| 值 | 含义 | 下一步 |
|---|---|---|
| `改文档` | 文档追代码 | 排进当前批次 |
| `改设计稿` | 设计稿追代码 | 排进当前批次 |
| `改代码` | 命中规则 2a 或 2b | 排进修复计划，附回归断言 |
| `待拍板` | 需要负责人决策，**必须写明要拍什么** | 列入待决清单 |
| `不处置` | 三方都对，只是没人讲清 | 补一句口径说明 |

**禁止写「待定」「后续再看」「视情况」。** 一行 DRIFT 卡在"待定"超过一轮，说明这条根本没查清。

### 3.1 判定顺序（照这个顺序问，别跳步）

```text
① 该事物在代码里存在吗？
   不存在 → GAP，去 DEFERRED，结束
   存在   → ②

② 库里的数据合规吗（符合代码自己的约束）？
   不合规 → DIRT，进巡检 SQL，结束
   合规   → ③

③ 代码违反硬约束（规则 2a 那五类）吗？
   违反 → 改代码，结束
   不违反 → ④

④ 代码的实现与它自己的注释/承诺相反吗？
   相反 → 改代码，结束
   不相反 → ⑤

⑤ 文档说错了 → 改文档
   设计稿说错了 → 改设计稿
   三方都对、只是没讲清 → 补口径说明（处置值填「不处置」但必须写清补哪句）
```

## 四、数字口径表

**下列数字一律以脚本输出为准，本表数字仅是 2026-11-10 的快照。** 人写的数字会静默过期。

复现命令：

```powershell
node scripts/facts/page-inventory.mjs
```

| 名称 | 值 | 构成 | 备注 |
|---|---|---|---|
| APP 产品页面 | **69** | `PAGE_ROUTES` 71 − 开发探测 2 | 文档与代码用的是这一个 |
| APP 路由常量 | **71** | 69 产品 + `devProbe` + `devRtl` | 含 2 个开发页 |
| 页面实现文件 | **71** | 69 产品 + 2 探测页 | `features/**/*Page.tsx` |
| 路由壳文件 | **72** | — | 已排除 3 个 `_layout` + 1 个 `+not-found` |
| 设计稿主屏 | **68** | `design/ui` 71 − 补充屏 3 | |
| 设计稿 HTML 总数 | **71** | 68 主屏 + 3 补充屏 | 补充屏 = `07b` / `07c` / `41b`，是弹层不是页面 |
| PC 后台屏数 | **28** | `design/admin/*.html` | **与 APP 是两套口径，不相加** |

### 4.1 口径规则

1. **说「APP 有多少页」时，必须说产品页面数（69），并注明是否含无设计稿的实现页。**
2. **说「设计稿多少屏」时，必须说主屏（68），补充屏单列。** 弹层不是页面。
3. **APP 与 PC 的数字禁止相加**（69 + 28 ≠ 97 个页面，是两个终端的两套口径）。
4. **新增任何「有多少个 X」的数字，先问"能用脚本数吗"。** 能，就写脚本并引用脚本；不能，必须写明数法与截止日期。

## 五、登记规则

### 5.1 DRIFT 表（`docs/facts/DRIFT.md`）

| 项 | 规则 |
|---|---|
| ID | `DRIFT-NNN`，三位数，**永不复用**（删掉的也留号） |
| 粒度 | **一行一条事实**。一条 DRIFT 里混两件事就是没查清 |
| 必填 | 事实 / 代码实际 / 另一方说法 / 谁该改 / 处置 / 证据 |
| 证据 | 必须写**文件:行号** 或**命令输出**。写「已确认」不算证据 |
| 证据强度 | `实测`（真跑过）/ `通读`（读过代码但没跑）/ `待复核` |
| 状态 | 只有 `开` / `关`。关闭时必须写清在哪次提交关闭 |
| 每轮上限 | 新增 **≤3 行**。超过 3 行说明当轮改动引入了成批新分叉，应停下来先修机制 |

### 5.2 DEFERRED 表（`docs/facts/DEFERRED.md`）

| 项 | 规则 |
|---|---|
| ID | `DEF-NNN` |
| **本表不是待办清单** | 它是**真相声明**：「这条确实没有，别再当成有了」 |
| 不设期限 | 设了期限就会变成承诺，而承诺需要负责人拍板 |
| 必须指向原文 | 每条都要给出既有挂账文件的出处，不复制原文（避免第三份副本） |
| 关闭条件 | 只有负责人明确说"这条做了"才移出 |

### 5.3 谁能改

- **任何 agent / 开发者**可以**新增** DRIFT 行和 DEFERRED 行。
- **关闭** DRIFT 行必须在同一提交里给出关闭证据。
- **删除**任何一行需要说明理由，且 ID 不复用。
- **改处置值**（如 `待拍板` → `改代码`）属于裁决变更，必须在 `CHANGELOG.md` 写明是谁拍的、依据是什么。

## 六、与既有制度的关系

**本规范不新建任何并行制度。** 仓库里已有的制度继续有效，本规范只补三个缺口。

| 既有制度 | 位置 | 本规范的关系 |
|---|---|---|
| 文档基线 | `docs/BASELINE.md` §四 | `docs/facts/*.md` 是**新增基线资产**，按四件事办（落款 / 指纹 / 索引 / CHANGELOG） |
| 变更日志 | `docs/CHANGELOG.md` | 裁决变更必须在这里留痕 |
| 各段挂账 | `docs/acceptance/seg{4,6,7}/挂账.md`、`docs/ops/运维手册.md` §七 | **继续是各段挂账的第一现场**。`DEFERRED.md` 只做**汇总索引**，指向它们，不取代 |
| 段串行约束 | `AGENTS.md` §4.14、总纲 | **本规范是横切工程约束，不占段位。** 它不改变第 0~8 段的顺序与边界 |
| 后端规范 §十四 | 《后端代码规范》 | 承接手段的写法照它（「谁在拦」） |
| 设计令牌三处同步 | `AGENTS.md` §4.13 | 属 DRIFT 已覆盖的一类（令牌与文档不同步就是漂移） |

### 6.1 为什么不把各段挂账合并进来

因为**合并会产生第二份副本，而第二份副本必然先腐坏**。这是本仓库已经验证过的模式：设计稿与代码各一份页面清单，结果两边都对不上。

`DEFERRED.md` 的行**只有三个字段**：ID / 一句话 / 出处链接。原文永远只在原文件里。

## 七、承接手段（谁在拦）

照《后端代码规范》§十四的体例：**答不上「谁在拦」的规则不该写。**

| 规则 | 承接手段 | 现状 |
|---|---|---|
| §一 真相源分级 | 本规范本身 + PR 模板问一句「这条改的是 P0 还是 P2」 | **待建**（G8） |
| §二 三类分开 | `DRIFT.md` / `DEFERRED.md` / 巡检 SQL 三个不同入口 | **本规范建立** |
| §三 处置 5 值、禁"待定" | 脚本检查 DRIFT 表的处置列取值白名单 | **待建**（G8） |
| §四 数字必须机器算 | `scripts/facts/page-inventory.mjs`；后续 `scripts/facts/*` 全部纳入 CI | **脚本已建，CI 待接**（G2） |
| §五 每轮新增 ≤3 行 | 人工核对，记在 CHANGELOG | 人工 |
| §六 不新建并行制度 | 本规范的 §六 表本身就是清单 | 人工 |

> **诚实说明**：截至本规范建立，**上表只有两条真正有东西在拦**（§二 的三个入口、§四 的脚本）。其余是"写下了但还没人守"。
> 这与《后端代码规范》§十四 的做法一致——**先登记"谁在拦"，没拦住的就标出来**，而不是假装已经管住了。

## 八、本规范不做什么

1. **不管「功能该不该做」**。那是总纲和各段工作流的事。
2. **不管设计风格**。设计稿怎么画不归本规范。
3. **不建立新的事实来源**。P0 就是代码和数据库，本规范不产生第三种事实。
4. **不要求历史上所有不一致立刻清干净**。要求的是：**已知的必须在表里有一行**。没进表的不算"没有不一致"，算"未发现"。
