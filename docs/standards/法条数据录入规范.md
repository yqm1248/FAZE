# 法条数据录入规范 v1.0

> 适用：所有往 `law_item`（本地法条库）写数据的场合——Flyway 迁移、PC 后台 A-27 批量导入、运维直接 SQL。
> 依据：《第 3 段工作流》A3；《数据表规范》§8.4；《技术路线》§11.6.1。
> 一句话：**法条是版本资产，不是种子数据。错一个字，AI 就会照着错字回答。**

---

## 一、三条硬要求

### ① 逐字准确

- 条文必须从**权威文本**抄录，不许自己编、不许改写、不许精简、不许合并条款。
- 权威来源（按优先级）：
  1. 国家法律法规数据库（`flk.npc.gov.cn`）官方文本
  2. 全国人大及其常委会公报
  3. 最高人民法院 / 最高人民检察院官方发布
- **禁止**来源：法律资讯网站、律师博客、AI 生成内容、二手汇编。
- `effective_date` **必填**：它是唯一键 `uk_law_article(law_code, article_no, effective_date)` 的组成部分，漏填会直接报错（这是设计意图，不是 bug）。
- 同一个条文的**不同版本是不同行**：修订后用新 `effective_date` 再插一行，旧行改 `status='amended'` 或留 `expire_date`，**不要 UPDATE 覆盖旧行**——旧回答的 `refs` 快照要靠旧行才能复核。

### ② `article_no` 与 `article_seq` 都要填

| 字段 | 内容 | 用途 |
|---|---|---|
| `article_no` | 人读的中文条号，如 `第六百七十九条` | 展示给用户、`ArticleNoValidator` 回查、`refs` 快照 |
| `article_seq` | 整数序号，如 `679` | 排序、范围查询、中文数字转换结果的比对基准 |

两者的换算关系必须成立：`ChineseNumberUtil.toArabic(article_no) == article_seq`。
**不许**只填一个：只填 `article_no` 排不了序，只填 `article_seq` 用户看不到条号。

### ③ `law_code` 用小写短码

首批 6 部法（与技术路线 §11.6.1 一一对应）：

| `law_code` | 法律全称 | `law_name` 必须逐字写成 |
|---|---|---|
| `civil_code` | 中华人民共和国民法典 | 中华人民共和国民法典 |
| `civil_procedure` | 中华人民共和国民事诉讼法 | 中华人民共和国民事诉讼法 |
| `labor_contract` | 中华人民共和国劳动合同法 | 中华人民共和国劳动合同法 |
| `labor_dispute` | 中华人民共和国劳动争议调解仲裁法 | 中华人民共和国劳动争议调解仲裁法 |
| `consumer_protection` | 中华人民共和国消费者权益保护法 | 中华人民共和国消费者权益保护法 |
| `marriage_judicial_1` | 最高人民法院关于适用《中华人民共和国民法典》婚姻家庭编的解释（一） | 最高人民法院关于适用《中华人民共和国民法典》婚姻家庭编的解释（一） |

- 新增法律只有一件事要做：在**本表**登记 `law_code` + `law_name`，再插 `law_item`。**不许**临时造短码（同一部法两种写法会让「按法律名归属条号」的校验失效）。
- `law_name` 里带书名号《》的司法解释，`law_name` **保留书名号**；`ArticleNoValidator` 的包容匹配已能处理「用户写《民法典》、库里写全称」的情况。

## 二、两条路的边界（这条最容易搞错）

| 场景 | 走什么 | 谁做 | 为什么 |
|---|---|---|---|
| **首批法条**（随版本发布） | Flyway 迁移 `V302__import_law_items.sql` | 段 3 建模板；负责人提供内容 | 法条是版本资产，要与代码版本一一对应 |
| **运营期新增法条**（负责人以后自己加 10 条、200 条、2000 条） | ① PC 后台 A-27「批量导入」接口（H1）<br>② 或直接 SQL 插 | 负责人 | **不要为新数据发一个迁移** |
| 演示 / 测试数据 | `database/seed/` | 各段 | 与真实法条隔离 |

**为什么运营期数据不能走 Flyway**：Flyway 是应用启动时自动执行的。每次加 10 条法条就发一个版本不现实；而且 Flyway 迁移**一旦执行就不可回改**（`validate-on-migrate: true`），录错了只能再写一个补丁迁移——运营数据录错是常态，这条路走不通。

**同理，演示/测试法条不许进 `V302`**：seed 里可以有假法条（如「第一条 测试条文」），但一旦进 Flyway 就会跟着版本发到生产。段 0 已把 5 条真实法条放 `V2`，段 3 的 `V302` 只放真实条文。

## 三、写入写法（模板）

```sql
INSERT INTO law_item
  (law_code, law_name, article_no, article_seq, content, effective_date, expire_date,
   status, keywords, is_enabled, created_by, created_by_type, created_at, updated_at)
VALUES
  ('civil_code', '中华人民共和国民法典', '第六百七十九条', 679,
   '自然人之间的借款合同，自贷款人提供借款时成立。',
   '2021-01-01', NULL,
   'active', '借款合同,自然人借款,合同成立,交付', 1, NULL, 'system', UTC_TIMESTAMP(), UTC_TIMESTAMP())
ON DUPLICATE KEY UPDATE
  law_name = VALUES(law_name), article_seq = VALUES(article_seq), content = VALUES(content),
  status = VALUES(status), keywords = VALUES(keywords), is_enabled = VALUES(is_enabled),
  updated_at = VALUES(updated_at);
```

要点：

1. **必须 `ON DUPLICATE KEY UPDATE`**：靠 `uk_law_article` 去重，重复执行不报错、不重复插入。
2. `expire_date` 为 `NULL` 表示现行有效；失效条文填失效日期，**不要删行**（删了旧 `refs` 就查不回原文）。
3. `status` 只有三值：`active` / `amended` / `repealed`。**没有「待校对」**——校对状态不进 DDL（《第 3 段工作流》§零.3 第 8 项）。
4. `is_enabled` 默认 1。停用一律走 PC A-27 的「停用」动作（改 `is_enabled=0`），**不要 DELETE**。
5. `created_by` / `created_by_type`：Flyway 导入填 `NULL` / `'system'`；后台导入填管理员 `sys_user.id` / `'admin'`。
6. `keywords` 是人工维护的**同义词短词**（逗号分隔，不要空格），检索时作为「同义词扩展」的输入。**不要**把它当正文塞长句。

## 四、录入前核对清单（逐条打勾再提交）

- [ ] 条文原文与权威来源**逐字一致**（含标点），已比对两处以上来源
- [ ] `article_no` 中文条号与 `article_seq` 整数**能互换**（用 `ChineseNumberUtil` 或手工核对）
- [ ] `law_code` 在本规范第一节的 6 个短码内（或已登记新增）
- [ ] `law_name` 使用法律全称，与 `law_code` 对应
- [ ] `effective_date` 已填，且为该版本实际施行日
- [ ] `keywords` 逗号分隔、无空格、含至少 2 个用户可能用的口语词
- [ ] 已在本地库执行一次，`SELECT COUNT(*)` 与预期一致
- [ ] 重复执行一次**不报错、不重复插入**
- [ ] 导入后能用 2 个关键词检索到（`GET /api/v1/pub/law-items?kw=…`）
- [ ] 导入后条号能被 `ArticleNoValidator` 判为存在

## 五、常见错误与后果

| 错误 | 后果 | 怎么发现 |
|---|---|---|
| 条文自己精简了几个字 | AI 照着简版回答，专业性与准确性下降，且无法追溯 | 逐字比对；`3-A2` 黄金题会暴露 |
| 只填 `article_seq` 不填 `article_no` | 条号精确检索与存在性校验全部失效 | `ArticleNoValidator` 单测 |
| `article_no` 用了阿拉伯数字（`第679条`） | 与库里中文条号对不上，精确路径命中 0 | 用 `第[零一二三四五六七八九十百千0-9]+条` 正则核对 |
| `effective_date` 漏填 | 唯一键报错，迁移失败 | 迁移执行时立即失败 |
| 同一部法两种 `law_code` | 按法律名归属条号时一半查不到 | `SELECT DISTINCT law_code` 核对 |
| UPDATE 覆盖旧版本条文 | 旧回答的 `refs` 快照与现行条文错位 | **禁止**；只能新插一行 |
