## 二、页面数：26，不是 27

**必须先把这件事说清楚，因为《PC 后台开发计划_v1.0》里写的是 27。**

实际是 **26 页**。开发计划 §2 的七个分类加起来是 3+3+4+3+5+2+6 = **26**，页面编号到 A-26 为止；§2.8 的「合计 27」是算术写错了，「为什么是 27 而不是 24」那句话也建立在这个错误上。

正确的说法是：**技术路线 §15.1 列了 9 个模块，本计划按它们排出 24 页；另补「案件管理」「内容审核队列」两页（§15.1 没有，但分期交付计划第 5、7 段的验收要求），合计 26 页。**

开发计划与本文档同步改为 26；技术路线 §15.1 没有错，错在开发计划的加法。

## 三、设计系统

### 3.1 四个文件各管什么

| 文件 | 管什么 | 改动影响 |
|---|---|---|
| `tokens.css` | 颜色、字号、间距、圆角、阴影、骨架常量 | 26 屏一起变 |
| `components.css` | 骨架与组件样式（表格、查询栏、标签、抽屉…） | 用到该组件的所有屏 |
| `shell.js` | 侧边栏 / 顶栏 / 标签页的 HTML 结构与菜单数据 | 26 屏的导航一起变 |
| 各屏 `<style>` | 只写这一屏特有的样式，类名用「页面名__块名」 | 只影响该屏 |

**规则**：页面里不出现任何 `#RRGGBB`、`rgba()`、`hsl()` 字面量，也不出现 4/8 倍数以外的间距。

### 3.2 颜色：继承 APP，但有三处必须派生

底色、状态色、品牌色全部与 `design/ui/tokens.css`（APP）同名同值。但有三个地方**直接沿用会在后台的浅底上掉到无障碍线以下**，所以派生：

| 派生变量 | 值 | 为什么 | 实测对比度 |
|---|---|---|---|
| `--brand-text` | `#3d57d8` | `--brand-primary`(#4a66ee) 当文字压在 `--brand-primary-soft`(#eef2ff) 上只有 **4.24:1**，不到 4.5 | 5.28:1（对 #eef2ff）、6.1:1（对白） |
| `--brand-on-dark` | `#b9c2fa` | 深色侧板/侧边栏上 `#eef2ff` 几乎等于白色，看不出是品牌色 | 9.05:1（对 #22283a） |
| `--state-danger-deep` | `#cc0a20` | `--state-danger`(#ee0a24) 当文字压在 `#fdecee` 上只有 **3.91:1** | 5.07:1 |

**使用规则**（写进 `_SPEC.md`，后续加屏必须遵守）：

- 背景、边框、图表线 → `--brand-primary`
- 品牌色**文字** → `--brand-text`
- 表格里的次级文字 → `--text-secondary`(#666)，**不用** `--text-muted`(#6b7280)：后者压在选中行底色 `--bg-selected`(#eef2ff) 上只有 4.32:1
- 深色底上的品牌色文字 → `--brand-on-dark`

### 3.3 骨架：四个值不能动，一个值可以压

RuoYi-Vue3 框架层写死的四个值，设计稿必须贴着，否则落不了地：

| 项 | 值 | 来源 |
|---|---|---|
| 侧边栏宽 | 200px | `$base-sidebar-width` |
| 顶栏高 | 50px | `.navbar` |
| 标签页高 | 34px | TagsView |
| 内容区 padding | 20px | `.app-container` |

**唯一改动的是菜单项高度**：RuoYi 默认一级 56px / 子项 50px，而本后台一级菜单有 **11 组**（数据看板、用户管理、律师管理、订单管理、财务管理、内容管理、案件管理、投诉工单、消息管理、系统设置、系统管理），按默认高度 900 画布装不下会出滚动条。

收到 **一级 50px / 子项 46px** 后：11×50 + 4×46 + logo 50 + 底部 56 = 840 < 900，刚好。

这是通过 CSS 变量覆盖（`--el-menu-item-height` 一类）实现的，**不改框架源码**，属于 AGENTS.md §3.3 允许的「配置覆盖」。若开发时发现该变量在 3.8.7 里改不动，退路是接受侧边栏滚动（RuoYi 默认行为就是这样）。

### 3.4 字号与控件刻度：比 APP 紧一档

| 项 | APP | PC 后台 | 理由 |
|---|---|---|---|
| 正文字号 | 15px | 14px | 后台一屏要装 10 行表格 + 查询 + 分页，15px 会撑爆 |
| 表格行高 | — | 48px | Element Plus 默认 40 太挤，状态标签和两行单元格需要 48 |
| 控件高度 | 44px 起 | 32px（小 28） | 桌面端鼠标点击，不需要 44；对齐 EP default 尺寸 |
| 圆角 | 12–16px 为主 | 卡片 8 / 控件 4 | 后台比 APP 方，信息密度优先 |

### 3.5 为什么侧边栏/顶栏用 JS 注入而不是每屏复制

APP 的 68 屏是每屏复制一份 tabbar 的——因为底部 tabbar 只有 4 项、约 50 行，复制可接受。

后台不适用：侧边栏是 11 组菜单 + 二三级子项，约 130 行 HTML，**26 屏复制 = 3400 行重复**，改一次菜单要改 26 个文件，必然分叉。

所以抽出 `shell.js`：页面只写一行 `<body class="shell" data-page="02-user-list">`，脚本按 `PAGES` 表注入骨架——决定菜单高亮哪一项、面包屑、标签页。

**代价**：设计稿依赖 JS 才能完整显示，且 `data-page` 写错会导致侧边栏不高亮（不会报错，会静默不显示）。所以 `_SPEC.md` 里把「`data-page` 必须等于文件名」列为第一条硬约束。

**真实项目不需要这个文件**：RuoYi 用 `permission.js` + 动态路由生成菜单。

## 四、26 屏抽象成 7 类页面范式

26 屏不是 26 种设计，是 **7 类范式的组合**。这一节是给开发看的：写 Vue 页面时，先判断属于哪一类，套对应范式。

| 范式 | 数量 | 屏 | 结构 |
|---|---|---|---|
| **A. 列表页（母版）** | 10 | 02、05、06、09、10、12、13、15、17、20、23、25 | 页头 → 查询栏 → 工具栏 → 表格（10 行）→ 分页 |
| **B. 审核分栏页** | 3 | 03、04、19 | 左 380px 队列 + 右详情，左右各自滚动，底部操作条 |
| **C. 详情页** | 2 | 11、21 | 左主区（信息/记录/回复）+ 右 340px 属性栏 |
| **D. 表单页** | 3 | 07、14、22 | 分组卡片 + 表单网格 + 底部保存栏 |
| **E. 看板** | 1 | 01 | 4 统计卡 → 图表行 → 待办/最近订单行 |
| **F. 登录** | 1 | 00 | 左品牌板 + 右表单，无骨架 |
| **G. 主从分栏（非审核）** | 2 | 16、24 | 左主表 + 右窄栏（术语表 / 申诉复核） |

**母版是 `02-user-list.html`**。A 类 12 屏全部由它派生，改它的间距 = 改 12 屏。这一点在 `_SPEC.md` 里写死了。

## 七、已知局限

1. **没有做深色模式**。RuoYi 的 `theme-dark` 只影响菜单，页面主体只做浅色，这是开发计划 §七 的既定范围。
2. **没有做移动适配**。1440 固定，后台是桌面工具。
3. **示例数据不是真数据**。人名、订单号、金额、法条条号全部是示意；法条条号取了真实值但**民诉法按 2021 修正版编号，需法务复核**。
4. **多语言是标注不是翻译**。设计稿只做简体中文，藏/维/哈文一律写「待填」，没有编造。
5. **交互只有静态形态**。抽屉、弹窗、驳回理由弹窗在 `components.css` 里有样式，但设计稿里只画了主状态，没有画每个覆盖层。

## 八、这份文档的变更规则

1. **页面编号（A-01 ~ A-26）一旦分配不改**。新增页面往后排（A-27 起）。
2. **改设计系统（tokens/components/shell.js）必须同时改本文件 §3**，并说明影响了哪些屏。
3. **新增一屏必须**：在 `shell.js` 的 `PAGES` 登记 → 在 `_SPEC.md` §5 自查 → 在本文件 §5 补一行 → `docs/BASELINE.md` 重算指纹。
4. **与《PC 后台开发计划》冲突时**：先确认哪个对（本文档负责「长什么样」，开发计划负责「先做哪个」），改错的那一份，不允许两份都留着。
