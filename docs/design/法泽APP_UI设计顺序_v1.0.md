# 法泽 FAZE · APP UI 设计顺序（V2.4）

> **这份文档解决什么**：68 个页面**按什么顺序设计**，每批的锚点在哪，复刻与延展怎么分；
> 以及导航树里 21 个**浮层**（非独立页面）和**页面四态 / 多语言**什么时候做。
>
> **设计原则（项目负责人 2026-10-29 明确）**：
> 1. **风格按原项目那一套复刻**，不重新设计。版式、配色、信息密度、文案都向原项目靠。
> 2. **图标不复刻**：原项目是 24px 位图标，高分屏发虚。改成一整套线性 SVG，但**保留原项目的青 / 蓝 / 橙三色**。
> 3. **图片不复刻**：头像、律师照片、文章封面一律用占位。律师头像将来由律师自己上传。
> 4. **先 APP，平台（PC 管理后台）最后做**。
>

### 3.3 文件命名规则

```text
页面    NN-名称.html        01-home.html
浮层    NNb-名称.html       07b-privacy-prompt.html   同页第 1 个浮层
        NNc-名称.html       07c-language-picker.html  同页第 2 个浮层
```

浮层排在**宿主页之后、下一个页面之前**，保证画布顺序 = 实际使用顺序。

**本批最重要的事不是版式，是把「平台不是法院」这条边界在 UI 上说清楚。**

案件中心四页里有三页天然带司法权色彩：立案、立案成功、送达。而平台是商业性法律服务
机构，不是司法机关 —— 《民事诉讼法》上的「立案」是法院对起诉材料审查后决定受理的
司法行为，「送达」是法院（或法院委托）把文书送交当事人的法定程序。一个 App 若在界面上
宣称「已立案」「本院已受理」「平台向你送达」，轻则虚假宣传，重则冒用司法机关名义。

处理方式（四屏统一，后续改文案不能退回去）：

| 位置 | 不能写 | 本批怎么写 |
|---|---|---|

**执行后回写的决策**（六屏，全部无参考图，下面每一条都是当场做的判断）：

- **★★★ 支付方式取余额制，与导航树冲突，取 AGENTS.md ★★★**
  导航树 v1.4 模块 7 写的是「支付方式：微信支付 / 支付宝」，那是把钱直接付给平台。
  但仓库规则 AGENTS.md v2.0（2026-10-27 定位改「真实上线」时定）是**余额制**：
  「界面展示账户余额，充值走微信 / 支付宝，消费用余额抵扣」。两者不能同时成立 ——
  余额制下用户付款时钱已经在自己账户里，收银台只有「余额」一个选项。
  **按 AGENTS.md 画**（优先级高于设计文档，且 v2.0 晚于导航树 v1.4）。
  后果：31-pay 只有「账户余额」一种支付方式，余额不足时按钮变「去充值」。
  最初把充值做成 31 的页内浮层（因为不给它单开一屏），v1.9 补了独立充值页 36 之后
  浮层**删掉**改为跳转 —— 同一件事摆两套界面，早晚分叉。
  **导航树模块 7 已按余额制改完**（v1.4 → v1.5），不再是待确认项。

- **金额排版立成一套组件（`.money*`，`components.css` 第 20 段）**，三条规矩：
  整数分传入、千分位 + 两位小数（`¥1,280.00`，不写「1280元」也不写「¥1280」）、
  等宽数字（`tabular-nums`）。缺小数位会让人怀疑还有尾数；不等宽上下就对不齐。
  展示级金额用新增令牌 `--fs-display: 34px`，只这一处用途。

- **金额不做颜色区分**。优惠与实付都不上色，只用减号前缀和 label 文字表达。
  理由：`--state-danger` 已经绑定了「删除 / 退出 / 风险操作」的语义，
  再拿它画优惠红字，会让「−¥50.00」和「删除账号」看起来是同一类警告。
  信息靠文案传递不靠颜色，对色弱用户也更稳。

- **退款金额只读，不让用户填**。让用户填金额等于请他填错，然后被驳回一次，

  不收进来，用户点「进行中」会看不到那单，以为它消失了。

  待支付 → 倒计时 +「取消订单 / 立即支付」；进行中 →「申请退款 / 联系律师」；

  `_walkthrough/29-34-orders.html`。

  最初只有二次确认框（列明扣多少 / 从哪扣 / 扣完剩多少），v1.9 补了支付密码之后
  确认框**删掉**了 —— 输密码本身就是在确认。再套一层，用户点三次才能付出去，
  点多了就会闭眼点，确认反而失去意义。

  底部按钮文案带金额（「确认支付 ¥99.00」），误点的成本一眼可见。
  余额不足态（`#state-low`）边框走警示色但整块不标红：差一点不是失败。

- **32 支付结果页最有价值的一行是「支付前余额 → 支付后余额」**。
  余额制的可疑点全在余额上。两个数并排，对得上就不用找客服。
  标题只写「支付成功」，不写「服务已开始」—— 付钱和服务生效是两件事，
  律师没接单时用户会以为平台赖账，所以下面单独一句交代「2 小时内联系你」。
  失败态第一句必须是「钱没被扣」，看到红叉的人第一个念头是钱去哪了。

  标签多选、文字选填，只有星级必填 —— 要求写满多少字，大多数人直接关掉。
  不出现任何「好评返现」「评价得积分」类引导：有对价的评价不是评价，是交易。

和平台服务费不是一回事，混在一段灰字里会被读成免责小字。
33 页的退款规则里，这一句也要单独加粗：用户投诉最多的就是「以为退款能连诉讼费一起退」。

**为什么补这三页（v1.9，项目负责人 2026-10-29 确认要补）**

定下余额制之后，导航树 v1.4 的 6 页只覆盖了「怎么买东西」，没有覆盖「钱本身」。
三页分别补三个缺口，每一条都是「不做就出事」：

| 新页 | 缺了会怎样 |
|---|---|
| 35 账户余额与明细 | 用户发现余额少了 99，**没有任何地方能查**，唯一出路是打客服电话。一个人问一次，客服成本就超过这单利润 |
| 36 充值页 | 余额制没有充值页，就**充不进去**，整个消费链路是断的 |
| 37 支付密码 | 余额是「已经充进来的钱」。没有支付密码，手机被别人拿起来的十几秒里就能花掉 —— 而花掉是消费不是转账，事后追不回来。登录密码挡的是「登不进账号」，挡不住「已经登录的人继续花余额」 |

三条连带改动：
1. **31-pay 的充值浮层删掉**，两个「去充值」入口直接跳 36 —— 同一件事两套界面早晚分叉。

  （提交 / 审查 / 立案 / 开庭 / 判决 / 执行）。

- **六段里有五段不归平台管，但边界只说一次。** 在「平台动作结束、法院动作开始」

### 6.1 每屏必须交付四态

导航树「全局约定」把四态列为**硬要求**，不是可选：

| 状态 | 必须有的东西 |
|---|---|
| 正常 | 数据齐全的样子 |
| 加载中 | 骨架屏（首次进入）或顶部 loading（下拉刷新） |
| 空状态 | 空状态图形 + 引导文案 + 一个可点的下一步 |
| 错误 | 错误说明 + 重试按钮（含断网） |

> **怎么交付才不爆炸**：不要求每屏写 4 个 HTML。做法是——
> **列表页与详情页**：在同一个 HTML 里用 `<section data-state="loading|empty|error">` 把结构标出来，
> 画布上默认只看正常态，但源码里四态的结构必须存在；
> **需要集中走查四态时**，另建一个 `_xxx-states.html`（下划线开头，**不上画布、不计入交付屏**），
> 把四种状态并排摆出来看，走查完就留着当参考。
>
> **列表页额外要求**：下拉刷新、上拉分页、骨架屏、空状态、加载失败重试 —— 这五项在列表屏里必须都能看到入口。
>
> 四态的具体开关：`app.js` 读 URL hash 的 `#state-loading` / `#state-empty` / `#state-error`，
> 所以每屏的四态都能单独打开验证，不需要为每个状态复制一份 HTML。

### 6.1.3 服务器与两个踩过的坑

**服务器**：用 `python scripts/serve-design.py`，**不要**用 `python -m http.server`。

后者不发 `Cache-Control`，浏览器按启发式规则缓存，改完文件刷新看不到变化。
第 4 批为此卡了两次：改了三处间距，项目负责人那边看到的还是旧版，
一度以为改动没生效，实际是浏览器拿了缓存，最后被迫手动加 `?v=N` 破缓存。

新脚本给所有响应加 `no-store`，并修正 `woff2` 的 MIME（原来是 `application/octet-stream`）。

```bash
python scripts/serve-design.py            # 默认 127.0.0.1:8123，服务 design/ui
python scripts/serve-design.py --verbose  # 需要看访问日志时
```

**坑 1：卡片间距加错层（第 4 批踩了两次）**

多卡片屏的 DOM 是三层：

```
main.screen
  └── div[data-state="normal"]     ← 卡片的真正父容器
        └── section.card ×N
```

`gap` 必须加在 `[data-state]` 上。加在 `.screen` 上**不生效也不报错** ——
因为 `.screen` 只有一个子元素，gap 没有东西可作用。表现就是「间距改了但没变化」。

```css
.screen > [data-state] {
  display: flex;
  flex-direction: column;
  gap: var(--sp-xl);
}
```

**坑 2：走查浮层的 hash 开关位置（第 5 批踩了）**

`app.js` 里 `#open-xxx` 这类开关必须写在对应变量赋值**之后**。
函数声明会提升，但 `var clearMask = document.querySelector(...)` 不会 ——
开关写早了，调用时变量还是 `undefined`，浮层打不开且没有任何报错。

### 6.1.4 中文换行产生的多余空格（第 6 批发现，全仓库清了一遍）

HTML 会把源码里的换行 + 缩进折叠成**一个空格**。中文正文本来没有词间空格，
所以只要一个句子在源码里换了行，渲染出来就多一个空格：

```html
<!-- 源码 -->
<p>
  这个数通常比你
  实际收入低，所以能举证就别偷懒。
</p>

<!-- 渲染：这个数通常比你 实际收入低，所以能举证就别偷懒。 -->
```

第 6 批做案例详情时第一版就是这么写的，走查截图里「比你 实际收入低」一眼能看出来。
逐句读很容易漏，所以写了个检查脚本：

```bash
python scripts/check-cjk-wrap.py                    # 查 design/ui 全部
python scripts/check-cjk-wrap.py design/ui/x.html   # 查单文件
```

脚本只看 `<body>` 之后、且不在 `<!-- -->` 注释内的行；判定条件是
「本行去尾空白后以中文/中文标点结尾」且「下一行去头空白后以中文/中文标点开头」。
退出码非 0 表示有问题。

**第 6 批一次性清了 8 个已交付文件的 55 处**（07b / 10 / 11 / 13 / 14 / 16 / 17 / 22）——
说明这个缺陷从第 2 批就存在，只是长文页每行字数多、单处空格不显眼，一直没被发现。
修法是把两行接成一行（不删任何字），已全部复核。

**不自动判定的两种情况**（可能是正确的）：
- 行尾是 `>`、行首是中文：多半是块级元素开头（浏览器会 strip 前导空白），
  也可能是中文接数字（那本来就该留空格）
- 行尾是中文、行首是 `<`：行内标签换行确实也会多空格，但要看标签内首字是不是中文，
  误报率高，交给人工判断

### 6.1.5 画布一次只挂 24 屏（第 8 批实测）

设计工作台的 `preview_page` 一次最多挂 **24 个 routes**，超出的**静默丢弃**——
不报错、不提示。第 8 批挂 30 个时，实际只加载了前 24 个，导致最后 4 屏

| 传入 screens | 画布实际挂载 |
|---|---|

| 26 项 | 只上前 24 项 |
| 30 项 | 只上前 24 项 |

### 6.4 金额符号别用纯 `em`（第 9 批走查发现）

`.money__sym` 第一版写的是 `font-size: 0.72em`。想法是「符号比数字小一档」，
比例挂在父级字号上，改一处全站生效。走查一量，**两端同时失控**：

| 上下文 | 父级字号 | 0.72em 实际渲染 | 后果 |
|---|---|---|---|
| 余额说明里的小金额 | 12px | **8.6px** | 太小，被判「字太小」（阈值 10px） |
| 支付页的展示金额 | 34px | **24.5px** | 太大，¥ 和数字一样重，整块头重脚轻 |

根因是 `em` 相对**父级**字号换算：父级一变大变小，符号跟着线性放大。
而「顺眼的符号比例」不是线性的 —— 小字要相对大一点才看得清，
大字要相对小一点才不抢戏。一条线性比例满足不了两端。

改法是用 `clamp()` 夹住，**上下限都取令牌里已有的字号档位**：

```css
.money__sym { font-size: clamp(10px, 0.6em, 17px); }
```

- 下限 10：落在 `--fs-micro`(11) 与 `--fs-caption`(12) 之间，是「再小就读不清」的底线
- 上限 17：正好是 `--fs-h2` 那一档，不引入新数值
- 中间 0.6em：正文金额（14~15px）时落在 8.4~9，被下限抬到 10，视觉不变

不取 18 而取 17 还有个副作用是好的：一屏里的字号档位不因为金额符号
多出一两个零星值，`check_design` 的「字号太杂」也就少一条噪音。

**同类教训**：凡是用 `em` 表达「比父级大一点 / 小一点」的装饰性文字
（符号、单位、角标），都要想一下父级字号会不会跨档跳变。
跨了就得上 `clamp()`。

### 6.5 `check_design` 的尺寸口径：设计稿固定 390，别用 375 量

设计稿的 `body` 是 `width: 390px; height: 844px`（`tokens.css` 里写死的画幅）。
用 `sizes: ["375x667"]` 量，**每一屏**都会报三条：

```
超出屏幕：header.statusbar — 伸出屏幕 15px
超出屏幕：div.navbar — 伸出屏幕 15px
超出屏幕：main.screen — 伸出屏幕 15px
```

390 − 375 = 15，就是这个数。这不是布局坏了，是画幅和测量窗口不匹配。
第 9 批用 375 量出 22 条，全部是这一类；拿 27-doc-mine、19-case-detail 两个老屏
同样的尺寸量，报的是一模一样的三条，可证明与批次无关。

所以：
- **默认用设计尺寸（390×844）量**，那才是这份设计稿的基准
- 真要验小屏，得先把画幅改成响应式（`width: 100%; max-width: 390px`），
  但那样画布上拖宽拖窄都会变形，不适合定稿设计
- 小屏适配本来就该在 RN 侧用 flex 做，设计稿只提供 390 的视觉基准

顺带记一条同类噪音：滚动容器（`.screen { overflow-y: auto }`）里的元素
被和 `.actionbar` 一起判「叠 Npx」，也是量法问题 —— 19-case-detail、
26-doc-preview 都报过，30-order-detail 也报了 21px。
用 `look_design at=bottom` 滚到底看一眼就能证伪：内容完整可见，底栏不压东西。

## 七、多语言与 RTL（项目负责人 2026-10-29 定：设计阶段不做）

**结论：设计稿只出简体中文版。多语言文案与 RTL 布局放到代码层实现。**

这个方案作废 —— 项目负责人明确说不需要现在做，到时候去代码层面实现。

就能暴露，比在设计稿里用占位文本模拟准得多。

### 7.1 设计阶段仍然保留的三件事

这三件都**不是**「做多语言」，是零成本的防返工：

| 保留 | 为什么不是多语言工作 | 状态 |
|---|---|---|
| **逻辑属性**（`margin-inline-start` / `padding-inline` / `inset-inline`，不写 `left` / `right`） | 字符数一样、写起来一样快。现在写 `left`，将来代码层要一处处翻 | ✅ 已全仓库执行 |
| **阿语字体已打包**（`fonts/noto-naskh-arabic.woff2`） | 这不是「适配」，是「没有字体就显示不出来」：维吾尔文与哈萨克文是连写文字，字体缺失会断字，直接读不了 | ✅ 第 3 批已做 |
| **图标镜像白名单**（§7.5 的规则） | 规则本身是知识，写进文档给代码层用；设计稿不拿它做验证 | ✅ 第 4 批已定，待代码层执行 |

- **不再出 RTL 对照稿**。`_walkthrough/13-article-rtl.html` 是第 3 批做的一份验证
  （用来确认连写字体缺失、字距会把字形拉开这两个问题），**留着当记录，不再新增**。
- 不再「每批挑一屏出维吾尔文版」。
- 设计稿里不写任何多语言文案，只有一个中文版。

### 7.3 第 60 页「语言切换」仍然要画

那是**功能页**——用户选择语言的界面（列表 + 当前选中态 + 立即生效）。它不是多语言适配，
是 APP 的一个设置项，导航树里有。第 16 批照常出，只出中文版设计稿。

### 7.4 已有的 RTL 知识（留给代码层，设计阶段不执行）

第 3~4 批摸出来的四条，代码层实现时直接用，不用重新试：

1. **连写文字不能调字距**。中文标题常用的 `letter-spacing: -0.01em` 在阿拉伯字母上
   会把本该连写的字形拉开。RTL 下所有标题的 `letter-spacing` 必须为 0。
2. **正文行高要提到 2.0**，中文的 1.75 在阿拉伯系文字上偏挤（这两条已在
   `_walkthrough/13-article-rtl.html` 里验证过）。
3. **数字要隔离**。`--font-num` + `unicode-bidi: isolate`，否则数字会被 bidi 重排到错误位置。
4. **图标不能全局翻转**。判断标准见 §7.5。

### 7.5 图标镜像白名单（第 4 批定，交给代码层执行）

判断标准只有一条：**这个图标的方向是不是它含义的一部分。**

| 类别 | 处理 | 具体图标 |
|---|---|---|
| **要镜像** | 方向本身就是含义 | 返回箭头、列表项 chevron、前进/后退、侧滑手势、横向进度条的走向、横向时间轴 |
| **不镜像** | 绝对方向或文化符号 | 时钟（顺时针是物理事实）、相机镜头、播放 ▶ / 暂停 ❚❚、对勾、叉、人像、文件、电话、房屋、心形、星级、品牌 logo、任何文字 |
| **看排版** | 取决于它落在哪边 | 发送按钮的纸飞机：若 RTL 下位于左侧，镜像；若仍在右侧，不镜像 |

**实现方式：组件级显式规则，禁止全局翻转。**

```css
/* 对：只翻方向性图标 */
[dir="rtl"] .navbar__back svg { transform: scaleX(-1); }
[dir="rtl"] .chat-head__back svg { transform: scaleX(-1); }

/* 错：全局翻 svg 会把时钟翻成逆时针、书本开口朝反、笑脸变哭脸 */
/* [dir="rtl"] svg { transform: scaleX(-1); } */
```

设计稿里已经按这个规则写好的镜像点（代码层照搬即可）：

| 位置 | 做法 |
|---|---|
| 导航栏返回箭头 | `components.css` 的 `[dir="rtl"] .navbar__back svg { scaleX(-1) }` |
| 聊天页返回箭头 | `17-chat.html` 的 `[dir="rtl"] .chat-head__back svg { scaleX(-1) }` |
| 消息气泡圆角 | 逻辑属性 `border-start-start-radius` / `border-start-end-radius`，自动镜像 |
| 输入区 + 与发送按钮位置 | flex 跟随 `direction` 自动反转，不用额外写 |

## 十一、这份文档的变更规则

1. 批次顺序按项目负责人要求调整时，改本文件并说明理由。
2. **不跳批**：上一批的 `check_design` 没清完，不进下一批。理由和文档计划一样——带着问题往下走，后面每一屏都要返工。
3. 某批做完发现母版有问题，**回改母版**，然后重跑依赖它的所有屏。
