## 一、这份基线是什么

**它是文档的"锁定快照"。** 从这一刻起：

1. 任何人（包括 AI agent）开始工作，**先读本文件**，就知道哪些文档是现行有效的、各自什么版本、内容指纹是什么。
2. 本文件列出的 **21 份资产，就是全部"已确定"的文档**。不在这张表里的 Markdown，都是过程记录或已删除。
3. 每份基线文档末尾都有一行落款「**【文档基线 vX.Y】**」。

### 1.1 落款版本号是什么意思（重要，容易误解）

落款写的是**该文档第一次被纳入基线的那一版**，不是当前基线版本，也**不随内容变更而升级**：

| 落款 | 含义 |
|---|---|
| `【文档基线 v1.0】` | v1.0 时就进基线了。**即使后来改过内容（如技术路线 v2.3、根 README），落款仍是 v1.0** |
| `【文档基线 v1.1】` | v1.1 才纳入基线（V1 基线表结构、错误码规范） |
| `【文档基线 v1.2】` | v1.2 才纳入基线（第 0 段执行计划 v3.0） |
| `【文档基线 v1.3】` | v1.3 才纳入基线（APP UI 设计顺序） |
| `【文档基线 v1.5】` | v1.5 才纳入基线（PC 后台开发计划、未完成需备注） |

**所以：判断某文档是否在基线内，看本文件有没有登记它的指纹，不看落款；判断某文档内容有没有变，比对指纹，不看落款。**

### 1.2 v1.3 为什么立（一句话）

**10-29 全天 58 次推送，文档基线一份都没更新。** 3 份在册资产（导航树、设计令牌、`tokens.json`）内容已经变了却没重算指纹，1863 行的设计主文档建了却没登记，`CHANGELOG.md` 一条记录都没写。v1.3 把这些一次性补齐。详见 `docs/CHANGELOG.md` 的 2026-10-29 那节。

### 1.3 v1.4 为什么立（一句话）

**v1.3 说"全部更新"，但漏了 3 份仍写着旧 65 页口径的文档**，其中两份是索引类（根 `README.md`、`docs/design/README.md`），最容易误导新人。v1.4 把全库残留的「65 页」清干净，包括一直挂着的技术路线 §1.3 模块页数表。

> **教训**：清旧口径不能只清自己改过的那几份，要全库 grep 一遍关键词。这次是 `grep "65 页|65 个页面"` 才发现的。

### 1.4 v1.5 为什么立（一句话）

**PC 管理后台的 UI 设计启动了。** 之前全库一直写着「PC 后台暂缓」，而设计一开工就要有页面清单与开发顺序，所以 v1.5 一次补齐三样：① 新增《PC 后台开发计划》与《未完成需备注》两份文档；② 把「暂缓」的表述改成「已启动」；③ 定下**两分支文档同步规则**（`UI设计` 分支的文档改动必须同步到 `docs` 分支，`git diff` 不为空即未完成）。

## 二、已确定的文档清单（21 份）

> **行数口径**：文件内 LF 换行符个数 + 1。
> **指纹口径**：SHA256 取前 16 位小写十六进制，足以区分文件，不必逐位比对。
> **行尾口径（v1.3 新增，重要）**：本表所有行数/字节/指纹**按 LF 文件实测**。仓库根目录的 `.gitattributes` 已设 `* text=auto eol=lf`，检出即 LF。
> 加这条是因为踩过一次：本机 `core.autocrlf = true` 会把检出转成 CRLF，而工作区实际残留着 31 个 CRLF 文件，两边字节数不一致 —— `设计令牌.md` 差 156 字节、设计主文档差 1873 字节。**按工作区算出来的指纹，别人 clone 下来对不上，等于给了个复现不了的基线。** 现已全库归一为 LF 并用 `.gitattributes` 锁定。
> **v1.3 重算说明**：本版对全部 21 份重新实测，不再沿用旧值。标 🆕 的是新增，标 ✏️ 的是指纹相对 v1.2 已变。

## 四、基线规则

1. **基线只增不改**。要改基线内容，出新版本（v1.3、v1.4…），并在本文件记录「新增 / 替换 / 删除了哪份、为什么」。
2. **新增文档必须同时做四件事**：① 加基线落款 ② 在本文件登记指纹 ③ 在 `docs/README.md` 加索引 ④ 在 `docs/CHANGELOG.md` 说明。**只做其中一件等于没做。**
3. **不写死版本号**。写「技术路线 2.4 节」而不是「v2.3 的 2.4 节」，避免升级后引用过期。
4. **工作区只留现行版**。过期的技术路线、已作废的策划稿，**删除**，不留在仓库里。删除时必须在第三节登记「删了什么、为什么删、从哪个 commit 能找回」。**追溯靠 git，不靠仓库里的废文件。**
5. **删除前必须先确认它已被取代或确认作废**，不能因为"看起来没用"就删。删错能恢复（git），但会浪费一轮排查。
6. **修改基线内文档后必须重算指纹**。指纹不一致时先判断改动是否预期，再决定是否出新基线。

## 五、如何验证基线完整性

在仓库根目录执行（PowerShell）：

```powershell
$files = @(
  "AGENTS.md","README.md","docs/README.md",
  "docs/architecture/法泽FAZE_分期交付计划_v1.0.md",
  "docs/architecture/法泽FAZE_第0段执行计划_v3.0.md",
  "docs/architecture/法泽FAZE_技术路线_v2.3.md",
  "docs/architecture/法泽FAZE_V1基线表结构_v1.0.md",
  "docs/architecture/法泽FAZE_错误码规范_v1.0.md",
  "docs/architecture/法泽FAZE_PC后台开发计划_v1.0.md",
  "docs/design/法泽APP_页面导航树_v1.4.md",
  "docs/design/法泽APP_UI设计顺序_v1.0.md",
  "docs/design/未完成需备注.md",
  "docs/design/页面清单与信息架构.md","docs/design/设计令牌.md",
  "docs/design/组件清单.md","docs/design/README.md",
  "design/tokens/tokens.json",
  "docs/standards/目录与命名规范.md","docs/standards/代码注释规范.md",
  "docs/standards/代码审查清单.md","docs/standards/README.md",
  "docs/analysis/原项目技术债清单.md","docs/analysis/参考项目规范提取.md"
)
foreach ($f in $files) {
  $p = (Resolve-Path -LiteralPath $f).Path
  $h = (Get-FileHash -LiteralPath $p -Algorithm SHA256).Hash.Substring(0,16).ToLower()
  "{0,-56} {1}" -f $f, $h
}
```

把输出与第二节的指纹表逐个对照。**指纹不一致不等于出错**（说明该文件在基线之后被更新过）：

- 改动是预期的 → 出新基线版本，更新指纹
- 改动是意外的 → `git log` 查谁改的、为什么

查看基线所在的提交：

```powershell
git show v1.5-docs-baseline --stat
git tag -n
```
