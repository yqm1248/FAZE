## 一、这份基线是什么

**它是文档的"锁定快照"。** 从这一刻起：

1. 任何人（包括 AI agent）开始工作，**先读本文件**，就知道哪些文档是现行有效的、各自什么版本、内容指纹是什么。
2. 本文件列出的 18 份资产，**就是全部"已确定"的文档**。不在这张表里的 Markdown，都是历史版本或过程记录，不得作为实施依据。
3. 每份文档末尾都有一行统一落款「**【文档基线 v1.0】**」，标明它属于这次基线。

**为什么需要它**：此前文档虽已全部入库，但散落在 5 个目录、21 个文件里，其中混着 4 个历史版本。没有一张总表，就没人（也没人形的 AI）能确信"我读的是不是最新的"。本文件用**文件指纹**把这个不确定性消掉。

## 四、基线规则

1. **基线只增不改**。要改基线内容，出新版本（v1.1、v1.2…），并在本文件记录「新增/替换了哪份、为什么」。
2. **新增文档必须同时做三件事**：① 在本文件登记指纹；② 在 `docs/README.md` 索引里加一行；③ 在 `docs/CHANGELOG.md` 说明。**只做其中一件等于没做。**
3. **不写死版本号**。写「技术路线 2.4 节」而不是「v2.3 的 2.4 节」，避免升级后引用过期。
4. **历史文档不删**。过期的技术路线保留在原处，由本文件第三节标明其性质。删掉会失去追溯能力。
5. **每份基线文档末尾必须有基线落款**。新增文档若没有落款，说明它还没进基线。

## 五、如何验证基线完整性

在仓库根目录执行（PowerShell）：

```powershell
$files = @(
  "AGENTS.md","README.md","docs/README.md",
  "docs/architecture/README.md",
  "docs/architecture/法泽FAZE_技术路线_v2.3.md",
  "docs/architecture/法泽FAZE_分期交付计划_v1.0.md",
  "docs/design/README.md","docs/design/法泽APP_页面导航树_v1.4.md",
  "docs/design/页面清单与信息架构.md","docs/design/设计令牌.md","docs/design/组件清单.md",
  "docs/standards/README.md","docs/standards/目录与命名规范.md",
  "docs/standards/代码注释规范.md","docs/standards/代码审查清单.md",
  "docs/analysis/原项目技术债清单.md","docs/analysis/参考项目规范提取.md",
  "design/tokens/tokens.json"
)
foreach ($f in $files) {
  $h = (Get-FileHash $f -Algorithm SHA256).Hash.Substring(0,16).ToLower()
  "{0,-50} {1}" -f $f, $h
}
```

把输出与本文件第二、三节的指纹表逐个对照。**指纹不一致不等于出错** —— 说明该文件在基线之后被更新过，此时应：
- 若改动是预期的 → 出基线 v1.1，更新指纹
- 若改动是意外的 → 查 `git log` 找出谁改的、为什么

查看基线所在的提交：

```powershell
git show v1.0-docs-baseline --stat
git list  # 或：git tag -n
```

## 七、基线落款样式

每份基线文档末尾的那一行，长这样：

```text
---

> **【文档基线 v1.0】** 本文件属于「法泽 FAZE 文档基线 v1.0」（2026-10-28 确立）。
> **后续一切文档从这里开始。** 基线清单与文件指纹见 `docs/BASELINE.md`。
```

判断一份文档是否在基线内，看它末尾有没有这一行即可。
