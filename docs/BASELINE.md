## 一、这份基线是什么

**它是文档的"锁定快照"。** 从这一刻起：

1. 任何人（包括 AI agent）开始工作，**先读本文件**，就知道哪些文档是现行有效的、各自什么版本、内容指纹是什么。
2. 本文件列出的 22 份资产，**就是全部"已确定"的文档**。不在这张表里的 Markdown，都是历史版本、过程记录或已作废，不得作为实施依据。
3. 每份基线文档末尾都有一行落款「**【文档基线 vX.Y】**」。

### 1.1 落款版本号是什么意思（重要，容易误解）

落款写的是**该文档被纳入基线的那一版**，不是当前基线版本：

| 落款 | 含义 | 举例 |
|---|---|---|
| `【文档基线 v1.0】` | v1.0 时就进基线了，v1.1 里内容未变（或仅版本升级时重算指纹） | `AGENTS.md`、`docs/standards/*` |
| `【文档基线 v1.1】` | v1.1 才纳入基线 | 第 0 段那 4 份规划文档 |

**两种落款都表示"在基线内"。** 判断某文档是否在基线内，**看本文件有没有登记它的指纹**，不看落款版本号。

## 四、基线规则

1. **基线只增不改**。要改基线内容，出新版本（v1.2、v1.3…），并在本文件记录「新增/替换了哪份、为什么」。
2. **新增文档必须同时做四件事**：① 加基线落款 ② 在本文件登记指纹 ③ 在 `docs/README.md` 加索引 ④ 在 `docs/CHANGELOG.md` 说明。**只做其中一件等于没做。**
3. **不写死版本号**。写「技术路线 2.4 节」而不是「v2.3 的 2.4 节」，避免升级后引用过期。
4. **历史文档不删**。过期的技术路线保留在原处，由本文件第三节标明其性质。删掉会失去追溯能力。
5. **作废文档也必须留名**。像「第0段任务分解 v1.0」这样从未推送过完整稿的中间产物，一旦它在别处被引用过，就要进第三节，不能悄悄删。

## 五、如何验证基线完整性

在仓库根目录执行（PowerShell）：

```powershell
$files = @(
  "AGENTS.md","README.md","docs/README.md",
  "docs/architecture/README.md",
  "docs/architecture/法泽FAZE_技术路线_v2.3.md",
  "docs/architecture/法泽FAZE_分期交付计划_v1.0.md",
  "docs/architecture/法泽FAZE_第0段执行计划_v2.0.md",
  "docs/architecture/法泽FAZE_第0段串行执行序列_v1.0.md",
  "docs/architecture/法泽FAZE_V1基线表结构_v1.0.md",
  "docs/architecture/法泽FAZE_错误码规范_v1.0.md",
  "docs/design/README.md","docs/design/法泽APP_页面导航树_v1.4.md",
  "docs/design/页面清单与信息架构.md","docs/design/设计令牌.md","docs/design/组件清单.md",
  "docs/standards/README.md","docs/standards/目录与命名规范.md",
  "docs/standards/代码注释规范.md","docs/standards/代码审查清单.md",
  "docs/analysis/原项目技术债清单.md","docs/analysis/参考项目规范提取.md",
  "design/tokens/tokens.json"
)
foreach ($f in $files) {
  $h = (Get-FileHash $f -Algorithm SHA256).Hash.Substring(0,16).ToLower()
  "{0,-52} {1}" -f $f, $h
}
```

把输出与本文件第二、三节的指纹表逐个对照。**指纹不一致不等于出错** —— 说明该文件在基线之后被更新过，此时应：

- 改动是预期的 → 出新基线版本（v1.2），更新指纹
- 改动是意外的 → 查 `git log` 找出谁改的、为什么

查看基线所在的提交：

```powershell
git show v1.1-docs-baseline --stat
git tag -n
```
