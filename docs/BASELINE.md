## 一、这份基线是什么

**它是文档的"锁定快照"。** 从这一刻起：

1. 任何人（包括 AI agent）开始工作，**先读本文件**，就知道哪些文档是现行有效的、各自什么版本、内容指纹是什么。
2. 本文件列出的 **31 份资产，就是全部"已确定"的文档**。不在这张表里的 Markdown，都是过程记录或已删除。
3. 每份基线文档末尾都有一行落款「**【文档基线 vX.Y】**」。

### 1.1 落款版本号是什么意思（重要，容易误解）

落款写的是**该文档第一次被纳入基线的那一版**，不是当前基线版本，也**不随内容变更而升级**：

| 落款 | 含义 |
|---|---|
| `【文档基线 v1.0】` | v1.0 时就进基线了。**即使后来改过内容（如技术路线 v2.3、根 README），落款仍是 v1.0** |
| `【文档基线 v1.1】` | v1.1 才纳入基线（V1 基线表结构、错误码规范） |
| `【文档基线 v1.2】` | v1.2 才纳入基线（第 0 段执行计划 v3.0） |
| `【文档基线 v1.3】` | v1.3 才纳入基线（APP UI 设计顺序） |
| `【文档基线 v1.5】` | v1.5 才纳入基线（PC 后台开发计划、未完成需备注） |
| `【文档基线 v1.12】` | v1.12 才纳入基线（开发计划总纲） |
| `【文档基线 v1.13】` | v1.13 才纳入基线（数据表规范） |

**所以：判断某文档是否在基线内，看本文件有没有登记它的指纹，不看落款；判断某文档内容有没有变，比对指纹，不看落款。**

> **⚠️ 历史不一致（v1.44 只纠正了一部分）**：v1.36（§7.40）曾把 `docs/README.md` 的落款从 `v1.0` 改成
> **当时的当前基线号 v1.36**，此后每版都跟着往上写，与本节的规则直接冲突（本节明写「根 README 落款仍是 v1.0」）。
> 根 `README.md` 与 `AGENTS.md` 的落款**没有**被改，仍是 `v1.0`，所以不是全库问题。
> v1.44 把 `docs/README.md` 改回 `v1.0` 并补了语义说明（见 §7.48）；
> **其余文档的落款是否也被跟随升级，v1.44 没有逐一核对**（抽到的例子：《第 1 段工作流》是 `v1.22 → v1.43`），
> 已登记为《第 1 段工作流》§十.1 的挂账 **G-11**，下次文档收口时统一核。
> **今后怎么改**：只更新正文里的「当前基线号」，不碰落款。

### 7.31 v1.27 新增 1 份 + 内容变更 10 份（第 4 段工作流定稿，带出三项连带修正）

> 起因：第 3 段施工文档已产出（v1.26），第 4 段（文书中心）只有总纲 §5.5 的边界定义与 8 条锚点。本文档是第 4 段的唯一施工文档。**段 0~3 的施工一次都没跑**，本文档按「假定段 3 已出口」写。

**本版最重要的一件事：段 4 的范围被改了。**

总纲 §5.5（2026-10-30 写）把段 4 定位成「**少数民族文字排版的最终检验场**」，要求模板四语言、验维吾尔文连写与藏文叠字。**2026-11-01 负责人拍板改为「只做中文」**，理由是：

- 法律**并不要求**文书必须中文。《宪法》第 134 条：「在少数民族聚居或者多民族共同居住的地区，应当用当地通用的语言进行审理；**起诉书、判决书、布告和其他文书应当根据实际需要使用当地通用的一种或者几种文字**」；《民事诉讼法》第 11 条同旨。伊犁哈萨克自治州正属该范围。
- 但**实务上**当事人递交法院的起诉状绝大多数是中文（卷宗归档、对方当事人、上诉审级、法官工作语言都是中文）。负责人把法泽的文书定位于「**能递交给法院的正式文件**」。

所以改的是**产品假设**，不是实现方式。连带结果：模板 20 份 → 5 份；原 `4-A3`（维吾尔文连写）与 `4-A4`（藏文叠字）删除并换成两条**新**锚点；`4-A6` 从「AIGC 隐式标识」改为「文书溯源元数据」；段 4 不再依赖藏文字体授权（那是段 0 `0-A4` 的事，仍要验，验的是**界面**）。

## 四、基线规则

1. **基线只增不改**。要改基线内容，出新版本（v1.3、v1.4…），并在本文件记录「新增 / 替换 / 删除了哪份、为什么」。
2. **新增文档必须同时做四件事**：① 加基线落款 ② 在本文件登记指纹 ③ 在 `docs/README.md` 加索引 ④ 在 `docs/CHANGELOG.md` 说明。**只做其中一件等于没做。**
3. **不写死版本号**。写「技术路线 2.4 节」而不是「v2.3 的 2.4 节」，避免升级后引用过期。
4. **工作区只留现行版**。过期的技术路线、已作废的策划稿，**删除**，不留在仓库里。删除时必须在第三节登记「删了什么、为什么删、从哪个 commit 能找回」。**追溯靠 git，不靠仓库里的废文件。**
5. **删除前必须先确认它已被取代或确认作废**，不能因为"看起来没用"就删。删错能恢复（git），但会浪费一轮排查。
6. **修改基线内文档后必须重算指纹**。指纹不一致时先判断改动是否预期，再决定是否出新基线。
