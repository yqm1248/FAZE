## 一、值班与响应（裁决 20）

### 1.1 口径（**禁止写成 7×24**）

| 级别 | 定义 | 响应时限 | 处置窗口 |
|---|---|---|---|
| **P0** | 全站不可用（服务宕机、数据库不可用）、**资金恒等式不成立**、身份/审计链路断裂、安全事件 | **立即**（告警发出后 15 分钟内必须有人看） | 全天 |
| **P1** | 核心功能受损（支付失败率高、接口错误率 > 5%、延迟 P95 > 1s、备份连续失败） | **次日 9:00–21:00** | 工作日与周末白天 |
| **P2** | 局部问题（单接口慢、磁盘 80%、监控偶发 target DOWN） | 次日 9:00–21:00，可合并维护窗口 | 工作日与周末白天 |

> **如实说明**：当前只有一名负责人，**做不到 7×24**。所以 P0 的定义收得很窄
> （只有「全站不可用」「钱不对」「身份/审计链断」算 P0），其余一律次日处理。
> **不要在文档或对外说明里写「7×24 值班」这种兑现不了的承诺**（工作流 §六 R5 明文）。

### 1.2 每日巡检（9:00 前完成，约 5 分钟）

1. Prometheus `http://127.0.0.1:9090/targets` → `faze-api` 是否 **UP**；
   Grafana `http://127.0.0.1:3000/d/faze-api-overview` → 4 个图是否正常。
2. `Get-Content .\logs\backup.log -Tail 3` → 最近一次是否 SUCCESS；
   `Get-ChildItem E:\faze-backup | Sort-Object LastWriteTime -Descending | Select-Object -First 3 Name,LastWriteTime`。
3. PC 后台运维健康报告（`GET /admin/ops/health-report`，F 组交付）红标项。
4. `Get-Content .\logs\faze-api-error.log -Tail 50` 扫一眼有没有新 ERROR。
5. 交接：未关闭的告警 + 未完成的备份/恢复要写进交接说明，不要口头交接。

### 1.3 通知渠道现状（**重要，别假设钉钉会响**）

| 通道 | 状态 | 说明 |
|---|---|---|
| 钉钉自定义机器人（裁决 2 的既定口径） | ❌ **未配置** | `sys_config.alert.dingtalk_webhook` / `alert.dingtalk_secret` 两键为**空串**（V703 已建）。T1 的 `AlertDispatcher` 在 webhook 为空时只打 WARN，不发送。 |
| 本地 mock 接收端 `scripts/alert/mock-receiver.py` | ✅ 可用 | 只用于**证明告警系统真的发出了 HTTP POST**（`7-A8` 的降级证据），不是给人看的通知。 |
| 后台红标 + 每日巡检报告 | ⚠️ 依赖 F 组交付 | `GET /admin/ops/health-report` 异常项标红。 |
| 邮件 | ⏭ 段 8 处理 | 工作流 §十一 的备选方案记录，本段不实现。 |

> **结论**：本段**没有任何一条「人能看到」的自动告警出口**。值班靠「每日人工巡检」+
> 「P0 由用户/接口先发现」。段 8 必须落地一条真实通道，否则 `7-A8` 永远只是挂账（见 §十一 第 1/2 条）。

### 2.2 启动 / 停止（幂等）

```powershell
Set-Location E:\dshcode\FAZE

# 启动（已在跑就跳过；缺二进制自动下载解压，首次约 3~5 分钟、约 600MB）
.\scripts\monitor\start-monitor.ps1
.\scripts\monitor\start-monitor.ps1 -PromPort 9091 -GrafanaPort 3001   # 端口冲突时
.\scripts\monitor\start-monitor.ps1 -SkipDownload                       # 离线环境

# 停止（没在跑也 exit 0）
.\scripts\monitor\stop-monitor.ps1
```

启动脚本做的事：二进制检测/下载 → `promtool check config` + `check rules` → 拉起 Prometheus
（工作目录 `scripts/monitor/`，`rule_files` 的相对路径才解析得对）→ 拉起 Grafana
（用 `GF_*` 环境变量注入端口/匿名/管理员，不改安装目录的 ini）→ **HTTP 就绪**探活
（不是「端口能连上」——`deploy/restart-api.ps1` 的 ready 就是假阳性）→ 幂等建数据源 +
导入 dashboard。

| 退出码 | 含义 |
|---|---|
| 0 | 全部就绪（Prometheus + Grafana + 数据源 + dashboard） |
| 1 | 二进制缺失/下载解压失败，或 `promtool` 配置校验失败 |
| 2 | 端口被**别的进程**占用（脚本会打印 PID/进程名） |
| 3 | 进程起来了但 HTTP 未就绪（超时） |
| 4 | Grafana 数据源/dashboard 安装失败（进程本身可能已起来） |

## 三、告警

### 3.1 通道与配置

| 项 | 值 |
|---|---|
| 通道（设计口径） | **钉钉自定义机器人**（webhook + 加签） |
| 配置位置 | `sys_config.alert.dingtalk_webhook` / `sys_config.alert.dingtalk_secret`（**当前两键为空串**） |
| 备用通道 | 后台红标（`GET /admin/ops/health-report`）+ 每日 09:00 巡检报告 |
| 本地降级验证 | `python -u .\scripts\alert\mock-receiver.py --port 8088` → 日志 `logs\alert-mock.log` |

### 3.2 6 条规则（`scripts/monitor/alert-rules.yml`）

| 告警 | 表达式（简化） | 持续 | 级别 | 本段状态 |
|---|---|---|---|---|
| `FazeServiceDown` | `up{job="faze-api"} == 0` | 1m | **P0** | ✅ 可触发（停服务即触发） |
| `FazeHighErrorRate` | 5xx 占比 > 5% | 3m | P1 | ⚠️ 常规业务异常不产生 5xx；dev-only `GET /api/v1/dev/fault?mode=500` 可造 500（§3.4） |
| `FazeHighLatency` | P95 > 1000ms | 5m | P1 | ✅ 可用慢请求注入触发 |
| `FazeBackupStale` | `time() - faze_backup_last_success_timestamp > 86400*1.5` | 即时 | P1 | ✅ 已实测：gauge 正常时 inactive；注入旧时间戳后 firing 且**系统自动 POST 到 mock**（02:02:57，269B） |
| `FazeDiskLow` | E: 盘使用率 > 80% | 5m | P2 | ⚠️ 需 `node_exporter`，**本段未安装** → 恒 Inactive |
| `FazeIdentityBroken` | `faze_identity_check_failed_total > 0`（段 5 巡检） | 即时 | **P0** | ⚠️ 指标**未交付** → 恒 Inactive |

> **v1.0 修正**：v1.0 把 `FazeIdentityBroken` 写成「资金恒等式不成立」，这是错的——
> 资金恒等式是 `1-A7` 的检查，不是这条规则。本条依赖段 5 的巡检失败计数，指标名以段 5 实际交付为准。

### 3.3 阈值双处维护（已知冗余，工作流 §十一 已登记）

阈值同时在两处：① `scripts/monitor/alert-rules.yml`（Prometheus 静态规则，**真正决定告警**）；
② `sys_config` 的 `alert.*` 键（后台可改，供界面展示/运营）。

本段**没有**做「改 sys_config 自动同步规则文件」。正确步骤：

```powershell
# 1) 改 alert-rules.yml 里的数字（例：0.05 → 0.03）
# 2) 热重载
Invoke-RestMethod -Method POST -Uri http://127.0.0.1:9090/-/reload
# 3) 同步改 sys_config 同名键（两处一致）
```

### 3.4 错误率与「让接口返回 500」

`common/exception/GlobalExceptionHandler.java` 把 `RuntimeException` / `Exception` 统一映射成
**HTTP 200 + 业务错误码**（`R.fail(COMMON_INTERNAL)`）；只有 `BusinessException`（按错误码的
httpStatus，多为 200）、403（无权限）、404（路径不存在）、429（限流）有真实状态码。
所以**常规业务异常不会产生 `status="500"`**，`FazeHighErrorRate` 平时不会 firing。

**本段 T1 补了一个仅 dev 的故障端点**（`@Profile("!prod")`）：

```powershell
curl.exe -s -o NUL -w "%{http_code}`n" "http://127.0.0.1:8081/api/v1/dev/fault?mode=500"   # => 500
```

实测它会出现在 `faze_http_requests_total{status="500"}` 里，`fault-inject.ps1 -Mode 500`
已把它列为首选探测目标（找不到任何 5xx 载体时会 exit 3，**不伪造**）。
**生产没有这个端点** → 生产错误率口径仍需段 8 决策（按业务错误码统计 / 异常映射 5xx / 保留独立故障端点）。

### 3.4b 告警链路的 3 个已知结构缺陷（本段实测，必须知道）

| # | 缺陷 | 现象 | 运维影响 |
|---|---|---|---|
| 1 | **`AlertDispatcher` 跑在 faze-api 进程内**（`@Scheduled`） | 服务挂了派发器也停 → `FazeServiceDown` 规则 firing 但**永远推不出去** | P0「服务不可用」告警形同虚设；段 8 必须改外部轮询/Alertmanager |
| 2 | **恢复通知是死代码**：`pushResolved` 依赖 `/api/v1/alerts` 返回 `resolved`，该接口只返回 pending/firing | 真实环境永远不会收到「✅ 已恢复」 | 告警恢复只能靠人工确认 |
| 3 | **去重键先写后发**（`SETNX` 后才 `sendDingTalk`） | webhook 为空 / 发送失败时，告警被吞 **1 小时** | 配置错误期间会丢告警；排查时先清 `faze:alert:*`（Redis **DB1**） |

### 3.5 告警演练（怎么证明「真的会响」）

```powershell
Set-Location E:\dshcode\FAZE
# A. 起 mock 接收端（另开窗口，保持运行）
python -u .\scripts\alert\mock-receiver.py --port 8088
# B. 让 AlertDispatcher 指向 mock：sys_config.alert.dingtalk_webhook = http://127.0.0.1:8088/alert
#    （本机验证用；段 8 换成真实钉钉 webhook + secret；改完等 Dispatcher 下一轮 60s 轮询）
# C. 注入故障
.\scripts\monitor\fault-inject.ps1 -Mode down -Force -AutoRestart -DownSeconds 150
# 或：.\scripts\monitor\fault-inject.ps1 -Mode slow -DurationSeconds 420
# D. 看 mock 收到的真实 POST
Get-Content .\logs\alert-mock.log -Tail 60
```

> **手 curl 一次不算证据**（`7-A8` 的「常见假通过」明文）。必须是 **AlertDispatcher 自动发出**的
> POST：日志里要有 `POST /alert` 与完整 body。没有钉钉群时这是唯一合法降级证据。

### 3.6 告警没响怎么排查（两条线分开查）

1. **系统侧**：Prometheus `/alerts` 里有没有 firing？`curl.exe -s http://127.0.0.1:9090/api/v1/alerts`；
   有 firing 但没 POST → 查 T1 的 `AlertDispatcher` 轮询与 `sys_config` webhook 值。
2. **通道侧**：单独 POST 一次钉钉 webhook 测加签（或看 mock 是否收到）。
   **两者分开排查，不要混在一起猜。**

## 四、备份与恢复

### 4.1 备份策略

| 项 | 值 |
|---|---|
| 对象 | MySQL `faze` 库（54 张表，含 `flyway_schema_history`） |
| 方式 | `mysqldump --single-transaction --routines --triggers`（InnoDB 一致性快照，不锁表） |
| 频率 | 每日 03:00（计划任务命令见 §4.6，**本段未实际注册**） |
| 目录 | `E:\faze-backup\`（与仓库分离，**不进仓库**） |
| 命名 | `faze_YYYYMMDD_HHmm.sql`；同分钟重跑自动加秒，不覆盖 |
| 校验 | 文件 > 0 字节 **且** > 上一次备份大小 × 0.5；失败即退出码 1 |
| 行数清单 | 同目录 `<dump>.manifest.tsv`（备份时点逐表行数，恢复校验基准） |
| 保留 | 删除 30 天前的 `.sql`，**无条件保留最近 3 份** |
| 成功标记 | `logs\backup-last-success.txt`：**单行 epoch 秒**（无 BOM），T1 的 Gauge 读它 |
| 失败发现 | 非 0 退出码 + `logs\backup.log` 的 FAIL 行；失败**不更新**成功标记 → 36h 后 `FazeBackupStale` 响 |

```powershell
Set-Location E:\dshcode\FAZE
.\scripts\backup\backup.ps1
.\scripts\backup\backup.ps1 -BackupDir D:\faze-backup -RetentionDays 14   # 磁盘紧张时降级
```

> **v1.0 修正**：v1.0 写「失败重试 3 次」——**当前脚本没有实现重试**（见 §十一 第 6 条）。
> 现在是「失败即非 0 退出 + 写 backup.log，下次 36h stale 告警」，请如实按这个口径值班。

### 4.2 恢复步骤（**只恢复到 `faze_restore`，绝不碰 `faze`**）

```powershell
Set-Location E:\dshcode\FAZE
$sql = (Get-ChildItem E:\faze-backup -Filter 'faze_*.sql' | Sort-Object LastWriteTime -Descending | Select-Object -First 1).FullName
.\scripts\backup\restore.ps1 -File $sql -ReportFile .\tmp\restore-report.txt
```

**硬保护**（在任何数据库操作之前执行，工作流 `7-A9` 要求不许删）：

- 目标库名 `faze` → 直接 `exit 1`，**不 DROP、不改任何数据**；
- 目标库名 `faze_admin` / `faze_test` → 同样拒绝；
- 目标库固定 `faze_restore`，先 `DROP DATABASE IF EXISTS` 再 `CREATE`（字符集跟随源库）。

**三层校验**：

1. **逐表行数**：54 张表逐一 `COUNT(*)`；基准是 `<dump>.manifest.tsv`（备份时点），
   **不是**「当前源库」——活库在备份到恢复之间被并发写入是正常的（本段实测 T1 并发跑 Flyway，
   `flyway_schema_history`/`sys_config` 行数变了）；当前源库行数作参考列并标注漂移。
2. **抽样 MD5**：`app_user` / `orders` / `balance_flow` 各 10 行，`MD5(CONCAT_WS('#', 全部列))`，
   按 MD5 排序取同一批行（保证两边可比）。
3. **数据可用性等价 SQL**：`SELECT ... FROM app_user WHERE phone='…'`（登录等价）+
   `SELECT COUNT(*) FROM orders WHERE user_id=…`（查单等价），手机号在报告里脱敏。

### 4.3 恢复后「业务可用」验证（本段未做服务级验证）

工作流要求「服务连 `faze_restore` 能登录、能查单」。**本段没有做**：

- 需要把 faze-api 的 datasource 临时指向 `faze_restore` 并**重启 faze-api**——重启是 T1/Lead 的权限，
  且会打断并行的后端开发；
- 本段替代证据：用 `mysql` 直接对 `faze_restore` 跑登录等价 SQL 与查单等价 SQL（见
  [7-A9-restore.md](../acceptance/seg7/7-A9-restore.md)）；
- **补验方式**（需 T1 配合）：改 `deploy/.env` 的 `FAZE_DB_URL` 库名为 `faze_restore`（或
  启动参数覆盖 `spring.datasource.url`）→ `.\deploy\restart-api.ps1` → 用测试账号登录、调一次
  `GET /api/v1/app/orders` → 改回 `faze` → 再重启 → 打接口确认恢复。

### 4.4 恢复演练频率与要求

- **每段收口前**跑一次完整演练（`backup.ps1` → `restore.ps1`），输出存 `docs/acceptance/segX/`；
- **每季度**至少一次（技术路线 §17.5），核对三层校验全绿；
- 演练**必须**包含「`restore.ps1 -TargetDb faze` 被拒绝」这一条；
- 演练不需要停服务（`--single-transaction` 不锁表），但**不要放在业务高峰**（IO 抢）。

### 4.5 磁盘不够时的降级

保留期 30 天 → **14 天**：`backup.ps1 -RetentionDays 14`（脚本 <14 会 WARN）。工作流 §三 G5
「卡住怎么办」允许该降级，但要在本手册与挂账里写明。**不允许**：备份放回仓库（会被 git 误提交）、
只保留 1 份（备份自身损坏就没有历史）。

### 4.6 Windows 计划任务（**只给命令，本段未注册**）

未经用户同意**不创建系统级计划任务**。装好以后由负责人执行（管理员 PowerShell）：

```powershell
# 每日 03:00 备份
schtasks /Create /TN "FAZE-DailyBackup" /TR "powershell -NoProfile -ExecutionPolicy Bypass -File E:\dshcode\FAZE\scripts\backup\backup.ps1" /SC DAILY /ST 03:00 /RU "%USERNAME%" /RL HIGHEST /F
# 查看 / 手工触发 / 删除
schtasks /Query /TN "FAZE-DailyBackup" /V /FO LIST
schtasks /Run /TN "FAZE-DailyBackup"
schtasks /Delete /TN "FAZE-DailyBackup" /F
```

> 注意：`schtasks` **没有**「失败重试 3 次」参数；要重试需在脚本外层包（`backup.ps1` 加 `-Retry`）
> 或用任务 XML 的 `<RestartOnFailure>`。**本段未实现**（挂账 §十一 第 6 条）。
> 注册后必须验证：`schtasks /Run /TN "FAZE-DailyBackup"` → `logs\backup.log` 多一行 SUCCESS。

## 五、日志与留存

### 5.1 文件位置（logback 实测配置，T1 的 G4 交付）

| 文件 | 内容 | 轮转 |
|---|---|---|
| `logs\faze-api.log` | 全量文本（人看，含 traceId） | 按天 + 100MB，保留 30 天 |
| `logs\faze-api-error.log` | 仅 ERROR（**先看这个**） | 按天 + 100MB，保留 **30 天**（v1.0 写的 90 天与实测不符） |

| `logs\fault-inject.log` | 故障注入动作记录 | 不轮转 |

### 5.2 数据库里的审计（审计 ≠ 日志）

| 类型 | 位置 | 留存 |
|---|---|---|
| `operation_log`（审计） | 数据库 | **≥ 3 年**（个保法/电商法），配置 `audit.operation-log-days`（默认 1095，低于则拒绝启动） |
| `login_log`（审计） | 数据库 | **≥ 180 天**（网安法），配置 `audit.login-log-days`（默认 180） |
| 资金流水 `balance_flow` / `payment_record` | 数据库 | **≥ 5 年**（资金） |
| 审计降级文件 | `logs/audit-fallback.log` | **出现即 P1 告警**（审计链断了） |

> 文件日志可轮转、可关级别，**不能当证据**；审计必须落库（《审计与日志规范》§2）。

## 六、故障分级与处置（速查）

| 故障 | 分级 | 第一步 |
|---|---|---|
| faze-api 不可达（`FazeServiceDown`） | **P0** | 见 §6.1 |
| 数据库连不上 | **P0** | `mysql -e "select 1"`；看连接池日志与 `faze-api-error.log` |
| 余额 ≠ SUM(流水) | **P0** | **停止一切资金写入**，导出 `balance_flow` 全量，找差异账户（`1-A7` 口径） |
| 身份巡检失败（`FazeIdentityBroken`） | **P0** | 段 5 指标未交付 → 人工查 `operation_log` 的身份相关动作，并通知 T1 |
| 接口错误率 > 5% | P1 | Grafana 看哪个 `path`，再看该 path 的错误日志（注意 §3.4：业务错误是 200） |
| 接口 P95 > 1s（`FazeHighLatency`） | P1 | 慢接口 topk → MySQL 慢查询 / Redis slowlog / 第三方超时 |
| 备份失败/过期（`FazeBackupStale`） | P1 | `Get-Content .\logs\backup.log -Tail 20` → 手工跑一次 |
| 支付成功率骤降 | P1 | 渠道回调日志 + `recharge_record` 的 failed 行 |
| 敏感词误杀大量用户 | P1 | A-25 把该词降级或停用（**不重启即生效**） |
| 磁盘 > 80%（`FazeDiskLow`） | P2 | `Get-PSDrive E`；清理备份/日志（§4.5） |

### 6.1 P0：faze-api 不可用

```powershell
Set-Location E:\dshcode\FAZE
# 1) 是进程没了还是端口不通
Get-CimInstance Win32_Process -Filter "Name='java.exe'" | Where-Object { $_.CommandLine -match 'com\.faze\.FazeApiApplication' } | Select-Object ProcessId, CommandLine
Test-NetConnection 127.0.0.1 -Port 8081 -InformationLevel Quiet
# 2) 先看 error 日志
Get-Content .\logs\faze-api-error.log -Tail 50
Get-Content .\logs\faze-api.out.log -Tail 80
# 3) 重启（注意：脚本的 ready 只等端口，是假阳性）
.\deploy\restart-api.ps1
# 4) 真正确认：健康 + 一次业务请求都必须通
curl.exe -s -o NUL -w "%{http_code}`n" http://127.0.0.1:8081/actuator/health
curl.exe -s -o NUL -w "%{http_code}`n" http://127.0.0.1:8081/api/v1/pub/app/config
```

> ⚠️ `deploy/restart-api.ps1` 打印 ready 时**只代表端口可连**，不代表业务可用。
> 重启后**必须**再打一次 health 或业务接口；本段已实测该脚本有假阳性。

### 6.2 故障注入工具（告警演练用）

`scripts/monitor/fault-inject.ps1`：

| 模式 | 做什么 | 触发哪条告警 | 风险 |
|---|---|---|---|
| `-Mode down -Force [-AutoRestart]` | 停 faze-api 进程（只认主类 `com.faze.FazeApiApplication`） | `FazeServiceDown`（1m） | **会短暂停服务**；不给 `-AutoRestart` 就保持停止 |
| `-Mode slow -DurationSeconds 420` | 对公开登录接口分片发 body，让服务端耗时 ~2s | `FazeHighLatency`（5m） | 占 Tomcat 线程，别长时间跑 |
| `-Mode 500` | 探测公开接口能否返回 5xx（首选 dev-only `/api/v1/dev/fault?mode=500`） | `FazeHighErrorRate` | 生产无该端点；找不到载体时 exit 3（§3.4） |

## 七、常见故障处置（工具/环境类）

| 现象 | 先查 | 处置 |
|---|---|---|
| `start-monitor.ps1` exit 2 | `netstat -ano \| findstr 9090`（或 3000） | 换端口 `-PromPort 9091 -GrafanaPort 3001`，或停占用进程 |
| Grafana 打不开 | `tmp\monitor\logs\grafana.err.log`、`tmp\monitor\logs\grafana\<日期>.log` | 常见：3000 被占、首次建库慢（等 60s）、日志目录无写权限 |
| Prometheus target DOWN | `http://127.0.0.1:9090/targets` 的 Error 列 | 401 → `/actuator/prometheus` 本机鉴权未放行；refused → faze-api 没起；看 `prometheus.out.log` |
| 规则不 firing | `http://127.0.0.1:9090/rules` 的 State | 无样本（指标未交付）恒 Inactive，属正常（§十一） |
| dashboard 是空的 | Grafana 数据源 URL 是否 `http://127.0.0.1:9090` | 改数据源或重跑 `start-monitor.ps1`（会补装） |
| 备份失败 | `logs\backup.log` 的 `error=` | MySQL 未起 / 磁盘满 / mysqldump 路径变 / `.env` 凭据变 |
| 恢复校验不一致 | `restore.ps1` 输出的 ❌ 行 | manifest 缺失且源库在动 → 重新备份再恢复；真不一致 → P1，别覆盖生产 |
| 忘记 Grafana 密码 | — | 改 `tmp\monitor\grafana-13.3.0\data\grafana.db`，或删库重启（会丢 dashboard，脚本自动重导） |
| `.ps1` 中文乱码/解析报错 | 文件是否 **UTF-8 with BOM** | `[System.IO.File]::WriteAllText($f,$t,(New-Object System.Text.UTF8Encoding($true)))` 重写 |
