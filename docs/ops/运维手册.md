## 一、值班与响应（一句话版）

| 级别 | 定义 | 响应时限 | 响应方式 |
|---|---|---|---|
| **P0** | 全站不可用（服务宕机、数据库不可用、资金恒等式不成立） | **立即**（发出告警后 15 分钟内必须有人看） | 钉钉群消息 → 手机 |
| **P1** | 核心功能受损（支付失败率高、接口错误率 > 5%、备份连续失败） | **次日 9:00–21:00** | 钉钉群消息 |
| **P2** | 局部问题（单接口慢、磁盘 80%） | 工作日 9:00–21:00 | 钉钉群消息 + 每日巡检报告 |

> **如实说明**：当前只有一名负责人，**做不到 7×24**。所以 P0 的定义收得很窄（只有「全站不可用」和「钱不对」算 P0），其余一律次日处理。**不要在文档里写「7×24 值班」这种兑现不了的承诺。**

## 二、监控启动

```powershell
# 启动 Prometheus(:9090) + Grafana(:3000)
.\scripts\monitor\start-monitor.ps1

# 停止
.\scripts\monitor\stop-monitor.ps1
```

- 抓取目标：`http://127.0.0.1:8080/actuator/prometheus`（`scripts/monitor/prometheus.yml`）
- Grafana 面板：导入 `scripts/monitor/grafana-dashboard.json`（4 个图：QPS / P95 / 错误率 / 敏感词命中）
- **开发/验收期允许监控与业务同机**；生产必须独立（见 §六）

## 三、告警

### 3.1 通道

| 项 | 值 |
|---|---|
| 通道 | **钉钉自定义机器人**（webhook + 加签） |
| 配置位置 | `sys_config.alert.dingtalk_webhook` / `sys_config.alert.dingtalk_secret`（**Jasypt 加密，不进仓库**） |
| 备用通道 | 后台红标（`GET /admin/ops/health-report`）+ 每日 09:00 巡检报告 |

### 3.2 规则（`scripts/monitor/alert-rules.yml`）

| 告警 | 阈值 | 持续 | 级别 |
|---|---|---|---|
| `FazeServiceDown` | `up{job="faze-api"} == 0` | 1m | P0 |
| `FazeIdentityBroken` | 资金恒等式不成立 | 即时 | **P0** |
| `FazeHighErrorRate` | 5xx 占比 > 5% | 3m | P1 |
| `FazeHighLatency` | P95 > 1000ms | 5m | P1 |
| `FazeBackupStale` | 距上次备份成功 > 36h | 即时 | P1 |
| `FazeDiskLow` | 磁盘 > 80% | 5m | P2 |

> **已知冗余**：阈值同时写在 `alert-rules.yml` 与 `sys_config`。改阈值要改两处（段 8 前统一为「规则文件读配置」）。

### 3.3 告警没响怎么办

1. 先看 `scripts/alert/mock-receiver.py` 是否收到（证明系统侧发出正常）
2. 再单独 POST 一次钉钉 webhook 测加签（证明通道正常）
3. **两者分开排查**，不要混在一起猜

## 四、备份与恢复

### 4.1 备份

```powershell
.\scripts\backup\backup.ps1
```

| 项 | 值 |
|---|---|
| 方式 | `mysqldump --single-transaction --routines --triggers` |
| 频率 | 每日 03:00（Windows 计划任务） |
| 存放 | `E:\faze-backup\faze_YYYYMMDD_HHmm.sql` |
| 保留 | **30 天**（另保留最后 3 份不论日期） |
| 校验 | 文件大小 > 0 且 > 上次 × 0.5（防空文件） |
| 失败 | 重试 3 次 → 仍失败则**告警**（`FazeBackupStale`） |

### 4.2 恢复演练

```powershell
.\scripts\backup\restore.ps1 -File E:\faze-backup\faze_20261102_0300.sql
```

| 项 | 值 |
|---|---|
| 目标库 | **固定 `faze_restore`**（脚本硬校验：目标库名等于 `faze` 则直接退出） |
| 校验 | 逐表行数比对 + 抽 3 张表各 10 行 MD5 |
| 业务可用性 | 把服务 datasource 临时指向 `faze_restore` 起一次 → 能登录、能查单 |
| 频率 | **每季度一次**（技术路线 §17.5） |

> **恢复演练绝不许指向生产库。** 脚本里的保护逻辑不许删。

## 五、日志与留存

| 类型 | 位置 | 留存 |
|---|---|---|
| 应用日志 | `logs/faze-api.log` | 30 天 |
| 错误日志 | `logs/faze-api-error.log` | 90 天 |
| `operation_log`（审计） | 数据库 | **≥ 3 年**（个保法/电商法） |
| `login_log`（审计） | 数据库 | **≥ 180 天**（网安法） |
| 审计降级文件 | `logs/audit-fallback.log` | 30 天；**出现即 P1 告警**（审计链断了） |

- 配置项：`audit.operation-log-days`（默认 1095）/ `audit.login-log-days`（默认 180）
- **启动校验**：低于 1095 / 180 时服务拒绝启动
- 清理任务：每日 04:00，**先归档到 `logs/archive/*.csv` 再删**；归档失败则不删

## 六、生产部署时要做的事（本机已做的不够）

| # | 事项 | 为什么 |
|---|---|---|
| 1 | 监控独立部署（不与应用同机） | 应用挂了监控也挂，等于没监控 |
| 2 | 告警多通道（钉钉 + 短信 + 电话） | P0 不能只靠一个群消息 |
| 3 | 真实 IP 采集（反向代理 `X-Forwarded-For`） | 否则审计里的 IP 全是 `127.0.0.1` |
| 4 | 备份异地存放 | 本机磁盘坏了备份一起没 |
| 5 | 敏感词热更新改版本号轮询 | Pub/Sub 在多实例下会丢消息 |

## 七、故障分级与处置（速查）

| 故障 | 分级 | 第一步 |
|---|---|---|
| 服务起不来 / health 不通 | P0 | 看 `logs/faze-api-error.log` 最后 50 行 |
| 数据库连不上 | P0 | `mysql -e "select 1"`；看连接池日志 |
| 余额 ≠ SUM(流水) | P0 | **停止一切资金写入**，导出 `balance_flow` 全量，找差异账户 |
| 支付成功率骤降 | P1 | 看渠道回调日志与 `recharge_record` 的 `failed` 行 |
| 接口错误率 > 5% | P1 | Grafana 看是哪个 path，再看该 path 的错误日志 |
| 备份失败 | P1 | 看 `logs/backup.log`；先手工跑一次备份 |
| 敏感词误杀大量用户 | P1 | A-25 把该词降级或停用（**不重启即生效**） |
